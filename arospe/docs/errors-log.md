## CSS Grid's default `align-items: stretch` lets one tall sibling cell distort a Flux `<ui-field>`'s own internal row heights in its unrelated neighbours — 2026-09-11

- **Context**: bugfix pass on `resources/views/livewire/shipping.blade.php`'s create/edit rate modal (`App\Livewire\Shipping\Index`, story 0037's own screen). A user report: the Min./Max. weight/Price row rendered visibly misaligned — the "Max. weight (kg)" input sat noticeably lower than its two siblings.
- **What happened**: the three fields sit in one `grid grid-cols-3` row. "Max. weight" alone carries a `:description` help text ("Leave blank for 'and above' -- no upper limit."). `flux:with-field` renders `:description` **before** the slotted control inside its own `<ui-field>` (a `display: grid` custom element with one implicit row per direct child), so the extra description row pushed that one field's *input* down relative to its siblings, which have no description of their own. Moving the help text to `:description:trailing` (rendered *after* the control) was tried first and made a second, unrelated bug visible: the translation string's real double quotes, echoed once by `with-field.blade.php`'s own `{{ $description }}`, rendered as a literal `&quot;` in the browser instead of a real quote — reproduced by execution, not by reading the Blade source. Moving the help text **outside** `flux:input` entirely (a plain sibling `<flux:text>` after it, inside a wrapping `<div>`) fixed the quote-escaping regression but only *narrowed* the misalignment (measured 40px → 18px) rather than closing it: with the wrapper cell now taller than its siblings (from the extra sibling text), the two *other* fields' own `<ui-field>` — untouched, identical markup — measured a label row height of 35.5px instead of their normal 17.5px, verified with `getComputedStyle`/`getBoundingClientRect` via a headless-browser diagnostic script, not assumed from the Blade source.
- **Root cause**: the `grid grid-cols-3` container had no `align-items` override, so it used CSS Grid's default `stretch` — every cell in the row is stretched to the height of the tallest one. Once "Max. weight"'s own cell grew taller (from the sibling help text), its neighbours' `<ui-field>` cells (still `display: grid` internally, with an implicit-row layout) were stretched too, and that extra stretched height was redistributed across **their own** internal grid rows in a way that shifted their label/input position — not merely added blank space at the bottom. This reproduced with byte-identical DOM structure between the tall and short fields (confirmed by diffing `outerHTML`), so the discrepancy is purely a stretch/redistribution effect, not a markup difference.
- **Fix applied**: added `items-start` to the row's grid container (`class="grid grid-cols-1 items-start gap-4 sm:grid-cols-3"`), so every cell keeps its own natural height instead of stretching to the tallest. Combined with the help text living outside `flux:input` (a sibling `<flux:text>` with an explicit `id`, referenced by an explicit `aria-describedby` on the input — restoring the accessibility association `:description` would otherwise have wired up automatically), all three inputs now measure the exact same `top` in the rendered DOM. Verified visually and by measurement (not merely "no PHP/console error") before and after. See `resources/views/livewire/shipping.blade.php`'s inline comment at the grid container for the full reasoning, kept in place rather than only in this log.
- **How to avoid it next time**: **a CSS Grid row of Flux fields with uneven natural heights (one field carries a description/help text the others don't) must not rely on the default `align-items: stretch`** — it does not merely add blank space to the shorter cells, it can let the stretched height propagate into a Flux `<ui-field>`'s *own* internal grid layout and shift where its label/input actually sit, even though that cell's markup never changed. Add `items-start` (or `items-end` if anchoring to the bottom is the actual intent) to any grid row mixing fields with and without a description/help text. Separately: **`:description:trailing` is not a safe drop-in replacement for `:description` in this codebase** — it double-escapes a translation string containing literal quote characters (verified by execution, rendering a literal `&quot;`); when a field's help text must not affect sibling alignment, move it to a plain sibling element outside `flux:input` instead, with an explicit `id`/`aria-describedby` pair to keep the accessibility association `with-field.blade.php` would otherwise provide for free. Diagnose alignment bugs like this by measuring the real rendered DOM (`getBoundingClientRect`/`getComputedStyle` via a headless browser) before proposing a fix — reasoning from the Blade source alone would not have predicted either failure mode here.

> **Widened same day (2026-09-11) — the first pass fixed only the reported row and missed a second, structurally identical instance in the same modal.** The Carrier/Zone row above the weight row (`grid grid-cols-1 gap-4 sm:grid-cols-2`) has the exact same shape: "Zone"'s cell is taller than "Carrier"'s because it carries a "Manage shipping zones" link underneath the select, and the grid had no `align-items` override either — so "Carrier"'s own `<ui-field>` was distorted the identical way, only surfaced once the user pointed at a still-misaligned screenshot after the first fix shipped. **The rule this adds: when this failure mode is found in one grid row, grep the same file for every other `grid grid-cols-` container and check each one for a sibling with extra content (a link, a help text, a badge) that makes its cell taller than its neighbours' — fixing only the row a screenshot happened to show is not the same as fixing the file.** `items-start` was added to this second grid too; both grids in this modal now carry it.

## A `data-test` hook on `<flux:modal>` itself is always present, open or closed — a "the modal stayed open" assertion needs the hook on conditionally-rendered content inside it — 2026-09-10

- **Context**: story 0039 (payment methods store-settings screen — UI), the edit modal on `resources/views/livewire/payment-methods.blade.php`. B2's browser test — the highest-risk scenario on this screen, per the task's own analysis — must prove a checksum-invalid IBAN rejection leaves the modal **open** rather than closed, alongside proving the previously-configured IBAN keeps showing and the database is unchanged. The first draft put `data-test="payment-method-modal"` directly on the outer `<flux:modal name="payment-method-modal" wire:model="showModal">` tag, the same tag every other property on the modal (`wire:model`, `@close`) already lives on.
- **What happened**: found during this story's own code review before it shipped as a live test gap, rather than after — `assertPresent('@payment-method-modal')` would have passed regardless of whether the save actually failed and the modal genuinely stayed open, because the hook was on an element Flux renders **unconditionally**. A test written against it would have looked like it verified "the modal remains open" while actually verifying nothing about `$showModal`'s real value.
- **Root cause**: `<flux:modal>` always renders its own wrapper markup in the DOM — Flux implements open/closed as CSS/JS visibility state on that wrapper (the underlying `<dialog>`/`<div>` element), not as a PHP conditional that removes the tag from the response. Livewire's own `wire:model="showModal"` binding controls *visibility*, not *presence*. So a hook placed on `<flux:modal>` itself answers "did this component mount a modal at all" (always true on this screen, from first paint), never "is the modal open right now" — the two questions look identical from the Blade source but are not the same assertion.
- **Fix applied**: `data-test="payment-method-modal"` moved onto the modal's own **inner** `<div>`, which is wrapped in `@if ($showModal)` inside the `<flux:modal>` tag — so the hook is only ever in the rendered HTML while the modal is genuinely open. `tests/Browser/PaymentMethodsIndexTest.php`'s B2 (`assertPresent('@payment-method-modal')` after a rejected save) and B3 (`assertMissing('@payment-method-modal')` after Cancel) both now assert something real, and both carry an inline comment stating why the hook sits where it does.
- **How to avoid it next time**: **when a test needs to assert a Flux modal's open/closed state structurally (not by inferring it from a side effect), put the `data-test` hook on content that is itself conditionally rendered inside the modal — `@if ($showModal) ... @endif` — never on the `<flux:modal>` tag itself, which is present in the DOM from first paint regardless of open/closed state.** This generalises past `<flux:modal>` to any Flux component whose "closed" state is implemented as CSS/JS visibility rather than PHP conditional rendering (a `flux:dropdown`'s popover body is the same shape) — verify by reading the rendered HTML with the component in both states, not by reasoning from the Blade source, the same discipline this log's other Flux/Blaze entries already establish.

## A SECOND `->call()` on an already-mounted `Livewire::test()` component does not re-throw `AuthorizationException` the way the first one does — 2026-09-10

- **Context**: story 0038 (payment methods backend), Phase 5 code review finding N1 — adding a test that revokes `payment-methods.edit` **between** `App\Livewire\PaymentMethods\Index::openEditModal()` succeeding and `save()` being called, to prove `save()` carries its own gate rather than inheriting one only from `openEditModal()`.
- **What happened**: the first draft wrote `expect(fn () => $component->set('iban', ...)->call('save'))->toThrow(AuthorizationException::class);` — the identical shape every `openEditModal()`-refusal test in this app already uses successfully (e.g. `expect(fn () => Livewire::test(Index::class)->call('openEditModal', ...))->toThrow(AuthorizationException::class)`). It failed with `Exception "Illuminate\Auth\Access\AuthorizationException" not thrown.` A debug reproduction confirmed the gate genuinely ran and genuinely refused — `$method->fresh()->iban` stayed at its original value after the call — but no PHP exception of any kind propagated out of `->call('save')` for `expect()->toThrow()` to catch.
- **Root cause**: not fully traced to a specific line in Livewire's internals, but empirically confirmed to depend on **which call in the chain** the exception is thrown from. `Livewire::test(Index::class)` (the component's *first* mount, plus any method chained directly onto that same expression) runs synchronously in the test's own call stack, so an exception thrown there is a normal PHP exception `expect()->toThrow()` catches correctly. A **second**, later `->call()`/`->set()` on an *already-hydrated* `$component` variable goes through Livewire's request-simulation pipeline instead, which appears to intercept `AuthorizationException` and turn it into a response object rather than letting it escape as a thrown exception — so nothing reaches `expect()->toThrow()`, and the test fails on "exception not thrown" even though the refusal itself worked exactly as intended.
- **Fix applied**: rewrote the test to `try { $component->set(...)->call('save'); } catch (AuthorizationException) { /* nothing */ }`, followed by a plain assertion on the resulting database state — the exact shape `tests/Feature/SalesRegions/RefusalLoggingTest.php`'s own `'save() authorization refusal is logged'` test already uses for the identical "revoke, then a second `->call()`" scenario, discovered only after tracing why that file's test wasn't written the "obvious" `expect()->toThrow()` way either. See `tests/Feature/PaymentMethods/AuthorizationTest.php`.
- **How to avoid it next time**: **when writing a Livewire authorization test that revokes a permission and then calls a SECOND method on an already-mounted `Livewire::test()` component (as opposed to the very first `Livewire::test(Component::class)->call(...)` in one chain), use `try { ... } catch (ExceptionClass) {}` followed by a state assertion — never `expect(fn () => ...)->toThrow(...)`.** The two call positions are not interchangeable even though they look identical at the call site; this repo already had the correct pattern in `SalesRegions\RefusalLoggingTest.php` with no comment explaining why it differs from the `openEditModal()`-first-call tests beside it, which is exactly the kind of silent precedent this log exists to make explicit. Before writing a *second*-call authorization-refusal test from scratch, grep an existing `RefusalLoggingTest.php` for the shape rather than copying the first-call pattern by pattern-matching alone.

## Livewire skips `ConvertEmptyStringsToNull`/`TrimStrings`, and Laravel skips non-implicit rules for a blank string — the two combine to let a raw `''` reach a `DECIMAL` column — 2026-09-10

- **Context**: story 0037 (shipping carriers and rates — UI), the `maxWeightKg` field on `App\Livewire\Shipping\Index`'s create/edit rate modal — `''` (blank) is the "and above" sentinel for `shipping_rates.max_weight_kg`, so a blank submission is a legitimate, common input, not an edge case. - **What happened**: read out of installed vendor source rather than assumed, three findings compounded into a real gap. **(1)** `vendor/livewire/livewire/src/Mechanisms/HandleRequests/HandleRequests.php:80-89` opts every `/livewire/update` request out of Laravel's global `ConvertEmptyStringsToNull` and `TrimStrings` middleware (`skipWhen(fn () => $this->isLivewireRequest())`), so a blank form field reaches the component as a literal `''`, never `null`, and untrimmed. **(2)** `'nullable'`'s own short-circuit only fires for a genuine PHP `null` — `Validator::isNotNullIfMarkedAsNullable()` (`Validator.php:886`) tests `is_null()`, and `''` is not null. Re-verified directly against `phpunit.xml:29` and `.env.example:28`: both pin `DB_CONNECTION=mysql`, with the latter's own comment reading *"never SQLite"* — there is no CI/production engine divergence in this repo at all. - **Root cause**: Livewire's request-payload opt-out (finding 1) and Laravel's blank-string implicit-rule skip (finding 2) are two independent, individually-documented behaviours that nobody had previously combined against a `nullable` decimal field on this project — each is correct in isolation, and the interaction is what is dangerous. A `'nullable'` rule reads, at a glance, as "this field tolerates absence," and the pre-existing inline comment stated exactly that reading without qualifying it — true for a real `null`, silently **not** true for the blank string a form control actually submits.
- **Fix applied**: `App\Livewire\Shipping\Index::saveRate()` normalises `$maxWeightKg` to a real `null` (`trim($this->maxWeightKg) === '' ? null : ...`) as the first statement after authorization and *before* `Validator::make(...)->validate()` ever runs — never relying on the blank-string skip to "coincidentally" behave safely. `App\Concerns\ShippingRateValidationRules::maxWeightRules()`'s own inline comment and docblock were corrected in place (quoting the old text per this project's audit-authored-page convention) to state precisely what `'nullable'` does and does not protect against, so a future caller of that trait cannot make the same assumption this story's own first draft made.
- **How to avoid it next time**: **a `'nullable'` validation rule protects only a genuine `null` value — it says nothing about a blank string, and on a Livewire `/livewire/update` request a blank form field is *always* a blank string, never `null`, because Livewire deliberately opts every such request out of `ConvertEmptyStringsToNull`.** Two concrete habits. **(a)** When a `wire:model`-bound field's "empty" state must reach a `nullable` database column, normalise the sentinel (`''`) to a real `null` in the component, before validation — never assume the validator's own rule chain will do it, since Laravel's blank-string skip (`presentOrRuleIsImplicit()`) is a *different* mechanism from `nullable`'s null-check and happens to produce a similar-looking "the field passed" outcome for a completely different reason. **(b)** Before writing a comment that claims a story-wide engine divergence (SQLite-green, MySQL-500, or the reverse) explains why a bug is masked, verify the actual connection every environment uses — `phpunit.xml` and `.env.example` here, checked directly rather than assumed from a plausible-sounding narrative — since a false "it's only a CI artifact" framing understates a bug that, as here, 500s in every environment including the one meant to catch it.

And more generally: **before trusting a shipped test's own inline comment about what it proves, re-derive the mechanism independently** — read the actual driver/helper source, as this story's `frontend-qa` did for `InteractsWithElements::select()`, rather than accepting a plausible-sounding claim at face value. ## `DB::transaction($fn, attempts: N)` retried a closure that mutated a model created outside it, producing a silent lost update reported as success — 2026-09-04

- **Context**: story 0029 (product variants — core backend). The same remediation that added `product_variants`' cross-table SKU-collision locking also added `attempts: 3` to three `DB::transaction()` calls (`CreateProduct`, `CreateProductVariant`, `UpdateProduct`), so the fixed lock order those transactions rely on converges under a real deadlock instead of 500-ing on the first collision.
- **What happened**: `appsec-auditor`'s Phase 4 re-audit — re-auditing the fix as new code, per the entry below on this same log — reproduced that `UpdateProduct`'s own retry was unsafe. Its closure captures `$skuChanged = $product->sku !== $sku` and then calls `$product->update([...])`, where `$product` is an `Eloquent` model **created outside the closure** and passed in as a parameter. Executed rather than reasoned about: on attempt 1, `update()` runs and `syncOriginal()` fires; on attempt 2 (after a rollback from a genuine `1213` or, far more likely, a `Lock wait timeout exceeded`), `$product->sku !== $sku` now reads `false` and `isDirty()` after `fill()` also reads `false` — so `update()` issues **no SQL at all**, the SKU re-derivation cascade is skipped entirely (`$skuChanged` gates it), and the action **returns a `Product` whose in-memory attributes show the new values** while nothing was actually written or rolled forward. A silent lost update, reported to the caller as a success. `App\Actions\Products\SyncProductGallery` shares the exact same shape (`forceFill(...)->save()` on the same outside-the-closure instance), so the featured-image/gallery write is lost with it.
- **Root cause**: `attempts: N` makes the closure **retryable**, and a retry restores the database to its pre-attempt state but does **not** reset any PHP object the closure mutated on a prior attempt — `Model::update()`/`save()` calls `syncOriginal()` on success regardless of whether the surrounding transaction later rolls back, so a second attempt reads its own first attempt's dirty-tracking as the baseline and silently no-ops. This is invisible by construction: `save()` on a model with nothing dirty is a **successful** no-op, not an error, so nothing throws and nothing logs. The two other `attempts: 3` sites in the same remediation (`CreateProduct`, `CreateProductVariant`) do **not** have this problem, because both build the row they mutate **inside** the closure via `forceCreate()` — a retried attempt there re-does real work rather than skipping it, the distinguishing property that makes `attempts: N` safe on one sibling and unsafe on another that looks identical from the outside.
- **Fix applied**: `UpdateProduct`'s `DB::transaction()` call now takes **no** retry parameter at all, with a comment above it naming this hazard so nobody re-adds `attempts: N` without re-deriving the analysis first — see [`app/Actions/Products/UpdateProduct.php`](../app/Actions/Products/UpdateProduct.php). The alternative fix considered and rejected was the key-passing shape `App\Actions\SalesRegions\SetSalesRegionActive` already established (pass **keys** into the closure, re-fetch every row the closure mutates from inside it, on every attempt) — not adopted here because `UpdateProduct` returns the caller's own `$product` instance and its cascade reads `$skuChanged` from a pre-mutation attribute, so re-shaping the action's return contract to close this window costs more than removing the retry outright. Full reproduction, the executed before/after table, and a second, coupled finding (`attempts` is silently inert on a **nested** `DB::transaction()` — only the outermost transaction's `attempts` ever fires, so `App\Livewire\Products\Editor::save()`'s own outer transaction, once story 0031 ships it, must **not** get an `attempts:` of its own without first fixing this same closure shape one level up) are in [security/derived-column-invariants.md](../security/derived-column-invariants.md#what-the-remediation-introduced-a-retried-transaction-is-a-retry-safe-unit-or-it-is-a-lost-update).
- **How to avoid it next time**: **adding `attempts: N` to a `DB::transaction()` call is a change to the closure's contract, not a flag — before adding it, check that every model, collection or accumulator the closure writes to was either created *inside* it or is re-fetched by key at the top of it, on every attempt.** The two safe shapes in this codebase: build/insert the row inside the closure (`forceCreate()`/`create()`, as `CreateProduct`/`CreateProductVariant` do), or pass primitive keys into the closure and re-read every row from the database as the closure's own first statement (as `SetSalesRegionActive` does). An Eloquent model instantiated *outside* the closure and mutated *inside* it is the common, easy-to-miss case, and it fails **silently** rather than loudly — there is no exception to catch, because a non-dirty `save()` is defined to succeed.

## An action's own parameter default reintroduced the omission ambiguity its stricter collaborator was built to close — 2026-09-01

- **Context**: story 0024, `App\Actions\Products\CreateProduct`/`UpdateProduct` wrapping `App\Actions\Products\SyncProductGallery` — the single writer of `products.featured_media_id` and every `product_media` row, whose own contract (D-17) is deliberately strict: the ordered gallery array it receives is the **complete, authoritative** new state, never a delta, so an omitted id is a detach and an empty array is "clear the whole gallery".
- **What happened**: the first implementation gave `CreateProduct`'s/`UpdateProduct`'s `$featuredMediaId`/`$orderedGalleryMediaIds` parameters ordinary PHP defaults (`= null`, `= []`) — the reflexive shape for "this field is optional". `appsec-auditor`'s Phase 4 audit round 1 flagged it as **F-1** (Medium): any caller that simply omitted the two arguments — a future queued job, a partial form submit, a test written before the gallery UI existed — would reach `SyncProductGallery` with an empty array and a `null` featured id, silently detaching every existing image and nulling the featured image, with no error and no way to distinguish "the caller meant to clear the gallery" from "the caller never mentioned it". The re-audit found the identical shape a second time (**F-6**) on `UpdateProduct`'s `$description` parameter, which had kept `CreateProduct`'s `= null` default even though the two actions are not equivalent for that field: on **create**, omitting `description` and "no description" are the same real state (a brand-new product genuinely starts empty), so the default is safe there and was deliberately kept; on **update**, omitting it does not mean "clear the description" — it usually means the caller never touched that field — so the identical-looking default silently wipes an existing description on a partial-field update.
- **Root cause**: `SyncProductGallery`'s whole design point is that **omission from its input is a decision, never left ambiguous** — that is what "complete, authoritative array" means. A default on the *wrapping* action's own signature reopens exactly the ambiguity the stricter collaborator exists to remove, one layer closer to the real caller: the collaborator can no longer tell "the actor explicitly submitted an empty gallery" from "the actor never mentioned the gallery at all", because both now produce the identical call. The `$description` case shows the same root cause without any collaborator in the picture at all — a full-replacement field on an **update** path has the identical property (omission from the payload is ambiguous between "clear it" and "leave it"), so the rule is not really about `SyncProductGallery` specifically.
- **Fix applied**: both `CreateProduct` and `UpdateProduct` now require `$featuredMediaId`/`$orderedGalleryMediaIds` with **no default** — a caller must always state intent, matching `SyncProductGallery`'s own contract. `UpdateProduct`'s `$description` parameter lost its `= null` default (F-6); `CreateProduct`'s keeps it, deliberately, with a docblock recording *why* the two actions are allowed to differ on this one parameter. See [`app/Actions/Products/CreateProduct.php`](../app/Actions/Products/CreateProduct.php) and [`UpdateProduct.php`](../app/Actions/Products/UpdateProduct.php).
- **How to avoid it next time**: **a default is safe on a parameter only when omitting it and the default's own value denote the *same real-world state* for every call site that will ever use it — never merely "this field is optional" as a convenience.** Two concrete checks. **(a)** When an action wraps a collaborator whose contract treats its input as complete and authoritative (a full-replace `sync()`, an ordered array, any "this is everything" shape), the wrapping action must not supply a default for the parameter it forwards — the collaborator's own strictness is undone the moment something upstream of it can omit the value silently. **(b)** On an **update** path specifically, a default that was correct on the matching **create** action does not transfer by symmetry — "no value yet" (create) and "value not being touched" (update) are different states, and only the first one is safely represented by a default. This is [the "absence in a payload from a partially-visible form is not a decision" family](errors-log-archive.md#a-guard-took-the-state-it-was-guarding-as-a-parameter-reopening-its-own-hole-one-level-up--2026-08-20) arriving from a new direction: there the ambiguity lived in the *payload a partially-visible UI form submits*; here it lives one layer lower, in the *action's own parameter defaults*, with no form or UI involved at all.

## An absolutely-positioned element with no explicit `top` takes its static position from DOM order, and can silently occlude a sibling — 2026-08-31

- **Context**: story 0022 (shared searchable multi-select component), building the results dropdown in [`resources/views/livewire/components/searchable-multi-select.blade.php`](../resources/views/livewire/components/searchable-multi-select.blade.php). The dropdown is `position: absolute` (D10's forced manual-popover shape — see [the debounce entry below](#a-livewire-directive-modifiers-duration-cannot-be-interpolated-as-part-of-a-component-tags-attribute-name--2026-08-31) for that deviation's own story) and carries no explicit `top-*` utility, relying on document flow for its offset — the same `mt-1`-only shape `wysiwyg-editor.blade.php`'s own link popover already uses.
- **What happened**: while the dropdown block was written directly after the search `<flux:input>` and before the chip row, opening it with any rendered height at all — including just the empty-state message — visually and interactively covered the chip row beneath it. `Livewire::test()` and the whole component-level Feature suite stayed green throughout, because neither ever renders real CSS; the defect surfaced only in a real browser test, as a Playwright click on a chip's remove control hanging until the tool's own actionability timeout — no PHP error, no console error, no failed HTTP request anywhere to point at.
- **Root cause**: `position: absolute` removes an element from normal flow for layout purposes, but its **static position** — the position it would have occupied had it stayed `static` — is still derived from DOM order, and nothing in this markup ever overrode that with an explicit `top`. The dropdown and the chip row are siblings; because the dropdown appeared first in source order, its static-position offset placed it directly over the chip row the moment it had any height, silently occluding the remove buttons underneath. `document.elementFromPoint()` at a chip's own remove-control coordinates returned the dropdown's empty-state `<div>`, not the button — confirmed by direct browser reproduction, the identical diagnostic the [`disabled:cursor-not-allowed` entry](errors-log-archive.md#disabledcursor-not-allowed-on-a-flux-button-was-never-the-cursor-the-user-saw--2026-08-16) further down this log already used to find a different DOM-vs-markup mismatch.
- **Fix applied**: the dropdown block in `resources/views/livewire/components/searchable-multi-select.blade.php` was moved to render **after** the chip area in source order, with no CSS change at all — the fix is purely a reordering, because it is the static-position fallback that moved. An inline comment above the dropdown records the exact failure (including the `elementFromPoint()` result) and forbids moving it back "for readability" without re-verifying.
- **How to avoid it next time**: **an absolutely-positioned element with no explicit `top`/`left` takes its placement from where it sits in the DOM, not from where it visually appears to sit relative to a sibling — fix an occlusion like this by reordering the markup, not by reaching for a `top` value, unless the offset genuinely needs to vary at runtime.** More generally: **when a real-browser click hangs on Playwright's own actionability timeout with no error anywhere in the stack, suspect occlusion before suspecting a broken handler** — `document.elementFromPoint()` at the target control's real on-screen coordinates is the fast, direct way to find out what the browser actually thinks is on top, and it is a diagnostic a `Livewire::test()`-only suite structurally cannot run. This is the same "the DOM's own ground truth disagrees with what the markup intends" lesson the `pointer-events`/`tooltip`-presence entries below already establish, arriving here through document flow instead of a Flux prop.

## A Livewire directive modifier's duration cannot be interpolated as part of a component tag's attribute NAME — 2026-08-31

- **Context**: story 0022, wiring `$debounceMs` (a per-consumer configurable prop, default 300) into the search input's debounce. The obvious form is `wire:model.live.debounce.{{ $debounceMs }}ms="search"`, mirroring the literal `wire:model.live.debounce.300ms` this app already uses elsewhere.
- **What happened**: `code-reviewer`'s Phase 2 INVEST review (finding B1) caught the shape before Phase 3 wrote real code around it — but it is worth recording because the *shape itself* had already been silently worked around twice, undocumented: [`resources/views/livewire/media/gallery.blade.php`](../resources/views/livewire/media/gallery.blade.php) hard-codes a literal `wire:model.live.debounce.300ms`, and [`resources/views/livewire/components/wysiwyg-editor.blade.php`](../resources/views/livewire/components/wysiwyg-editor.blade.php) sidesteps the whole shape by debouncing through a hand-rolled Alpine `setTimeout()` instead. Neither prior file states *why* a dynamic duration was avoided; story 0022's own implementation is the first to write the reason down, in [`resources/views/livewire/components/searchable-multi-select.blade.php`](../resources/views/livewire/components/searchable-multi-select.blade.php)'s file-banner comment.
- **Root cause**: Blade's `ComponentTagCompiler` parses a component tag's attribute **names** with the regex `[\w\-:.@%]+`, which does not include `{`, `}` or `$` — so an interpolated `wire:model.live.debounce.{{ $debounceMs }}ms` attribute *name* is not a shape `compileComponentTags()` can parse at all, because that compiler runs before Blade's own `{{ }}` echo compiler ever sees the string. This is a **different** failure from the three `livewire/blaze` attribute-*value*-folding traps already in this log (the bare-`@disabled`, the conditionally-bound `tooltip`, and the two-`@directive()` entries below): those are about a value not compiling correctly inside a folded Flux tag; this is about a dynamic segment inside the attribute's own **name**, which no Blade component tag — Flux-folded or not — can ever parse, because the tag compiler never gets as far as evaluating anything for a name it cannot even tokenize.
- **Fix applied**: `resources/views/livewire/components/searchable-multi-select.blade.php` uses a plain (non-`.live`) `wire:model="search"` for deferred binding, plus a hand-rolled Alpine `x-on:input="clearTimeout(searchDebounceTimeout); searchDebounceTimeout = setTimeout(() => $wire.set('search', $event.target.value), {{ $debounceMs }})"` — the same debounce mechanism `wysiwyg-editor.blade.php` already established, now stated as the *reason* rather than merely followed. `{{ $debounceMs }}` interpolates cleanly here because it sits inside an ordinary attribute **value** (`x-on:input="..."`), the shape Blade *does* compile correctly throughout this file — the file's own banner comment states the distinction explicitly so a future reader does not "fix" the working value-interpolation back into the broken name-interpolation form for consistency.
- **How to avoid it next time**: **a `wire:*.debounce.Xms`-style Livewire directive *modifier* is part of the attribute's name, and a value that must vary per consumer (a prop, not a compile-time constant) cannot be interpolated into it — reach for a hand-rolled Alpine `setTimeout()` + `$wire.set(...)` instead**, the mechanism `wysiwyg-editor.blade.php` already established, and write the reason into a comment rather than leaving the next reader to rediscover it by trial and error. This generalizes past debounce: **any Livewire directive whose configuration lives in its modifier chain (`.debounce.Xms`, `.throttle.Xms`, …) is fixed at compile time and cannot vary per component instance** — a literal duration works, a property never will.

## A bare `@disabled(...)`/`:disabled="..."` inside a `<flux:button>` tag's attribute list corrupts the whole compiled view — 2026-08-31

- **Context**: story 0021 (shared WYSIWYG rich-text editor), building the eight-button toolbar in [`resources/views/livewire/components/wysiwyg-editor.blade.php`](../resources/views/livewire/components/wysiwyg-editor.blade.php). Every button needs to render `disabled` when the component's own `$disabled` read-only flag is `true` — the same conditional-attribute shape it would be tempting to write as one `<flux:button ... @disabled($disabled) />` tag, the way a plain HTML `<button>` would take it.
- **What happened**: `code-reviewer`'s Phase 5 review (finding N4) reproduced, via direct `Blade::render()` execution, that a bare `@disabled(...)` — or an equivalent `:disabled="..."` binding — written inside a `<flux:button>` tag's attribute list does not compile the way it would on a plain HTML tag. It corrupts the tag's **whole** attribute string into invalid PHP, which is a PHP **syntax error** that breaks the entire compiled view — not merely that one button's disabled state, and not a silent mis-render like the two traps immediately below. Any page embedding the component would 500 outright.
- **Root cause**: `livewire/blaze` (already implicated in the two entries directly below this one) folds `@blaze`-annotated Flux components at compile time, and its component-tag compiler parses a tag's raw attribute list **before** the general Blade directive pass runs. `@disabled(...)`/`:disabled="..."` written as if it were an ordinary attribute is not a form that parser tolerates inside a folded tag — it does not resolve to a conditional `disabled=""` the way it would on a native HTML element; it corrupts the compiled attribute string outright.
- **Fix applied**: every one of the toolbar's eight controls in `resources/views/livewire/components/wysiwyg-editor.blade.php` is written as a full `@if ($disabled) <flux:button ... disabled /> @else <flux:button ... x-on:mousedown.prevent="..." /> @endif` pair — two complete, separately-compiled tags — rather than one tag carrying a conditional `disabled` attribute. An inline comment sits directly above the first occurrence, naming the finding and pointing at the two related traps below so nobody "simplifies" it back into a single conditional attribute.
- **How to avoid it next time**: **in this codebase, never write a bare `@disabled(...)` directive directly inside a `<flux:*>` component tag's attribute list — branch the whole tag with `@if`/`@else` instead**, exactly as the `tooltip`-presence trap and the `cursor-not-allowed!` placement rule immediately below already establish for other props on the same kind of tag. This is now the **third** documented Flux/Blaze markup trap sharing one root cause (`livewire/blaze`'s compile-time folding not tolerating a directive where a plain attribute is expected) — verify any new one by rendering the real compiled view (`Blade::render()`, or a rendering test asserting real HTML), never by reading the Blade source. This one is easier to catch than its two siblings only because it throws outright rather than silently mis-rendering — but only for whoever renders the page first, which in an untested branch may be a real user.

This is the same family as the [deferred-findings entry](errors-log-archive.md#a-deferred-storys-findings-were-claims-about-a-tree-that-no-longer-existed-and-one-of-them-would-have-reopened-a-bug-in-this-log--2026-08-23) — a claim about a tree, outliving the tree — with the shortest fuse of any of them: one of these was false on the day it was written, and the other never true at all.

## A stale `public/hot` file from an old `npm run dev` session made all 19 browser tests time out, misread as real UI bugs — 2026-08-28

- **Context**: running the full `php artisan test` suite (per docs/workflow.md Phase 5, verifying tasks `0019a`/`0019b` before closure) surfaced 19 failures, every one of them in `tests/Browser/{UsersIndexTest,RolesIndexTest,SalesRegionsIndexTest}.php` (`Timeout 5000ms exceeded`), and none in any Media/Feature/Unit test — a completely different, unrelated failure set from the two tests those tasks actually fixed.
- **What happened**: the saved Playwright screenshot for one timeout showed the real page loading, but with every element rendered at native browser defaults — gigantic unstyled SVG icons, near-invisible default-size text, no layout at all — the unmistakable signature of a page with **zero CSS applied**, not a broken component or a real product bug.
- **Root cause**: `public/hot` existed (dated the same day, `07:24`), left behind by an earlier `npm run dev` invocation that was never cleanly stopped. Laravel's `@vite()` directive checks for this file first and, when present, emits asset tags pointing at the Vite **dev server** (`http://localhost:5173/...`) instead of the built manifest in `public/build/` — confirmed via `curl`: the rendered `<link>`/`<script>` tags all pointed at port 5173, and nothing was listening there. Every page the browser tests visit therefore loaded with no CSS and no JS framework code, so every interaction-dependent assertion (a dropdown populating, a modal opening, Flux's JS initializing) hit its 5-second timeout waiting for a DOM state that could never arrive.
- **Fix applied**: `rm public/hot` (gitignored, per `.gitignore:5` — never a repo file, never something to commit or restore). All 19 browser tests passed immediately afterward with no other change; the full suite went 950/950 with no code touched for this specific failure set.
- **How to avoid it next time**: **when every browser test in a run fails with a timeout and none of them share an obvious functional cause, check for a stale `public/hot` before debugging any of the tests themselves.** `ls public/hot` (or a saved failure screenshot showing completely unstyled markup, which is the visual signature) settles it in seconds — killing an `npm run dev` process by closing a terminal, rather than `Ctrl+C`ing it, is what leaves this file behind, since Vite's own exit hook is what normally deletes it. This is the same failure shape [the Frontend Bundling rule in `CLAUDE.md`](../CLAUDE.md) already names as a first troubleshooting step ("ask the user to run `npm run build`/`npm run dev`") — the addition here is `public/hot` specifically as the file to check, and that a bulk timeout across otherwise-unrelated browser test files is the tell that it's environmental, not a regression in any of them.

## An Imagick resource limit was requested in the wrong unit, masked by the host's own `policy.xml` silently clamping it — 2026-08-28

- **Context**: task 0019a, investigating why `tests/Unit/Actions/Media/GenerateImageConversionsResourceLimitsTest.php` (story 0019) failed consistently — on every run, sequential and parallel, throughout this session — while a companion behavioral test in the same file (a genuine oversized image is actually refused) kept passing.
- **What happened**: `Imagick::getResourceLimit(Imagick::RESOURCETYPE_AREA)` read back `256000000` after `GenerateImageConversions::applyImagickResourceLimits()` requested `1024000000` (`MAX_DIMENSION^2 x BYTES_PER_PIXEL_CEILING`, the same formula also correctly used for `MEMORY`/`MAP`). No exception, no warning — the request was silently satisfied with a smaller value.
- **Root cause**: two facts, neither previously verified against this project's real container. **(1) `RESOURCETYPE_AREA` is a pixel-count resource** (mirroring `WIDTH x HEIGHT`), **not a byte-count one** like `MEMORY`/`MAP` — applying the same "bytes per pixel" formula to it was a category error, present in the code and in [security/image-upload-processing.md](security/image-upload-processing.md)'s docblock quote alike. **(2) `Imagick::setResourceLimit()` can only tighten a resource below the host's `policy.xml` ceiling, never loosen it, and clamps silently** — confirmed by direct reproduction (`tinker`): requesting `1024000000` for `AREA` when the policy ceiling is `256000000` leaves the limit at `256000000`; requesting `100` (below the ceiling) takes effect immediately. This project's `docker/8.5/Dockerfile` installs Debian's packaged **ImageMagick 6.9.12-98 Q16** (via `php8.5-imagick`) — a different major version and build than the `ImageMagick 7.1.2-8 Q16-HDRI` [security/image-upload-processing.md](security/image-upload-processing.md) was measured against — and Debian's package ships a restrictive default `/etc/ImageMagick-6/policy.xml` that page's own "there is no `policy.xml` on this project's ImageMagick install" line said didn't exist. Both facts compounded: the wrong unit (item 1) only produced a visible failure because the host's policy (item 2) happened to be *more* restrictive than the value being wrongly requested — on a policy-less host, the same bug would have silently passed while providing far weaker protection than the docblock claimed.
- **Fix applied**: `app/Actions/Media/GenerateImageConversions.php` now requests `MAX_DIMENSION^2` (a pixel count) for `RESOURCETYPE_AREA`, matching `WIDTH x HEIGHT`; `MEMORY`/`MAP` are unchanged. Test updated to match. [security/image-upload-processing.md](security/image-upload-processing.md) gained a dated correction block rather than a silent rewrite, per [this log's own rule](errors-log-archive.md#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20) for audit-authored pages. See task `0019a`.
- **How to avoid it next time**: **when a resource-limit or capacity value is requested via a system library, verify the *unit* the library actually uses for that specific resource type — don't assume every same-shaped call in a group (`WIDTH`/`HEIGHT`/`AREA`/`MEMORY`/`MAP`/`DISK`/`TIME` here) shares the same unit just because the code sets them all in one function.** And separately: **a value-clamping ceiling (a system `policy.xml`, a cloud quota, a `ulimit`) that silently accepts a too-large request instead of erroring is exactly the shape that hides a wrong-unit bug for months** — the test that would have caught this immediately (asserting the *effective, read-back* value rather than trusting the call succeeded) is precisely the test story 0019 wrote, and it worked exactly as intended the moment it ran against a host whose policy was strict enough to expose the mismatch. Don't weaken a test like this to make it pass "on some hosts" — fix the unit instead.

## A test suite's own "runs as non-root" claim was re-verified using the wrong `sail` invocation — 2026-08-28

- **Context**: task 0019b, investigating a `chmod(0555)`-based permission test (`tests/Unit/Actions/Media/GenerateImageConversionsFailedWriteTest.php`) that flaked once under full-suite `--parallel` load. Its inline comment claimed the suite "runs as a non-root local user (uid=1000)" as the reason `chmod()` reliably blocks the write.
- **What happened**: `./vendor/bin/sail exec laravel.test whoami` was used to "verify" this and returned `root`, leading to a first-pass conclusion that the comment was stale (the container had started running tests as root since the comment was written) and that the chmod-based mechanism must be working "for a different reason" — Flysystem's `is_writable()` pre-check, reasoned to hold regardless of the real uid. That conclusion was wrong.
- **Root cause**: `sail exec <service> <cmd>` and `sail artisan <cmd>` are **not the same invocation**. Reading `vendor/laravel/sail/bin/sail`: `sail artisan` (and `sail php`, `sail composer`, …) always runs `docker compose exec -u "$APP_USER"` where `APP_USER` defaults to `sail` (uid matching the host user); a bare `sail exec` does not add `-u` and defaults to root. The actual test suite is run with `sail artisan test`, so it genuinely runs as uid 1000 — the original comment was correct. Checking the wrong invocation produced a confident, plausible-sounding but false "environment drift" explanation, exactly the failure mode [the 2026-08-24 hedge entry](errors-log-archive.md#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24) already warns about — except here the hedge was self-inflicted rather than inherited from a review comment.
- **Fix applied**: reverted the test file's comment to state the correct mechanism (uid 1000 via `sail artisan`, with a citation to the exact line in `vendor/laravel/sail/bin/sail`), verified directly with `posix_getuid()` through `sail artisan tinker` — the same invocation path the real suite uses. See task `0019b`.
- **How to avoid it next time**: **when verifying a fact about "the environment the tests run in," reproduce it through the *exact* command the tests themselves run, not a different one that happens to target the same container.** `sail exec`, `docker exec`, and `sail artisan`/`sail php` can resolve to different users, working directories, or entrypoints even against the identical service — the container is not the unit of truth, the invocation is.

## The full test suite, run repeatedly and heavily in one session, degrades in ways unrelated to any code change — 2026-08-28

- **Context**: the same test-suite performance/parallelization review and follow-up fix session as the two entries above and task `0019a`/`0019b`. Roughly eight full-suite `--parallel --processes=8` (or sequential) runs were executed back-to-back inside one Sail/WSL2 container over about an hour, on top of several `tinker` sessions.
- **What happened**: the first four or five full-suite runs were clean (one known, unrelated pre-existing failure). Later runs in the same session started failing 58–64 unrelated tests at once, almost all `ErrorException: tempnam(): file created in the system's temporary directory` surfacing as 500s on any test that renders a Blade view — none of them related to the code being changed. Restarting the `laravel.test` container reduced container-reported swap usage (1.4Gi → 790Mi) but did **not** clear the failures on the next run; a follow-up non-parallel, narrower run (`tests/Feature/Auth`, `tests/Feature/Users`, `tests/Feature/Media`) then ran in 126.8s — noticeably slower than its share of an earlier clean full run — with one different, also-unrelated Imagick decode failure.
- **Root cause**: not conclusively identified, and not chased further — writing up a specific mechanism here without having proven it would repeat the mistake the entry above just made. Two credible contributing factors, both consistent with what was observed and neither confirmed: (1) `storage/framework/views` (the compiled Blade view cache) is **not** isolated per parallel-test-token the way the database and `Storage::fake()` already are (verified: no `ParallelTesting::setUpTestCase()`/`setUpProcess()` hook anywhere in `app/`), so eight processes compile into the same directory concurrently — a plausible source of a `tempnam()`/rename race under load, though `getResourceLimit` output makes clear the file wasn't actually starved of space or descriptors. (2) This project's own docs already flag WSL2-specific memory behavior (`docs/testing/ci/commands.md`'s PHPStan memory-limit note); a container restart clearing only ~40% of reported swap, not all of it, is consistent with WSL2 not releasing host-level pages promptly, and sustained heavy load from repeated runs plausibly degrades the whole session rather than any single run.
- **Fix applied**: none. This is recorded as an open observation, not a closed finding — no code change addresses it, and it could not be reliably reproduced on a fresh run within this session's remaining time budget.
- **How to avoid it next time**: **don't run many consecutive full-suite `--parallel` executions back-to-back in one long-lived dev container/session when benchmarking or verifying a fix — space them out, or use a fresh container per measurement.** Before recommending `--parallel` for CI (a real, useful recommendation this session also produced — see the test-performance report in this session), pilot it on the actual CI runner across several independent, isolated runs rather than trusting a long local session, since this failure mode is exactly the kind that a single clean CI job (one process lifetime, no accumulated history) may never hit at all. If it recurs on a *fresh* run, the `storage/framework/views` per-token isolation gap above is the first thing to test — add a `ParallelTesting::setUpTestCase()` hook pointing `config('view.compiled')` at a `TEST_TOKEN`-suffixed directory, mirroring how `Storage::fake()` already does it, and see whether the failure stops reproducing.

> **Correction — 2026-08-28, same day, next investigation session.** The predicted fix above (per-token `view.compiled` isolation) was implemented and **empirically disproven as the cause**: a small, targeted slice (`tests/Feature/Auth`, `--parallel --processes=4`) reproduced the *exact same 9 tests* failing, deterministically, across repeated runs — with the per-token isolation hook already in place and its directories confirmed present and writable. Since the failure was 100% reproducible at small scale (not merely "under sustained load"), it was tractable to isolate properly: with the isolation hook reverted, the identical 9 tests failed in the identical way, proving conclusively that shared-directory contention between workers was never the mechanism.
>
> **The real cause: `storage/framework/views` sits inside the project's bind-mounted volume** (`.:/var/www/html` in `compose.yaml`), and concurrent `tempnam()`+`rename()` writes through Sail's WSL2↔Docker bind mount are unreliable — a well-known class of issue with bind-mounted volumes under concurrent I/O, unrelated to disk space, inode count, or file-descriptor limits (all confirmed plentiful). **Fix**: `storage/framework/views` is now a named Docker volume (`sail-views` in `compose.yaml`), native to the container rather than bind-mounted, with `docker/8.5/start-container` `chown`-ing it to the `sail` user on every container start (a fresh named volume is created owned by `root`, and `sail artisan` never runs as root). Verified: the exact reproduction that failed 9/9 consistently now passes 42/42, repeatably; the full 950-test suite passes cleanly under `--parallel --processes=8`, twice in a row (~128s and ~131s, vs. a ~338s sequential baseline — a genuine, stable ~2.6x). The per-token `view.compiled` isolation (`AppServiceProvider::configureParallelTesting()`) was kept as a nested subdirectory *inside* the now-fast volume (`storage/framework/views/test_{token}`) — harmless, and cheap insurance against worker contention even on a filesystem that no longer requires it.
>
> This is the same lesson [the entry above](#a-test-suites-own-runs-as-non-root-claim-was-re-verified-using-the-wrong-sail-invocation--2026-08-28) states in a different shape: an unconfirmed mechanism, however plausible, is a hypothesis to test, not a fact to build a fix around — and here the fastest way to confirm or disprove it was to find a **small, deterministic** reproduction instead of continuing to reason about a rare flake under sustained load. See [testing/ci/commands.md#run-in-parallel](testing/ci/commands.md#run-in-parallel) for the shipped numbers and [testing/worktree-databases.md](testing/worktree-databases.md) for the adjacent per-worktree isolation this does *not* replace (the volume is per-container, not per-worktree — two worktrees sharing one Sail container still need their own database names, exactly as before).
