_Previously: 2026-09-14 — Story 0045 (Orders core CRUD backend). Added [The three-way delete-behaviour rule: cascade, restrict, or null](../database/migrations/delete-behaviour-and-vendored.md#the-three-way-delete-behaviour-rule-cascade-restrict-or-null): `create_orders_table` and `create_order_items_table` are the first pair of migrations to exercise all three of this project's FK delete behaviours at once (cascade on `order_items.order_id`, restrict on `orders.customer_id`/`.payment_method_id`/`.sales_region_id`/`.shipping_rate_id`, null on `order_items.product_id`/`.product_variant_id`), which is what finally makes the underlying rule statable in one place — explicitly **not** framed as a first for any individual behaviour, since `passkeys.user_id` (cascade), `sales_regions.parent_id` (restrict) and `media.uploaded_by` (null) each already stood alone as that behaviour's example. Verified against a live, migrated instance (`php artisan db:table orders` / `order_items`) rather than read off either migration file; no hand-written index on any of the six FK columns either.

_Previously: 2026-09-10 — Story 0043 (Customers — "new customer" notification, backend). Added "A published stub is not the same thing as a package-vendored migration", distinguishing `notifications:table`'s published, editable, config-free stub from `create_permission_tables.php`'s genuinely package-vendored, config-driven one — the two are easy to conflate since both arrive via an Artisan command. Folded the prior `_Last updated:` line (story 0033) into a single line below, per [contracts.md](../contracts/token-and-doc-rules.md#doc-growth-management-rule)'s doc-growth-management rule.

_Previously: 2026-09-07 — Story 0033 (Shipping zones — backend). Corrected a stale, now-disproven claim under [Structure](../database/migrations/basics-and-alterations.md#structure): `create_passkeys_table`'s hand-written `$table->index('user_id')` was said to duplicate an index `constrained()` already causes InnoDB to create — measured directly (`php artisan db:table passkeys`) and found false, since InnoDB only auto-creates an FK-support index when no suitable index already exists; the hand-written index satisfies the requirement itself and merely changes the resulting index's name. Old text quoted in place per this project's audit-authored-page convention; the underlying design guidance (don't hand-write an FK index on a *new* table without a reason) is unaffected. Added `create_shipping_zone_geography_entry_table` as the "no explicit FK index" rule's **tenth** confirming instance and the first crossing a UUID FK and a `bigint` FK inside one composite primary key. Folded the prior `_Previously:` line (a 2026-09-05 footer collapse) into this single line, per the doc-growth-management rule in [contracts.md](../contracts/token-and-doc-rules.md#doc-growth-management-rule)._
