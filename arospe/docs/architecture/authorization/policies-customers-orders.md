# Authorization — Policies: Customer and Order

> Part of [Authorization](../authorization.md). **Read this part when:** you touch `CustomerPolicy` or `OrderPolicy` (the three-ability order screen, state-based refusals, the accepted Super Admin/Cancel drift). The other parts are listed in the [hub](../authorization.md#table-of-contents).

### `CustomerPolicy` — the eleventh policy, and the first a passive record with no privilege tier of its own

[`App\Policies\CustomerPolicy`](../../../app/Policies/CustomerPolicy.php) (story 0041) gates the `customers` catalog ([database/schema.md](../../database/schema-other/customers.md#customers)) on the already-seeded `customers.*` module permissions — no new permission, no `RolePermissionSeeder` change (`customers` has carried the four `.view`/`.create`/`.edit`/`.delete` slugs since task 0002). It is modelled directly on [`SalesRegionPolicy`](policies-sales-media-categories.md#salesregionpolicy--the-third-policy-and-the-first-with-no-target-branch) rather than re-derived: flat, tier-free abilities delegating straight to `hasPermissionTo()`, permission names as `public const` on the class, no target-dependent branch on `update()`.

| Ability | Signature | Rule | Authorized from |
| --- | --- | --- | --- |
| `viewAny` | `(User $actor)` | holds `customers.view` | `App\Livewire\Customers\Index::mount()` (story 0044) and `routes/customers.php`'s own `can:customers.view` middleware |
| `create` | `(User $actor)` | holds `customers.create` | `App\Actions\Customers\CreateCustomer::__invoke()`, its own first statement (class-level — no instance exists yet); and `Index::openCreateModal()`/`save()`, as a second layer |
| `update` | `(User $actor, Customer $target)` | holds `customers.edit` — `$target` is **not** consulted | `App\Actions\Customers\UpdateCustomer::__invoke()`, its own first statement; and `Index::openEditModal()`/`save()`, as a second layer |
| `delete` | `(User $actor, Customer $target)` | holds `customers.delete` — `$target` is **not** consulted | `App\Livewire\Customers\Index::confirmDelete()`/`deleteCustomer()` (story 0044) — there is no dedicated `DeleteCustomer` action, so the guard sits in the component by necessity, the same placement `App\Livewire\Users\Index::deleteUser()` already establishes for the identical reason |

**`delete()` (story 0042) is a fourth flat, tier-free ability, added to this same file rather than a new policy class — the hand-off 0041's own D-12 named.** It carries **no** privilege-tier branch, no ownership check and no self-target guard, unlike `UserPolicy::delete()`: any holder of `customers.delete` may delete any customer, because a customer holds no privilege tier to escalate through (0042's own D-3). 0041's own unit test asserting `CustomerPolicy` defined exactly `viewAny`/`create`/`update` and not `delete()` is updated in place by story 0042 rather than deleted or worked around, so the method-existence pin now asserts the opposite: all four abilities are defined.

**Corrected 2026-09-11 (story 0044) — the paragraph below described a route-and-component-free interim state that this story closed, and is quoted rather than silently rewritten, per this project's audit-authored-page convention.** It used to read: *"Why this policy has real call sites despite the story shipping no route or component — the identical shape `ShippingRatePolicy` already establishes. D-9's reconciling rule applies on its stronger half here: `create`/`update` each have **no route and no Livewire component at all** yet, so the action is the *only* reachable enforcement point that exists today, and each self-authorizes as its own first statement through a constructor-injected `App\Actions\Auth\LogRefusedPrivilegedAttempt::authorize(...)`, `targetType: 'customer'` passed explicitly (`resolveTarget()` auto-resolves only `User`/`Role`). `viewAny` satisfies the *other* half — no caller yet at all — with story 0044 named as its future consumer, matching how `ShippingRatePolicy::viewAny` waited for story 0037."* Story 0044 is that future consumer, shipped: [`App\Livewire\Customers\Index`](../../../app/Livewire/Customers/Index.php) is now a real, routed (`customers.index`) component authorizing all four abilities as the first statement of `mount()`/`openCreateModal()`/`openEditModal()`/`save()`/`confirmDelete()`/`deleteCustomer()`, so `create`/`update`/`delete` each have a second, component-layer enforcement point on top of the action's own self-authorization — the same two-layer shape [`ShippingRatePolicy`](policies-shipping-payment.md#shippingratepolicy--the-ninth-policy-and-the-first-with-real-call-sites-from-day-one) reached once story 0037 shipped its consumer. `create`/`update`'s constructor-injected `LogRefusedPrivilegedAttempt::authorize(...)` call inside the two actions is unchanged by this story — it logs the actor's own refusal regardless of which of the two layers (component or action) is the one that actually throws.

**Why `update()`/`delete()` ignore `$target` even though a customer *is* a full-CRUD entity, unlike the read-mostly catalogs (`SalesRegion`, `ShippingZone`) this shape was first built for.** **Corrected 2026-09-10 (story 0042) — the parenthetical below no longer holds, and is quoted rather than silently rewritten, per this project's audit-authored-page convention.** It used to read: *"`Customer` implements no auth contract, uses neither `HasRoles` nor `SoftDeletes` — story 0041's own D-11"*. `App\Models\Customer` now uses `SoftDeletes` (story 0042), so only the `HasRoles` half is still true; see [database/schema.md](../../database/schema-other/customers.md#soft-deletes-and-why-the-users-reasoning-does-not-transfer) and [security/soft-delete-patterns.md](../../security/soft-delete-patterns.md#a-second-soft-deleted-model-deliberately-unalike--appmodelscustomer-story-0042) for why `SoftDeletes` on `Customer` carries **no** authentication weight of any kind, so the rest of this paragraph's reasoning is unaffected: a customer record can never be the acting user and holds no privilege tier at all (`Customer` implements no auth contract and uses no `HasRoles`), so "may this actor edit/delete this customer" reduces to "does the actor hold `customers.edit`/`.delete`" with zero row-level nuance regardless of which customer is named — there is no Administrator-tier-style branch a `Customer` target could ever trigger the way a `User` target can on `UserPolicy::update()`/`delete()`. The `$target` parameter is kept anyway (not dropped from the signature) for the same two reasons [`SalesRegionPolicy`](policies-sales-media-categories.md#salesregionpolicy--the-third-policy-and-the-first-with-no-target-branch) keeps its own: a future per-row `Gate::allows('update', $customer)` UI hint asks the *identical* method the write authorizes with, so a hint can never drift from a click; and if a later story does introduce a row-level rule (a customer an actor may not view, a per-region restriction), it edits one method body rather than relocating every call site's target — evaluated against a freshly re-fetched row, never the caller's instance, per that policy's own Phase 4 note.

`VIEW_PERMISSION`/`CREATE_PERMISSION`/`EDIT_PERMISSION`/`DELETE_PERMISSION` (the last one added by story 0042) are `public const` on the class, per [naming.md](../../conventions/naming/routes-and-permissions.md#permission-names)'s convention — the **tenth** follower of it (`UserPolicy` remains the sole outlier among eleven policies).

### `OrderPolicy` — the twelfth policy

[`App\Policies\OrderPolicy`](../../../app/Policies/OrderPolicy.php) (story 0045) gates the `orders` domain ([database/schema-orders.md](../../database/schema-orders.md)) on the already-seeded `orders.*` module permissions — no new permission, no `RolePermissionSeeder` change (`orders` has carried the four `.view`/`.create`/`.edit`/`.delete` slugs since task 0002). It is modelled directly on [`ShippingRatePolicy`](policies-shipping-payment.md#shippingratepolicy--the-ninth-policy-and-the-first-with-real-call-sites-from-day-one) rather than re-derived — this story's own exact structural analogue: backend-only, no route, no Livewire component, the action as the sole reachable enforcement point.

| --- | --- | --- | --- |

| `create` | `(User $actor)` | holds `orders.create` | `App\Actions\Orders\CreateOrder::__invoke()`, its own first statement (class-level — no instance exists yet) |

| `cancel` | `(User $actor, Order $order)` | holds **both** `orders.edit` **and** `orders.refund` — **and** `$order->isManuallyCancellable()` | `App\Actions\Orders\CancelOrder::__invoke()`, its own first statement (a bare `Gate::authorize()`), story 0050 — see [Manual order cancellation](domain-invariants.md#manual-order-cancellation--the-third-state-based-refusal-and-the-first-ability-requiring-two-permissions) below |

**Five flat abilities from day one, no per-target branch on any of them — and `create` is the only one with a real caller *in this story*, deliberately.** This is a **stronger** instance of the "ships with no caller yet" shape [`CustomerPolicy`](#customerpolicy--the-eleventh-policy-and-the-first-a-passive-record-with-no-privilege-tier-of-its-own)'s `viewAny` already establishes: at story 0045's own close, three of the four abilities (`viewAny`/`update`/`delete`) had no caller, not one. The reason is named in the task file's own **D-13** rather than left implicit — stories 0048–0052 introduce genuinely **row-state-dependent** rules PRD §3.2 requires (editing an order's line items is blocked once it reaches `Shipped`; manual cancellation is blocked in three states; a refund is refused outside `Paid`/`PartiallyRefunded`), and every one of them is a branch added to `update()`'s or `delete()`'s **existing** method body rather than a new policy class or a relocated call site. Shipping the class now, with its abilities named and its permission constants fixed, is what lets five future stories each add one row-state branch instead of each deciding independently where the rule belongs — the same "ability ownership drifts across an epic otherwise" reasoning [`ShippingRatePolicy`](policies-shipping-payment.md#shippingratepolicy--the-ninth-policy-and-the-first-with-real-call-sites-from-day-one) already used to justify shipping all four abilities up front despite `viewAny` having no caller either.

**Corrected 2026-09-15 (story 0047) — `viewAny` gained its first real caller sooner than this section originally predicted, and the table row above is quoted rather than silently rewritten, per this project's audit-authored-page convention.** It used to name the caller as *"Nothing yet — story 0055's `mount()` is its first planned caller"*. `App\Livewire\Customers\Show` — the customer order-history screen — reached `Order::class` first: its `canViewOrderHistory()` gates the order-history section on `Gate::allows('viewAny', Order::class)`, the section-level ability guarding a cross-module disclosure (see [security/livewire-authorization.md](../../security/livewire-authorization/entry-point-and-method-gates.md#a-screen-owned-by-one-module-disclosing-another-modules-records)). `update`/`delete` remain uncalled, exactly as this paragraph's own reasoning anticipated for them specifically.

> ⚠️ **Extended 2026-09-17 (story 0050, order manual cancellation backend) — the policy's ability roster grows to SIX, and `cancel` breaks the "flat, no per-target branch" description every ability above it carries.** `App\Actions\Orders\CancelOrder::__invoke()` calls `Gate::authorize('cancel', $order)` as its own first statement (a bare `Gate::authorize()`, matching `transitionStatus`'s own choice over `LogRefusedPrivilegedAttempt::authorize()`), story 0050. Two things distinguish `cancel` from every ability that came before it. **(a) It is this app's first ability requiring TWO permissions** (`orders.edit` **and** `orders.refund`, via `OrderPolicy::ORDER_REFUND_PERMISSION` — the first class to name that permission with a `public const`, since story 0051's `RecordRefund` seeds and consumes it as a bare literal) rather than one, a human product decision (D-6 in the story's own task file): cancelling an order is administratively paired with a refund in practice, so an actor trusted to cancel must also be trusted to handle the refund conversation that usually follows. **(b) It is the first ability whose boolean return genuinely depends on the target row** — `$order->isManuallyCancellable()` (permitted only from `Pending`/`Processing`, and never while `payment_status` is `PartiallyRefunded`) — and that row-state clause has a real, non-obvious consequence: because `Gate::authorize('cancel', $order)` evaluates it too, an ORDINARY actor holding both permissions is refused by the Gate itself (`AuthorizationException`) the moment the order is in a guarded state, and never reaches `CancelOrder`'s own subsequent checks at all. Only a **Super Admin** — whose `Gate::before` bypass never consults `cancel()`'s body — ever reaches those, which is exactly why they exist: see [Manual order cancellation](domain-invariants.md#manual-order-cancellation--the-third-state-based-refusal-and-the-first-ability-requiring-two-permissions) below for the full mechanism and why this is a deliberate reading of "a UI hint, not a control" rather than a design flaw. `viewAny`/`create`/`update`/`delete`/`transitionStatus` are untouched by this story.

**`create` self-authorizes through `App\Actions\Auth\LogRefusedPrivilegedAttempt`, never a bare `Gate::authorize()`** — `CreateOrder::__invoke()`'s own first statement, `targetType: 'order'` passed explicitly since `resolveTarget()` auto-resolves only `User`/`Role` instances or classes, and no `targetId` (a class-level check, no row exists yet). Pinned by `tests/Feature/Orders/RefusalLoggingTest.php`, matching the shape [`ShippingZonePolicy`](policies-shipping-payment.md#shippingzonepolicy--the-eighth-policy-and-the-one-d-9-uses-to-reconcile-the-policy-vs-permission-check-divergence-with-0035)'s own create-time refusal-logging test already establishes for an identical class-level target.

**D-13 is a Phase 2 reversal, not an original decision, and it is worth reading as a caution about citing precedent from memory.** The story's own task file originally argued for **no** `OrderPolicy` at all, on the reasoning that "this story's only write is a creation, and 'may this actor create an order' reduces to `orders.create` with zero row-level nuance — a policy would be one method returning `$user->can()`", citing [`CustomerPolicy`](#customerpolicy--the-eleventh-policy-and-the-first-a-passive-record-with-no-privilege-tier-of-its-own)'s own **D-12** as the precedent for skipping the class. That citation was backwards: story 0041's D-12 is the record of `CustomerPolicy` being **created**, not skipped, for the reason quoted there — "a no-policy domain entity is not a pattern this repo has." `ShippingRatePolicy` is what actually settled the question, being the identical structural shape (backend-only, no route or component, action-as-only-enforcement-point) and having shipped four abilities from day one anyway. This is the **third** time on this page a "no policy needed, it's just `$user->can()`" argument has been proposed and reversed by review rather than avoided at Phase 1 — [`ProductAttributeTypePolicy`](policies-products.md#productattributetypepolicy--the-seventh-policy-and-the-first-whose-no-policy-recommendation-was-reversed-at-phase-2) (story 0028) and `CustomerPolicy` itself (story 0041, D-12) are the other two — worth naming because the pattern keeps recurring despite two prior corrections already being on record.

`VIEW_PERMISSION`/`CREATE_PERMISSION`/`EDIT_PERMISSION`/`DELETE_PERMISSION` are `public const` on the class, per [naming.md](../../conventions/naming/routes-and-permissions.md#permission-names)'s convention — the **eleventh** follower of it (`UserPolicy` remains the sole outlier among twelve policies).

**Story 0051 does *not* add a sixth ability here, despite 0045's own D-13 naming refunds as one of the row-state rules that would grow `OrderPolicy`.** `App\Actions\Orders\RecordRefund` gates on a **bare** `Gate::authorize('orders.refund')` permission string instead — DR-2 in the story's own task file separates two questions D-13's forward note had conflated: *may this actor record refunds at all* (a flat capability, zero row-level nuance, refused with a 403) is genuinely a policy-shaped question, but *may this order be refunded right now* (its `payment_status` must be `Paid`/`PartiallyRefunded`) is not about the actor at all — **no** actor, Super Admin included, may refund an already-fully-refunded order, and expressing that as a policy method would render it a 403 that `Gate::before`'s bypass makes inert for the one actor most likely to try it (see [A rule that must bind a Super Admin actor cannot go through `Gate`](administrator-tier.md#a-rule-that-must-bind-a-super-admin-actor-cannot-go-through-gate) below). The state refusal is a `ValidationException`, raised inside the action itself, never a `Gate` check. This **narrows** 0045's D-13 rather than closing it: 0048's/0049's/0050's row-state rules may still warrant growing this policy, and whichever lands first should re-evaluate.
