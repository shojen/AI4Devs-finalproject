# Authorization — Domain invariants vs authorization rules

> Part of [Authorization](../authorization.md). **Read this part when:** you must decide whether a rule is an authorization rule or a domain invariant (direct `throw`, state-based refusals). The other parts are listed in the [hub](../authorization.md#table-of-contents).

## A domain invariant is not an authorization rule, and does not live here

Task 0017 added a kind of guard this page had not carried before, and the boundary is worth stating once so a later story files its own rule in the right place. **The Sales Region catalog must hold exactly one default entry, and that entry must be active.** Two of the screen's refusals enforce it — promoting an inactive entry, and disabling the current default without naming an active replacement.

Read the two categories side by side:

| | An authorization rule | A domain invariant |
| --- | --- | --- |
| Question | *May **this actor** do this?* | *Would the **data** still be valid?* |
| Answer for a Super Admin | yes, via [the bypass](super-admin.md#the-super-admin-bypass) | **the same as for anyone else** — the catalog does not care who asked |
| Where it lives | a policy, a `can:` gate, or a direct throw in an action | inside the action's own transaction, under the row lock |
| Refusal shape | `AuthorizationException` → 403 | `ValidationException` → the form's error bag |

The consequences that follow are the reason this is not filed as "just another guard":

- **It cannot be a policy method or any `Gate`-mediated check.** `Gate::before` grants the Super Admin before a policy runs, and a Super Admin is exactly as capable of leaving the catalog with zero defaults as anyone else. This is the same reasoning as [a rule that must bind a Super Admin actor cannot go through `Gate`](administrator-tier.md#a-rule-that-must-bind-a-super-admin-actor-cannot-go-through-gate), reached from a different direction — there the rule was about privilege, here it is about data — and the two arrive at the same shape: a direct throw inside the action.
- **It runs strictly *after* authorization, never instead of it.** The actions authorize `update` first, outside the transaction, so a caller who may not touch the row is refused before any invariant is even evaluated — and a permission refusal is never disguised as a validation message. Same ordering rule as [step-up](step-up-and-refusal-logging.md#ordering-the-permission-refusal-always-wins).
- **Its subject must be re-read under lock**, which an authorization check's subject does not have to be: a permission is a property of the actor, while an invariant is a property of rows that another transaction can move underneath you. That is the whole content of [security/model-instance-trust.md](../../security/model-instance-trust.md), and it is why both invariant-enforcing actions re-fetch every row they touch in one ordered `lockForUpdate()` query inside their own `DB::transaction(..., attempts: 3)`.
- **It is still logged like a refusal.** Both throws call `LogRefusedPrivilegedAttempt::log()` on the line above, with the snake_case reasons `default_must_be_active` / `default_deactivation_requires_replacement` (and, in the same shape, `category_in_use` / `category_still_in_use` for the product and blog category delete blocks) — so "show me every refused attempt" catches an invariant refusal too, without the log implying an authorization decision was made. See [Recording a refusal](step-up-and-refusal-logging.md#recording-a-refusal--what-every-gate-owes-the-audit-trail).

The mechanics — the exploit paths, the lock ordering, the two re-audit rounds — belong to [security/model-instance-trust.md](../../security/model-instance-trust.md) and are pointed at rather than duplicated here.

### Order editability — the second state-based refusal, and the shape three more stories copy

`App\Actions\Orders\{AddOrderItem,RemoveOrderItem,UpdateOrderItemQuantity}` (story 0048) are this pattern's second real instance, after the Sales Regions default-catalog invariant above — and the first written explicitly *as* a reusable shape for a whole epic rather than arrived at independently. Read the two side by side: the Sales Regions guard asks "would the catalog still be valid" about a self-referencing row; this one asks "is this order still open to editing" about `orders.status`. Same category of question — about the **data**, not the actor — so the table above governs it without modification.

[`App\Exceptions\OrderNotEditableException`](../../../app/Exceptions/OrderNotEditableException.php) — a **direct `throw`**, never a `Gate` ability and never an `App\Policies\OrderPolicy` method — fires when `$order->status` is `Shipped` or `Delivered` (`App\Enums\OrderStatus`), rendering **409 Conflict** with a constant, never-interpolated message. Two rules generalise past this one story:

- **The permission check runs strictly before the state guard, never the reverse.** All three actions call `Gate::authorize('update', $order)` (via `LogRefusedPrivilegedAttempt::authorize()`, against `OrderPolicy::update()`, which gates on `orders.edit` alone) as their first statement, and only then run the hard-block guard. An actor lacking `orders.edit` who targets a `Shipped` order receives the `AuthorizationException`, never the 409 — inverting it would let the 409 disclose the order's existence and shipped/delivered state to somebody with no permission to read either, the identical [step-up ordering rule](step-up-and-refusal-logging.md#ordering-the-permission-refusal-always-wins) restated a third time on this page.
- **It must bind a Super Admin, so it cannot be a `Gate` check** — the same reasoning as [A rule that must bind a Super Admin actor cannot go through `Gate`](administrator-tier.md#a-rule-that-must-bind-a-super-admin-actor-cannot-go-through-gate) and [security/authorization-patterns.md](../../security/authorization-patterns/ability-coverage-and-guards.md#a-rule-that-must-bind-a-super-admin-actor-must-be-a-direct-throw-not-a-gate-check), arriving from the domain-invariant direction rather than the privilege direction: `Gate::before` grants a Super Admin before `OrderPolicy::update()` ever runs, so a `Gate`-mediated block would be inert against exactly the actor a hard block with "no confirmation path around it" (PRD §3.2) exists to bind. Pinned by a dedicated test asserting a Super Admin is refused identically to an ordinary `orders.edit` holder.

**This story's own Phase 4 security audit (finding F-4) hardened the guard beyond what the Sales Regions instance shows above, and the addition generalises too.** The state check runs **twice**: once against the caller-supplied `$order` (a plain `refresh()`, unlocked, so a stale instance is refused fast, before any transaction opens), and a **second time** inside the `DB::transaction()`, against the same row re-fetched under `lockForUpdate()` — closing the window between the first check and the write where a concurrent status transition (0049) could otherwise slip an edit through. Sales Regions' own invariant already re-reads its subject under lock inside its transaction; Orders' version is the first to show *both* halves — an unlocked fast-fail check outside the transaction, and a locked re-verification inside it — as one deliberate pair rather than the lock alone.

Three more Orders stories add another instance of this exact shape rather than reinventing it: **0050** (manual cancellation, blocked in three states) and **0051**/**0052** (a refund refused outside `Paid`/`PartiallyRefunded`). Each should be a direct throw, 409, checked after `Gate::authorize()` and re-checked under lock — copy this story's `assertEditable()` method (duplicated identically across all three actions rather than extracted, per the task file's own D-5 — extract a shared guard only once a fourth call site appears), not the Sales Regions one, since Orders' locked-re-check is the shape both audits eventually converge on.

> **Story 0055 is that fourth reader, and it extracted the predicate, not the guard.** The `Shipped`/`Delivered` status set now lives once in `App\Models\Order::isLineItemEditable()`; the three `assertEditable()` bodies still each log the refusal and throw (triplicated, deliberately), and the order-detail screen's edit controls read the same predicate. `Order::isRefundable()` does the same for `RecordRefund`'s payment-state guard. Both are non-throwing and say nothing about the actor. `isLineItemEditable()` is true on a `Cancelled` order — it reproduces the shipped guard, and the PRD blocks only `Shipped`/`Delivered` — recorded as an open product question, not a bug.

> **Narrowed 2026-09-17 (story 0050) — the "re-checked under lock" half of this prediction does not hold for manual cancellation, and this is a deliberate divergence rather than a gap.** `App\Actions\Orders\RecordRefund` (0051) does open a `DB::transaction()` and re-read its rows under `lockForUpdate()`, matching the prediction exactly — but `App\Actions\Orders\CancelOrder` (0050) does not: it is a single-row, single-column write with no second statement and no multi-step computation for a lock to protect, the same "nothing to wrap" reasoning `TransitionOrderStatus` (0049) already used for its own unlocked write. What *does* carry over unchanged is the direct-throw/409 shape and the permission-before-state ordering — see [Manual order cancellation](#manual-order-cancellation--the-third-state-based-refusal-and-the-first-ability-requiring-two-permissions) below for the guard itself and the two-permission/policy-hint nuance this story adds on top of the shape predicted here.

### Order status regression confirmation — the app's second "are you sure" mechanism, and why it is not step-up

`App\Actions\Orders\TransitionOrderStatus` (story 0049) moves an order along PRD §3.2's linear ladder (`Pending → Processing → Shipped → Delivered`), applying a forward move immediately and refusing a **backward** one unless the caller passes `confirmed: true`. That refusal — [`App\Exceptions\OrderStatusRegressionRequiresConfirmationException`](../../../app/Exceptions/OrderStatusRegressionRequiresConfirmationException.php), rendering **409 Conflict** — is neither an authorization rule nor the domain-invariant shape [above](#a-domain-invariant-is-not-an-authorization-rule-and-does-not-live-here): it is this app's **second** "are you sure" mechanism, and its first that has nothing to do with identity. A reader who only knows [step-up authentication](../../security/step-up-authentication.md) (task 0015a) will reach for its vocabulary — a fresh password, a 423 — by reflex; neither applies here, and the distinction is worth stating flatly rather than left to be rediscovered per-story:

| | Step-up (task 0015a) | Order status regression confirmation (story 0049) |
| --- | --- | --- |
| Question asked | *Is the person at the keyboard still the account holder?* | *Did you mean to move this order backward?* |
| Satisfied by | Re-entering a password on Fortify's `password.confirm` screen | Passing `confirmed: true` on the same call |
| Expires | Yes — `config('auth.password_timeout')` | No — it is per-call, and carries nothing forward |
| Refusal status | **423 Locked** (`App\Exceptions\PasswordConfirmationRequiredException`) | **409 Conflict** (`OrderStatusRegressionRequiresConfirmationException`) |
| Who it binds | The session | The single request |
| Re-authenticates? | Yes | No — `EnsureRecentPasswordConfirmation` is never called, no password is re-requested |

Two things carry over from step-up deliberately, and one does not:

- **The 409 is a UI *intent* signal, not a credential check** — the actor is already authenticated, authorized (`OrderPolicy::transitionStatus()` runs first — see the ability table above, and [ordering: the permission refusal always wins](step-up-and-refusal-logging.md#ordering-the-permission-refusal-always-wins)) and recent; the request is simply in conflict with the order's current state until the caller says they meant it. This is the same reasoning [Order editability](#order-editability--the-second-state-based-refusal-and-the-shape-three-more-stories-copy) above uses for its own 409, arriving at an identical status for an unrelated refusal — see [`app/Exceptions/RoleInUseException.php`](../../../app/Exceptions/RoleInUseException.php), whose shape both `OrderNotEditableException` and this exception copy verbatim.
- **The throwing guard is a wrapper around a non-throwing predicate**, the exact shape [step-up's own predicate/wrapper split](../../security/step-up-authentication.md#one-predicate-two-shapes--the-ui-hint-must-call-the-guard-not-copy-it) already establishes for `EnsureRecentPasswordConfirmation::isRecentlyConfirmed()`. `TransitionOrderStatus`'s guard is a direct wrapper around `OrderStatus::isBackwardFrom()` (non-throwing), so the UI hint (story 0055's "this will move the order backward" confirmation, `Show::requestStatusChange()`) asks the identical method the throw is built on and cannot drift from the rule that refuses.
- **What does *not* carry over: no re-authentication, no expiry, no session binding.** `$confirmed` is a plain action parameter (`bool $confirmed = false` on `TransitionOrderStatus::__invoke()`), satisfied per-call and remembered nowhere — there is no equivalent of `auth.password_timeout` here, and a caller who confirms once must confirm again on the next backward request. See the task file's own **D-2** for the full reasoning this table condenses.

`OrderStatus::rank()`/`isBackwardFrom()` (also story 0049) are the enum-side half of this mechanism: `rank()` covers only the four linear statuses (`Pending`=0 … `Delivered`=3) and has **no `Cancelled` arm**, so calling it on `Cancelled` raises `\UnhandledMatchError` rather than inventing a position — `TransitionOrderStatus` refuses any transition touching `Cancelled`, in either direction, with **no confirmation path at all**, strictly *before* either method is ever reached (D-3/D-6). That refusal is a third, distinct kind again — a `ValidationException` on `status` resolving `orders.transitions.cancellation_unsupported`, not this section's 409 and not the domain-invariant shape above — because it is not "in conflict pending confirmation", it is outright out of this story's scope (story 0050 owns cancellation). A transition to the status the order already holds is a fourth: `ValidationException` on `status` resolving `orders.transitions.same_status`, and `$confirmed` is not consulted (D-4).

### Manual order cancellation — the third state-based refusal, and the first ability requiring two permissions

`App\Actions\Orders\CancelOrder` (story 0050) is [Order editability](#order-editability--the-second-state-based-refusal-and-the-shape-three-more-stories-copy)'s third instance, per that section's own forward note — cancellation is permitted only while `status` is `Pending`/`Processing` **and** `payment_status` is not `PartiallyRefunded`, blocked with **no confirmation path** in `Shipped`, `Delivered`, or `PartiallyRefunded`. [`App\Exceptions\OrderCancellationBlockedException`](../../../app/Exceptions/OrderCancellationBlockedException.php) renders **409 Conflict**, following `OrderNotEditableException`'s shape exactly — a constant, never-interpolated message, never a 403 or a 422.

**What makes this instance genuinely different from its two predecessors, rather than a fourth copy of the same shape: the state clause lives in *both* the policy and the action, on purpose, and the two layers bind different actors.**

| | `update()` (story 0048) / `transitionStatus()` (0049) | `cancel()` (story 0050) |
| --- | --- | --- |
| State clause lives in | The **action** only (`assertEditable()` / the Cancelled/same-status checks) — never the policy | **Both** `OrderPolicy::cancel()` (`$order->isManuallyCancellable()`) **and** `App\Models\Order::isManuallyCancellable()`'s caller, `CancelOrder` itself |
| Why the policy stays state-free (the other two) / gains state (this one) | A `Gate`-mediated state rule is inert for a Super Admin (`Gate::before`), so it must live outside `Gate` entirely | The state clause is *also* meant to answer story 0055's `Gate::allows('cancel', $order)` UI hint (`Show::canCancel`) correctly, without re-deriving the rule a second time |
| Consequence for an ORDINARY, fully-permitted actor | Reaches the action's own state check either way — permission and state are two independent gates | Refused by `Gate::authorize('cancel', $order)` itself (`AuthorizationException`) the moment the order is in a guarded state — `CancelOrder`'s own already-cancelled/blocked-state checks are **unreachable** for this actor |
| Consequence for a Super Admin | Bypasses the permission gate (`Gate::before`); the action's own state check still binds | Bypasses `cancel()` entirely, state clause included (`Gate::before` never calls the policy) — `CancelOrder`'s own checks are the **only** thing that binds them |

The load-bearing property is unchanged from `update()`/`transitionStatus()`'s own rule — **a check that must bind a Super Admin actor cannot be `Gate`-mediated** (see [A rule that must bind a Super Admin actor cannot go through `Gate`](administrator-tier.md#a-rule-that-must-bind-a-super-admin-actor-cannot-go-through-gate)) — `cancel()`'s policy-level state clause is understood as a **UI hint**, never the control, precisely because it is inert for the one actor most likely to need binding. What is new here is that the hint is *also* wired into the enforcement path for every other actor, as an accepted side effect rather than a second, independent design: an ordinary actor's blocked-state attempt surfaces as a 403 (`AuthorizationException`) rather than the 409 `OrderCancellationBlockedException` a Super Admin would receive for the identical attempt — both are refusals, both leave the order unchanged, and the PRD's "no confirmation path around it" requirement holds either way, but the exact status code an ordinary actor sees differs from a Super Admin's. `OrderCancellationBlockedException`'s own 409 render is still directly unit-tested (independent of any actor), and a Super Admin's path through `CancelOrder` is what exercises it end to end.

**The two-permission requirement** (`orders.edit` **and** `orders.refund`, via `OrderPolicy::ORDER_REFUND_PERMISSION`) is a human product decision (D-6 in the story's own task file), not a technical one: cancelling an order is administratively paired with a refund in practice, so an actor trusted to cancel must also be trusted to handle the refund conversation that usually follows. It is an **intersection**, not either permission substituting for the other — holding `orders.refund` alone, or `orders.edit` alone, is refused identically to holding neither. `App\Actions\Orders\RecordRefund` (story 0051) seeds and consumes `orders.refund` as a bare literal (its own DR-2); `cancel()` is the first class to **decide** with it, which is why its single-name constant lands on `OrderPolicy` rather than `RecordRefund`, per [naming.md](../../conventions/naming/routes-and-permissions.md#permission-names)'s "name a permission once on the class that owns the rule".

**`App\Models\Order::isManuallyCancellable()`** is the one non-throwing predicate both the policy's hint and the action's guard wrap — never a second, independently-written comparison. It reads `status` **and** `payment_status`, unlike `OrderNotEditableException`'s guard (`status` only): the cross-dimension case (`PartiallyRefunded` blocking cancellation even from `Pending`/`Processing`) is this story's own highest-risk test, named explicitly because a guard copy-adapted from `TransitionOrderStatus` would pass every other test in the suite and silently miss it. `App\Enums\OrderStatus::rank()`/`isBackwardFrom()` are untouched — `CancelOrder` is an independent action, not a call into or out of `TransitionOrderStatus` (0049's `rank()` still has no `Cancelled` arm and still throws `\UnhandledMatchError` on one).

Cancelling an order already in `Cancelled` is a **fourth** distinct refusal shape on this page — a `ValidationException` on `status`, following `TransitionOrderStatus`'s own same-status precedent (D-4 there, D-3 here) rather than a silent no-op — and it runs *above* the blocked-state check inside `CancelOrder`, so an already-cancelled order (not in `{Pending, Processing}`) is refused for the right reason rather than falling into the blocked branch by coincidence.

### The order detail screen — the first three-ability screen

[`App\Livewire\Orders\Show`](../../../app/Livewire/Orders/Show.php) (story 0055, route `orders.show`) is the first screen in this app governed by **three abilities of which only one gates the route**. `can:orders.view` (route + `mount()`) grants the page; `orders.edit` governs line items and status; `orders.edit` **and** `orders.refund` govern cancellation (`OrderPolicy::cancel()`, [above](#manual-order-cancellation--the-third-state-based-refusal-and-the-first-ability-requiring-two-permissions)); `orders.refund` alone governs refunds. Each mutating **and** each disclosing method (both dialog openers included) authorizes as its own first statement, and the actions behind them authorize again. The per-control map is in [api/orders.md](../../api/orders.md#ordersshow--the-twelfth-permission-gated-route-and-the-first-screen-governed-by-three-abilities).

This is the `Gate::allows()`-is-a-UI-hint section's ([above](grant-meta-rules-and-ui-hints.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer)) first screen with a **state** dimension as well as a permission one, and it renders the two differently on purpose:

| Dimension | Refused by | Rendered as |
| --- | --- | --- |
| Permission (`orders.edit`, `orders.refund`) | the ability | a **disabled** control with a tooltip, hook present on both branches |
| Row state, line items / status / cancel (`isLineItemEditable()`, `isManuallyCancellable()`, a cancelled order) | a domain predicate, never a 403 | a **disabled** control; the action's 409 is rendered inline if a stale page still submits it |
| Row state, refund (`isRefundable()`) | PRD §3.2: "the refund action does not render" | **absent from the DOM**; the permission dimension of the same control stays disabled |

The reusable half a later epic inherits: **a state-based refusal renders as a disabled control (or, where the PRD says so, as DOM absence), never as a 403 the actor has to trigger to discover**, and the hint reads the guard's own non-throwing predicate rather than a status set written a second time. Absence is a presentation choice layered on top of `RecordRefund`'s own refusal, never a substitute for it.

> **Accepted, documented drift.** A Super Admin sees Cancel **enabled** on a `Shipped` order: `Gate::before` skips `OrderPolicy::cancel()`, state clause included, so the hint is inert for exactly the actor a direct throw exists to bind. The click reaches `CancelOrder`, which throws `OrderCancellationBlockedException` (409); `Show::cancelOrder()` catches it and renders the message inline instead of a 500. Pinned by a test named as documented drift.

`#[Locked]` `orderId`, `pendingStatus` and `pendingFromStatus` keep a client from re-pointing the component or forging a backward-confirmation target. The step-up mechanism is not used here; the backward-transition and cancel dialogs are the "are you sure" mechanism described [above](#order-status-regression-confirmation--the-apps-second-are-you-sure-mechanism-and-why-it-is-not-step-up), rendered by the shared [`<x-confirm-dialog>`](../../api/orders.md#shared-pieces-this-story-introduced).

### A system-triggered write may be ungated — `AutoCancelFullyRefundedOrder`, and the three conditions that make it safe

`App\Actions\Orders\AutoCancelFullyRefundedOrder` (story 0052) cancels an order whose every line item is fully refunded, and it contains **no `Gate::authorize()`, no `Auth::user()` read and no policy call** — a documented exception to "an authorization rule belongs to the action", not an omission. It is reached only through `RecordRefund` → `OrderFullyRefunded` (dispatched after the refund transaction commits) → `CancelFullyRefundedOrder` (synchronous listener). Three conditions make the exemption safe, and all three must hold for any future system-triggered write that copies this shape:

- **It reads no actor.** The trigger is a state transition, not a person.
- **Its only reachable entry point is gated.** `RecordRefund` authorizes `orders.refund` as its first statement. A later story adding a second caller inherits the obligation to gate that caller.
- **The exemption is written in the class's own docblock**, so "exempt" is distinguishable from "forgotten".

It also bypasses both `CancelOrder` (which blocks `Shipped`/`Delivered`/`PartiallyRefunded`, exactly the states the PRD says auto-cancel must handle) and `TransitionOrderStatus`, writing `status` via `forceFill()`. A `$systemTriggered` flag on `CancelOrder` was rejected: a boolean that switches a guard off is a one-argument bypass of the rule the guard exists to enforce. The manual guard is unchanged and pinned by a regression test.
