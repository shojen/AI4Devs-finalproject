# Migration Conventions — Delete behaviour and vendored migrations

> Part of [Migration Conventions](../migrations.md). **Read this part when:** you choose cascade/restrict/null for an FK, or touch a package-vendored or published-stub migration. The other parts are listed in the [hub](../migrations.md#table-of-contents).

## The three-way delete-behaviour rule: cascade, restrict, or null

Every FK's `->cascadeOnDelete()` / `->restrictOnDelete()` / `->nullOnDelete()` choice on this page so far has been argued individually, at the table where it appears. Story 0045's two migrations ([`create_orders_table`](../../../database/migrations/2026_09_11_162629_create_orders_table.php), [`create_order_items_table`](../../../database/migrations/2026_09_11_162630_create_order_items_table.php)) are the first pair in this codebase to exercise all three behaviours **at once**, on six FK columns across two tables — which is what finally makes the underlying rule statable in one place rather than left for a reader to infer by comparing three separate tables. This is not a "first" of any individual behaviour — every one of the three already has an earlier, standing example, named below — only the first place all three are visible together.

**Cascade — when the child has no independent meaning without its parent.** `order_items.order_id` is `cascadeOnDelete()` (**D-11**), the only cascade in either migration, for the identical reason [`create_passkeys_table`](basics-and-alterations.md#structure)'s `passkeys.user_id` already cascades: a line item recorded against no order is not a smaller version of a line item, it is nothing at all. Note this cascade is close to unreachable in practice today — orders are never hard-deleted this phase, `Cancelled` is a `status` value, not a delete — so it is insurance against a future hard-delete path rather than a live behaviour.

**Restrict — when the child is a peer whose own data would be destroyed by following the parent down.** `orders.customer_id`, `.payment_method_id`, `.sales_region_id` and `.shipping_rate_id` are all `restrictOnDelete()`, the same reasoning [`sales_regions.parent_id`](uuid-primary-keys.md#uuid-primary-keys) already establishes: an order is not part of a customer, a payment method, a sales region or a shipping rate — it merely references one, and destroying any of those four rows must never silently take a historical order down with it (or, for `customer_id` specifically, silently orphan it — see [schema-other.md](../schema-other/customers.md#customers)'s own "orders are never orphaned" note, and story 0042's soft-delete-on-`Customer` decision that exists partly to make this restriction livable in practice).

**Null — when a snapshot preserves the row's meaning without the reference.** `order_items.product_id` and `.product_variant_id` are `nullOnDelete()` (**D-2**), matching [`media.uploaded_by`](../schema-products/sales-regions-and-media.md#uploaded_by-and-the-soft-delete-interaction--read-this-before-fixing-the-fk)'s standing example. This one is **safe only because a snapshot already exists**: `product_name`, `product_sku` and `unit_price` are copied onto the line item at creation (see [schema-orders.md](../schema-orders/snapshots-totals-and-rules.md#the-price-snapshot--read-from-the-variant-never-the-parent-when-one-is-named)) and survive the null, so a line item whose catalog row was later deleted remains fully legible as history with a dangling reference — never a blank row. `nullOnDelete()` without that snapshot would be the wrong choice: an administrator retiring a discontinued product must never be blocked by history they cannot act on, but the history must still say what was actually ordered.

Verified against a live, migrated instance rather than read off either migration file: `php artisan db:table orders` reports `orders_customer_id_foreign`, `orders_payment_method_id_foreign`, `orders_sales_region_id_foreign` and `orders_shipping_rate_id_foreign` all as `no action / restrict`; `php artisan db:table order_items` reports `order_items_order_id_foreign` as `no action / cascade` and both `order_items_product_id_foreign` / `order_items_product_variant_id_foreign` as `no action / set null` — exactly the three-way split above, and no hand-written `$table->index()` on any of the six columns ([An FK column does not also get an explicit index here](uuid-primary-keys.md#an-fk-column-does-not-also-get-an-explicit-index-here)).

**The rule, stated once for reuse:** cascade when the child is a *part of* its parent; restrict when the child is a *peer* whose own data the delete would destroy or orphan; null when a *snapshot* already makes the reference optional to the row's own meaning. A new FK on a domain table should be assignable to one of these three by asking which of the three sentences describes the relationship — not by pattern-matching the nearest existing table.

## Package-vendored migrations

`database/migrations/2026_07_12_181045_create_permission_tables.php` is `spatie/laravel-permission`'s stub, published as-is. It reads its shape entirely from `config('permission.*')` rather than hardcoding table/column names — do not hand-edit table/column names inside this file; change `config/permission.php` instead and regenerate. It also guards against missing config with `throw_if(...)`:

```php
// database/migrations/2026_07_12_181045_create_permission_tables.php
throw_if(empty($tableNames), 'Error: config/permission.php not loaded. Run [php artisan config:clear] and try again.');
```

When vendoring a package migration like this, keep that defensive `throw_if` pattern — it turns a silent misconfiguration into an immediate, actionable migration failure.

### A published stub is not the same thing as a package-vendored migration

`database/migrations/2026_09_10_205634_create_notifications_table.php` (story 0043) is the opposite case from `create_permission_tables.php` above, and the distinction is worth stating explicitly because the two are easy to conflate — both arrive via an Artisan command rather than being hand-typed from scratch. `php artisan notifications:table` **publishes** Laravel's own notifications-table stub into `database/migrations/`; from that moment it is ordinary repository source, not a file this project reads config to regenerate. Its default body reads no config at all — it hardcodes `$table->morphs('notifiable')`, full stop — so there is nothing to "vendor" and no `config/` key to change instead of editing it.

That is exactly why it had to be **edited**, not left as published: `morphs('notifiable')` emits an `UNSIGNED BIGINT notifiable_id`, and `users.id` is a `CHAR(36)` UUID ([schema.md](../schema-users-auth.md#users)) — the stock column can never hold a real recipient. The fix is `$table->uuidMorphs('notifiable')` instead, one line, decided once at publish time with no ongoing config dependency the way `create_permission_tables.php` has. Treating a published stub as hands-off **is** the mistake this page's `create_permission_tables.php` guidance exists to prevent for a *different* file — applying that same hands-off instinct here would have shipped the broken `morphs()` column. The test: does the file read its shape from `config()` at migration time? `create_permission_tables.php` does; a published `notifications:table` stub does not — so the first is package-vendored and must not be hand-edited, and the second is app-owned and must be reviewed like any other migration in this repo. See [schema.md](../schema-other/notifications.md#notifications) for the shipped column list.
