# Database Schema — Orders — orders

> Part of [Database Schema — Orders](../schema-orders.md). **Read this part when:** the task touches the `orders` table: status columns, totals, tax snapshot, address snapshot columns, flags. The other parts are listed in the [hub](../schema-orders.md#table-of-contents).

### `orders`

Source: `database/migrations/2026_09_11_162629_create_orders_table.php` (story 0045) — a greenfield UUID `create_*` migration following [`create_sales_regions_table`](../migrations/uuid-primary-keys.md#uuid-primary-keys)'s established pattern: `uuid('id')->primary()`, every string column length-capped, every money-like column `decimal`, and no hand-written index on any column `constrained()` already indexes.

Model: [`App\Models\Order`](../../../app/Models/Order.php). Columns in real physical order (verified with `php artisan db:table orders` against a live, migrated instance):

| Column | Type | Notes |

| `id` | uuid (v7) PK | `CHAR(36)`; generated by `HasUuids`. | `refunded_amount` | `DECIMAL(10,2)`, default `0.00` | story 0051 — the running total `App\Actions\Orders\RecordRefund` keeps consistent with the SUM of this order's `refunds` rows' `amount`; a **merchandise-only** total (`quantity × unit_price`), excluding tax and shipping, which are both `0.00` on every order today (R-2) — see [`refunds`](items-and-refunds.md#refunds) below. All twelve address columns mirror [`customers`](../schema-other/customers.md#customers) column-for-column in both name and length — deliberately, since they exist to hold an exact copy of a `Customer` row's own address at the moment an order is created.

**No `deleted_at`.** Orders are never deleted this phase; `Cancelled` is a `status` value PRD §3.2 defines, not a soft delete.

**`#[Fillable]`** lists the operator-supplied inputs a new order genuinely needs (`customer_id`, `payment_method_id`) plus the twelve address columns — the address columns are fillable because they are a frozen *copy* written at creation time, not a derived/computed value, and a legitimate future caller (an order-address edit screen) could reasonably need to write them directly. Every other column — `order_number`, `status`, `payment_status`, `subtotal`, `tax_amount`, `shipping_amount`, `total`, `tax_rate`, `flagged_for_review`, `sales_region_id`, `shipping_rate_id` — is **deliberately omitted** and written only via `forceFill()`/`forceCreate()` from [`App\Actions\Orders\CreateOrder`](../../../app/Actions/Orders/CreateOrder.php): each is either derived arithmetic, a status a later story owns, or a tax input, and none may ever arrive from a form. Pinned by a test that fails if the omission is undone — the same "omission is this codebase's mass-assignment guard" convention [conventions/base-standards.md](../../conventions/base-standards/stack-and-model-conventions.md#model-conventions) documents.

#### Indexes — exactly the FK-created ones, plus one

`php artisan db:table orders` reports exactly six indexes: `primary` on `id`, `orders_order_number_unique`, and four FK-created indexes (`orders_customer_id_foreign`, `orders_payment_method_id_foreign`, `orders_sales_region_id_foreign`, `orders_shipping_rate_id_foreign`) — verified against a live, migrated instance, not read off the migration. No hand-written `$table->index()` anywhere ([migrations.md](../migrations/uuid-primary-keys.md#an-fk-column-does-not-also-get-an-explicit-index-here)); `order_number`'s UNIQUE index is the only non-FK index on the table.
