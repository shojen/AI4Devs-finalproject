# Database Schema — Internationalization

Part of [Database Schema](schema.md) — see [schema.md](schema.md#er-diagram) for the full ER diagram and [schema.md#notes](schema.md#notes) for the UUID/ADR-0001 status notes. This file covers PRD Epic 5's two backend-only tables (story 0068): `store_languages` (the admin-managed content-authoring language catalog) and `locale_settings` (the app's single default-dashboard/notification-language settings row). Both are standalone — no FK in, no FK out, no relationship line in the ER diagram — and neither is the per-user `users.ui_locale` (story 0066): [PRD assumption 14](../PRD/sections/foundations.md#assumptions--confirmed-decisions) defines these as **two independent i18n layers**, and this story deliberately touches both plus a third, unrelated thing (`App\Enums\UiLocale`) without merging any of the three. See the story's own task file for the full three-way comparison table.

### `store_languages`

Source: `database/migrations/2026_09_27_122924_create_store_languages_table.php` — the admin-managed set of languages the store's **content** is authored in ([PRD Epic 5, Layer 2](../PRD/sections/epic-5-internationalization.md#epic-5--internationalization)). The store default may be a language the dashboard does not even offer (French, Japanese, …) — that is correct and intended, and is what distinguishes this table from `locale_settings` below.

Model: [`App\Models\StoreLanguage`](../../app/Models/StoreLanguage.php). Columns in real physical order:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid (v7) PK | `CHAR(36)`; generated by `HasUuids`. A plain greenfield UUID table under [ADR 0001 Amendment 1](../decisions/0001-uuid-primary-keys.md#amendment-1-2026-08-27--the-scope-is-the-policy-not-the-list-of-seven)'s general policy — nothing for the ADR to add, the same bucket `sales_regions`/`media`/`payment_methods` sit in |
| `code` | `VARCHAR(10)`, **unique** | ISO 639-1 alpha-2, lowercase (`es`, `fr`) — normalised with `Str::lower()` before every write, since `'fr'`/`'FR'` collide at the table's `utf8mb4_unicode_ci` unique index but not under PHP `===`. `VARCHAR(10)` rather than `2` deliberately keeps headroom for a possible future regional-variant fixture (`pt-BR`) with no migration needed to use it |
| `name` | `VARCHAR(100)` | the bundled fixture's endonym (`Español`, `Français`) — never caller-supplied. `App\Models\StoreLanguage` declares `#[Fillable([])]`: with a picker over a closed list there is no independent "what should this be called" input for a form to supply at all, so a plain `create()`/`fill()` would silently write nothing and every write goes through `forceFill()`/`forceCreate()` |
| `is_default` | boolean, default `false` | exactly one row carries it; enforced in the actions under a row lock, **not** by a database constraint — the identical `sales_regions.is_default` shape and for the identical reason (MySQL 8.4 has no partial index; a `STORED`-column + `UNIQUE` workaround would force a strict clear-then-set ordering) |
| `is_active` | boolean, default `true` | the catalog's soft state. **Diverges from `sales_regions.is_active`'s `false` default deliberately**: that table's seeder inserts ~248 rows that should *not* start live, while every row here is inserted one at a time — either the Spanish bootstrap or an administrator who just picked it — and every one of those wants to be usable immediately |
| `timestamps` | | |

**"Remove" means `is_active = false`, never a delete of any kind — no `SoftDeletes` either.** The same `is_active`-is-the-soft-state shape [`sales_regions`](schema-products/sales-regions-and-media.md#sales_regions) already establishes, chosen so a later story's translation rows keyed to a removed language are never silently destroyed by a cascade nor block removal forever via `restrictOnDelete()`. Two consequences: re-adding a previously-removed code **reactivates the existing row** (`AddStoreLanguage` is a find-or-create, matched byte-exact on `code` in any state, never a plain insert) rather than creating a duplicate, and no story downstream ever depends on an `onDelete` clause firing against this table.

**At least one active language must always exist — an invariant `sales_regions` never needed**, because that catalog seeds ~254 rows while this one seeds exactly one. Enforced as a domain invariant inside `RemoveStoreLanguage`'s row lock (a `ValidationException`, never a 403), and it binds a Super Admin identically — the catalog does not care who asked. See [architecture/authorization/domain-invariants.md](../architecture/authorization/domain-invariants.md#a-domain-invariant-is-not-an-authorization-rule-and-does-not-live-here).

**Indexes — exactly two, both present by requirement.** `php artisan db:table store_languages` reports `primary` on `id` and `store_languages_code_unique`. No FK column exists on this table, so [the "an FK column does not also get an explicit index" rule](migrations/uuid-primary-keys.md#an-fk-column-does-not-also-get-an-explicit-index-here) does not apply here — it will apply to stories 0070+ when they add `store_language_id` to their own tables.

**Populated by [`database/seeders/StoreLanguageSeeder.php`](../../database/seeders/StoreLanguageSeeder.php)**, a one-time bootstrap — `if (StoreLanguage::query()->doesntExist()) { … }` — never a repeatable resync: unlike `SalesRegionSeeder`, which owns its catalog permanently and refreshes it on every deploy, this table is seeder-owned only until its first row exists, after which it is entirely administrator-managed. It seeds **Spanish only**, named from the bundled fixture (`StoreLanguage::availableLanguages()['es']`, never a hardcoded `'Español'` literal) rather than English too, and aborts loudly rather than seed an unnamed entry if the fixture is missing or malformed. Called unconditionally from both `DatabaseSeeder` and `ProductionSeeder`, outside the `['local', 'testing']` fixture gate, beside `SalesRegionSeeder`.

**The bundled reference list is a validation/reference source, never pre-seeded as candidate rows.** `database/data/iso-639-languages.json` (the complete ISO 639-1 alpha-2 set, ~184 entries, no regional variants, one JSON object per line — see [`database/data/README.md`](../../database/data/README.md) for its provenance and refresh procedure) is read by exactly **one** named class method, `StoreLanguage::availableLanguages(): array` (`code => name_endonym`), shared by the seeder above and `App\Concerns\StoreLanguageValidationRules::codeRules()`. This is deliberate: with a curated list in hand, a table could instead pre-seed all ~184 entries as inactive candidate rows (the `sales_regions` shape) — rejected because it would make `is_active = false` ambiguous between "never chosen" and "deliberately removed, possibly still holding translations", which are the two states this table's removal-warning extension point (below) needs to tell apart. Under the shipped design a candidate is a fixture entry with no row at all; a removed language is a row with `is_active = false` — the distinction is structural, not a third column.

**`StoreLanguage::availableLanguages()` is read from `app/` at request time, not only from a seeder** — this table's fixture is the first bundled `database/data/` file with that shape; see [conventions/directory-structure.md](../conventions/directory-structure/layout-conventions.md#reading-the-layout--stock-locations-registration-free-policies-databasedata-routes-and-actions-grouping) for what that widens in the general `database/data/` convention. A shape guard inside `availableLanguages()` throws on a missing, empty or malformed fixture (mirroring `SalesRegionSeeder::assertValidCountryFixture()`), so a broken fixture fails loudly rather than validating every submission against nothing.

**The removal warning's extension point gained its first real entry with story 0070.** `StoreLanguage::translationUsageCount(string $languageId): int` sums `DB::table($table)->where($column, $languageId)->count()` across every `{table, column}` pair registered in `config('store-languages.translation_relations')` — shipped **empty** by this story, now holding one literal: `['table' => 'product_category_translations', 'column' => 'store_language_id']`, appended by [`product_category_translations`](schema-products/categories-and-products.md#product_category_translations), with **no** edit to this method, `RemoveStoreLanguage`, or any component — exactly the "append one array literal, and nothing else" contract this table's own D8 committed to. The count is advisory only, never blocking. Four sibling stories (Blog Categories, Blog Tags, Products, Blog Posts) each append their own single entry the same way. See [conventions/base-standards.md](../conventions/directory-structure/config-registry.md#an-app-owned-config-file-is-a-registry-and-must-survive-configcache) for the registry shape this config file follows.

**The registry's own drift guard (`tests/Feature/StoreLanguages/TranslationRelationsRegistryTest.php`, story 0070) is schema-derived, not list-derived.** Its easy half confirms every registered `{table, column}` pair actually exists (`Schema::hasTable()`/`hasColumn()`); its harder, more valuable half enumerates every table matching the `<entity>_translations` naming suffix — via `Schema::getTableListing(schema: Schema::getCurrentSchemaListing(), schemaQualified: false)`, scoped to the **current connection's own database** — and set-equates that list against the registry, so a sibling table that exists but was never registered fails the guard instead of silently going unwarned. `Schema::getCurrentSchemaListing()` matters: an unscoped call lists tables across every database on the shared MySQL server, which this repo's one-`testing_<id>`-database-per-worktree convention (see [testing/worktree-databases.md](../testing/worktree-databases.md)) would otherwise see as false duplicates during normal parallel development.

### `locale_settings`

Source: `database/migrations/2026_09_27_122925_create_locale_settings_table.php` — the app's single, persisted, admin-configurable **default dashboard language** and **default notification-email language**, both constrained to the two-case `App\Enums\UiLocale` (`en`/`es`). **This is the repo's first singleton table.** It is deliberately not a row in `store_languages` (a different value domain — any ISO 639-1 language versus exactly two — and a different cardinality, one settings row versus a list), not a generic key/value settings table (no precedent in this repo, and it would discard `UiLocale`'s typing entirely), and not a config file written at request time (`config/` here is deploy-time and git-committed; see the registry convention linked above).

Model: [`App\Models\LocaleSetting`](../../app/Models/LocaleSetting.php). Columns in real physical order:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TINYINT UNSIGNED` PK, **fixed literal `1`** | deliberately **not** UUIDv7 — a further named exception to [ADR 0001 Amendment 1](../decisions/0001-uuid-primary-keys.md#amendment-1-2026-08-27--the-scope-is-the-policy-not-the-list-of-seven)'s policy, for the opposite reason to [Amendment 5](../decisions/0001-uuid-primary-keys.md#amendment-5-2026-09-06--the-named-bigint-exception-is-real-geography_entries)'s `geography_entries` — see [ADR 0001's Amendment 10](../decisions/0001-uuid-primary-keys.md#amendment-10-2026-09-27--locale_settings-a-second-named-exception-for-the-opposite-reason-to-geography_entries) |
| `default_ui_locale` | `VARCHAR(5)`, `NOT NULL`, **no DB default** | plain `string`, deliberately **not** enum-cast on the model — this is the story's sharpest correctness decision, below |
| `default_notification_locale` | `VARCHAR(5)`, `NOT NULL`, **no DB default** | same, independent column — never read by `defaultUiLocale()` or vice versa |
| `timestamps` | | |

**No index beyond the primary key.** `php artisan db:table locale_settings` reports exactly one: `primary` on `id`. The row is only ever fetched by its fixed key, so there is nothing else to index.

**Singleton-ness is enforced by the fixed key plus one named accessor, not by a `CHECK` constraint.** `LocaleSetting::current(): self` (`findOrFail(LocaleSetting::SINGLETON_ID)`) is the one sanctioned read path for a caller that needs *the* row; a second row can only ever appear via a deliberate `forceCreate(['id' => 2, …])` bypass. Every write is an atomic `LocaleSetting::query()->upsert([...], uniqueBy: ['id'], update: [<the calling action's own column>, 'updated_at'])` — an `INSERT … ON DUPLICATE KEY UPDATE` keyed on the same fixed literal. This upsert shape is not the original design: Phase 3 first shipped `find()` then `forceCreate()`, and a Phase 4 security-audit finding (CWE-362/CWE-755, Low) showed that even with the fixed key, two concurrent *first* writes to an unseeded table both saw no row and both attempted to insert `id = 1` — the loser surfacing a raw `UniqueConstraintViolationException` (a 500) rather than a clean write. The upsert closes that race entirely, and it only works *because* the key is a fixed literal: `ON DUPLICATE KEY` needs a key both writers agree on in advance, which an auto-increment key cannot give. `update:` names **only the calling action's own column**, so `SetDefaultUiLocale` and `SetDefaultNotificationLocale` can never clobber each other's write, including both racing to create the row for the first time — the other column is filled from the *other* accessor's own three-tier resolution on the insert branch, which the `update:` list then never overwrites on the conflict branch.

⚠️ **Neither column is enum-cast, and a reviewer must not add the cast "for consistency" with `SalesRegion.kind` or `User.status`.** `HasAttributes::getEnumCaseFromValue()` resolves a Laravel enum cast with `$enumClass::from($value)`, which throws `\ValueError` the moment a stored value falls outside the current case set. `users.ui_locale` (story 0066) is read once per authenticated user; **this row is read on the fallback branch of every web request, guest requests included**, so an enum cast here would be a strictly worse instance of the identical hazard — it would 500 the entire application the moment the column ever held a stale value, with no authenticated user required to trigger it. Both columns are also `NOT NULL` with **no database default**, deliberately: they *are* the fallback, so a `DEFAULT` would let a broken bootstrap silently succeed with a value nobody chose — the same reasoning `sales_regions.kind` already carries for having no default.

**The one sanctioned way to read either default**, consumed by story 0066's `SetUiLocale` middleware and `User::preferredLocale()`:

```php
// app/Models/LocaleSetting.php
public static function defaultUiLocale(): UiLocale;
public static function defaultNotificationLocale(): UiLocale;
```

Both resolve through the identical three-tier chain, in order, each tier using `tryFrom()` — **never** `from()`:

```php
UiLocale::tryFrom((string) $stored)                      // 1. the persisted admin choice
    ?? UiLocale::tryFrom((string) config('app.locale'))  // 2. bootstrap fallback — tryFrom, NEVER from
    ?? UiLocale::English;                                // 3. last resort
```

Step 2 must be `tryFrom()` because `config('app.locale')` is an arbitrary Laravel locale string with no guarantee of being a `UiLocale` case (`APP_LOCALE=fr` is a legal deployment setting), and `UiLocale::from()` on an unmapped value would 500 every request in the application. Step 3 is reachable only when the settings row is missing *and* the configured locale is not offered — i.e. a broken install — and exists to keep the app rendering, never as a value anything else may rely on as a default (there is deliberately no `UiLocale::default()` method).

**Populated by [`database/seeders/LocaleSettingSeeder.php`](../../database/seeders/LocaleSettingSeeder.php)**, the identical one-time-bootstrap shape `StoreLanguageSeeder` uses (`doesntExist()`-gated, unconditional, composed into `DatabaseSeeder` and `ProductionSeeder`), seeding both columns from `config('app.locale')` and aborting loudly — writing no row — when that value is not a `UiLocale` case.

**Two narrow write actions, never one taking both locales** — `App\Actions\Localization\SetDefaultUiLocale` and `SetDefaultNotificationLocale`, each `__invoke(UiLocale $locale): LocaleSetting`. A single two-parameter action would force every caller to supply both values, turning "change one default" into a read-modify-write that can silently clobber a concurrent change to the column the caller never meant to touch; two single-column actions have no such window. Neither wraps a `DB::transaction()` — one column, one row, no multi-row invariant to protect, unlike `store_languages`' default swap.

**No cache on the read**, despite this row sitting on the app's highest-frequency path (every web request's locale-resolution fallback). `CACHE_STORE=database` in this app today ([schema.md](schema-users-auth.md#infrastructure-tables) lists the `cache` table), so a cache hit would be a single-row indexed lookup against the `cache` table replacing a single-row primary-key lookup against a one-row table — no measurable gain, plus an invalidation obligation. Revisit once Redis lands (PRD assumption 18); the flush-after-commit-never-inside-a-transaction rule is pre-recorded for that day in [security/authorization-patterns.md](../security/authorization-patterns/bypass-cache-and-guards.md#flush-the-permission-cache-after-the-transaction-commits-never-inside-it). No per-request memoisation ships either (a documented deferral, not an oversight): the accessors' own `find()` calls do not call `current()` and are not memoised, so a request reading both defaults pays two queries today.
