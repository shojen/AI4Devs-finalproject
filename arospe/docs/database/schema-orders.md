# Database Schema — Orders

Part of [Database Schema](schema.md) — see [schema.md](schema.md#er-diagram) for the full ER diagram and [schema.md#notes](schema.md#notes) for the UUID/ADR-0001 status notes. This file covers `orders` and `order_items` (story 0045, PRD [§3.2 Orders](../PRD/PRD.md#32-orders)) — Epic 3's second and third domain tables, and the first pair in this codebase whose *only* reason to ship together is a single cross-table invariant: an order is a customer plus one or more priced line items, and every price is frozen at the moment of ordering. Split into its own file rather than appended to [schema-other.md](schema-other.md) because the invariant needs enough prose (the price snapshot, the address snapshot, the three-way delete-behaviour split, a security fix on the write path) to be worth a dedicated page, per [contracts.md](../contracts.md#doc-growth-management-rule)'s doc growth management rule — and because Epic 3's remaining Orders stories (0046–0055) will all extend this same domain rather than `payment_methods`/`customers`/`notifications`.

### `orders`

Source: `database/migrations/2026_09_11_162629_create_orders_table.php` (story 0045) — a greenfield UUID `create_*` migration following [`create_sales_regions_table`](migrations.md#uuid-primary-keys)'s established pattern: `uuid('id')->primary()`, every string column length-capped, every money-like column `decimal`, and no hand-written index on any column `constrained()` already indexes.

Model: [`App\Models\Order`](../../app/Models/Order.php). Columns in real physical order (verified with `php artisan db:table orders` against a live, migrated instance):

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid (v7) PK | `CHAR(36)`; generated by `HasUuids`. A plain UUIDv7 business entity under [ADR 0001 Amendment 1](../decisions/0001-uuid-primary-keys.md#amendment-1-2026-08-27--the-scope-is-the-policy-not-the-list-of-seven)'s general policy — Orders is not one of the ADR's original seven named entities, and needs no further amendment |
| `order_number` | `VARCHAR(20)`, **unique**, **not** mass-assignable | a support-usable reference distinct from the UUID (**D-1**) — see [`order_number` generation](#order_number-generation) below |
| `customer_id` | `CHAR(36)` FK → `customers.id`, `restrictOnDelete()` | required; the customer this order belongs to |
| `status` | `VARCHAR(20)`, default `'pending'` | cast to [`App\Enums\OrderStatus`](../../app/Enums/OrderStatus.php). No index — the same low-cardinality-token cardinality argument [`users.status`](schema-users-auth.md#users) and [`sales_regions.kind`](schema-products.md#sales_regions) already establish |
| `payment_status` | `VARCHAR(20)`, default `'pending_payment'` | cast to [`App\Enums\PaymentStatus`](../../app/Enums/PaymentStatus.php). Same no-index reasoning as `status` |
| `sales_region_id` | `CHAR(36)` FK → `sales_regions.id`, nullable, `restrictOnDelete()` | `NULL` at creation, always — resolving it is stories 0053/0054's job, not this one's (**D-9**) |
| `shipping_rate_id` | `CHAR(36)` FK → `shipping_rates.id`, nullable, `restrictOnDelete()` | `NULL` at creation, always — resolving it is stories 0037/0054's job (**D-9**) |
| `payment_method_id` | `CHAR(36)` FK → `payment_methods.id`, **not** nullable, `restrictOnDelete()` | required — PRD §3.2 requires every order to reference a configured payment method |
| `tax_rate` | `DECIMAL(6,3)`, nullable | a snapshot mirroring [`sales_regions.rate`](schema-products.md#sales_regions)'s own precision. `NULL` at creation, **never** `0.000` — "not configured" and "a legitimate 0%" must not share a representation, the identical rule `sales_regions.rate` already establishes |
| `subtotal` | `DECIMAL(10,2)` | derived from the line items at creation (**D-8**) |
| `tax_amount` | `DECIMAL(10,2)` | `0.00` at creation, always — tax computation is stories 0053/0054's |
| `shipping_amount` | `DECIMAL(10,2)` | `0.00` at creation, always — shipping selection is stories 0037/0054's |
| `total` | `DECIMAL(10,2)` | `subtotal + tax_amount + shipping_amount`, written out as that arithmetic identity rather than as a copy of `subtotal`, so it stays true unchanged once a later story populates the other two terms (**D-8**) |
| `flagged_for_review` | `BOOLEAN`, default `false` | the geo/fraud review flag PRD §3.2 defines for tax resolution (**D-10**); this story never sets it `true` |
| `shipping_address_line1` / `shipping_address_line2` | `VARCHAR(255)`, nullable | frozen copy of the customer's shipping address at order time (**D-4**) — see [The address snapshot](#the-address-snapshot) below |
| `shipping_city` | `VARCHAR(100)`, nullable | " |
| `shipping_postal_code` | `VARCHAR(20)`, nullable | " |
| `shipping_province` | `VARCHAR(100)`, nullable | " |
| `shipping_country` | `VARCHAR(2)`, nullable | " |
| `billing_address_line1` / `billing_address_line2` | `VARCHAR(255)`, nullable | frozen copy of the customer's billing address at order time |
| `billing_city` | `VARCHAR(100)`, nullable | " |
| `billing_postal_code` | `VARCHAR(20)`, nullable | " |
| `billing_province` | `VARCHAR(100)`, nullable | " |
| `billing_country` | `VARCHAR(2)`, nullable | " |
| `created_at` / `updated_at` | timestamp, nullable | |

All twelve address columns mirror [`customers`](schema-other.md#customers) column-for-column in both name and length — deliberately, since they exist to hold an exact copy of a `Customer` row's own address at the moment an order is created.

**No `deleted_at`.** Orders are never deleted this phase; `Cancelled` is a `status` value PRD §3.2 defines, not a soft delete.

**`#[Fillable]`** lists the operator-supplied inputs a new order genuinely needs (`customer_id`, `payment_method_id`) plus the twelve address columns — the address columns are fillable because they are a frozen *copy* written at creation time, not a derived/computed value, and a legitimate future caller (an order-address edit screen) could reasonably need to write them directly. Every other column — `order_number`, `status`, `payment_status`, `subtotal`, `tax_amount`, `shipping_amount`, `total`, `tax_rate`, `flagged_for_review`, `sales_region_id`, `shipping_rate_id` — is **deliberately omitted** and written only via `forceFill()`/`forceCreate()` from [`App\Actions\Orders\CreateOrder`](../../app/Actions/Orders/CreateOrder.php): each is either derived arithmetic, a status a later story owns, or a tax input, and none may ever arrive from a form. Pinned by a test that fails if the omission is undone — the same "omission is this codebase's mass-assignment guard" convention [conventions/base-standards.md](../conventions/base-standards.md#model-conventions) documents.

#### Indexes — exactly the FK-created ones, plus one

`php artisan db:table orders` reports exactly six indexes: `primary` on `id`, `orders_order_number_unique`, and four FK-created indexes (`orders_customer_id_foreign`, `orders_payment_method_id_foreign`, `orders_sales_region_id_foreign`, `orders_shipping_rate_id_foreign`) — verified against a live, migrated instance, not read off the migration. No hand-written `$table->index()` anywhere ([migrations.md](migrations.md#an-fk-column-does-not-also-get-an-explicit-index-here)); `order_number`'s UNIQUE index is the only non-FK index on the table.

### `order_items`

Source: `database/migrations/2026_09_11_162630_create_order_items_table.php` (story 0045), timestamped after `create_orders_table` since it FKs into it.

Model: [`App\Models\OrderItem`](../../app/Models/OrderItem.php). Columns in real physical order (verified with `php artisan db:table order_items`):

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid (v7) PK | `CHAR(36)`; generated by `HasUuids` |
| `order_id` | `CHAR(36)` FK → `orders.id`, `cascadeOnDelete()` | the only cascade in this domain — see [Delete behaviour](#delete-behaviour--the-same-three-way-rule-stated-once) below |
| `product_id` | `CHAR(36)` FK → `products.id`, nullable, `nullOnDelete()` | the catalog product this line item references at order time |
| `product_variant_id` | `CHAR(36)` FK → `product_variants.id`, nullable, `nullOnDelete()` | present only when the line item names a specific variant |
| `product_name` | `VARCHAR(255)` | snapshot, matching [`products.name`](schema-products.md#products)'s own length — always the **parent product's** name, even for a variant line item (a variant has no name column of its own) |
| `product_sku` | `VARCHAR(128)` | snapshot, capped at [`product_variants.sku`](schema-products.md#product_variants)'s length (128) rather than `products.sku`'s (64) — the **longer** of the two, since this column holds either |
| `quantity` | `INT UNSIGNED` | required, `≥ 1` |
| `unit_price` | `DECIMAL(10,2)` | the price **at the time of order** — this story's core invariant. See [The price snapshot](#the-price-snapshot--read-from-the-variant-never-the-parent-when-one-is-named) below |
| `line_total` | `DECIMAL(10,2)` | `unit_price × quantity`, computed once at creation |
| `refunded_quantity` | `INT UNSIGNED`, default `0` | the column ships now; nothing reads it yet — stories 0051/0052's per-line-item refund bookkeeping (**D-3**) |
| `created_at` / `updated_at` | timestamp, nullable | |

**No `deleted_at`.** A line item's lifecycle is tied entirely to its parent order (`cascadeOnDelete()`), never deleted independently.

**`#[Fillable]`** covers only `product_id`, `product_variant_id` and `quantity` — the three values a caller genuinely supplies. `product_name`, `product_sku`, `unit_price`, `line_total` and `refunded_quantity` are all **deliberately omitted**: every one is derived by `CreateOrder` from the resolved catalog row, and a fillable `unit_price` would hand a caller the ability to set its own price — the single sharpest write in this story. Written only via `OrderItem::forceCreate()`, never the relation's ordinary `create()`, which would silently drop all four derived columns.

#### Indexes — exactly the FK-created ones, no others

`php artisan db:table order_items` reports exactly four indexes: `primary` on `id`, and three FK-created indexes (`order_items_order_id_foreign`, `order_items_product_id_foreign`, `order_items_product_variant_id_foreign`) — verified against a live, migrated instance. No hand-written index anywhere on this table either.

### The price snapshot — read from the variant, never the parent, when one is named

The story's central invariant, and the one every downstream Orders story (refunds, tax) depends on: `order_items.unit_price` / `.product_sku` / `.product_name` are written **once**, at creation, from whatever the catalog says *right now* — never re-derived, never re-read on render. A later change to `products.price` or `product_variants.price`, or the deletion of either row (`nullOnDelete()` above), never moves an existing line item's snapshot. This is the identical rule [`sales_regions.rate`](schema-products.md#sales_regions) and this file's own [address snapshot](#the-address-snapshot) already establish for a different column: never re-derive historical financial (or, there, geographic) data from a mutable source.

**D-15 — a variant line item snapshots its price and SKU from the *variant* row, never the parent product.** `product_variants.price` is `NOT NULL` and fully independent of `products.price` — that is what a variant *is* — so the rule is stated per column, exactly as [`CreateOrder`](../../app/Actions/Orders/CreateOrder.php) implements it:

- `unit_price` ← `product_variants.price` when a variant is named, else `products.price`.
- `product_sku` ← `product_variants.sku` when a variant is named, else `products.sku` (also why `order_items.product_sku` is capped at the longer of the two lengths).
- `product_name` ← always `products.name`, whether or not a variant is named.

This needed its own decision and its own regression test rather than "obviously the variant" — the *wrong* implementation (resolve the product, read `$product->price`, attach the variant id only as a reference) is the natural one to write, and it passes every test whose fixtures happen to give the product and its variant the same price. `tests/Feature/Orders/` pins the regression by mutating the **variant's** own row and re-fetching the order — a test that mutates only the parent product's price cannot detect this failure mode at all.

#### F-1 (Phase 4 security audit) — resolving a related pair of ids: validate the relationship, not two existences

A line item payload carries **two** ids that must belong together — `product_id` and `product_variant_id` — and validating that each individually exists (`Rule::exists('products', 'id')`, `Rule::exists('product_variants', 'id')`) does not prove the two rows are *related*. The Phase 4 security audit on this story found exactly that gap: `CreateOrder`'s first draft resolved the product and the variant as two independent lookups, so a caller holding only `orders.create` could submit an expensive product's id together with an unrelated, cheap product's variant id and have the line item written with the expensive product's **name** at the cheap variant's **price** — real, direct price manipulation, invisible to every check a reviewer would naturally run (both ids exist, both rows are re-read from the database, every value is copied from a real catalog row).

The shipped fix resolves the variant **through** its own item's already-resolved product, in memory, after both collections are bulk-fetched (never one query per item — a separate finding, **F-2**, on the same method): a variant whose `product_id` does not match the item's own resolved product is refused with the identical `ModelNotFoundException` a nonexistent variant would produce, never silently accepted. See [security/related-id-pair-resolution.md](../security/related-id-pair-resolution.md) for the full write-up — the vulnerable shape, why the simplest per-item `$product->variants()->findOrFail()` fix could not be used directly here (it would reintroduce the N+1 the bulk-fetch requirement exists to close), and the two other places in this codebase already checked and found safe against the same failure mode.

### The address snapshot

**D-4.** `orders` carries its own frozen copy of the customer's shipping and billing addresses — twelve columns, written once from the resolved `Customer` at creation and never re-read from it afterward. Two reasons: the same "never re-derive historical data from a mutable source" rule the price snapshot follows, and a forward one — PRD §3.2's tax resolution (stories 0053/0054) reads "the **order's** shipping address" and "the **billing** address", and if those columns did not exist here, "the order's address" could only mean a live join to `customers` — so a customer moving from one Sales Region to another would silently change the tax basis of every past order. An order for a customer holding no addresses at all (a legitimate state, per [`customers`](schema-other.md#customers)) persists twelve `null`s rather than failing.

### `order_number` generation

**D-1.** A UUIDv7 is unreadable over the phone and unwriteable on a delivery note, so `orders` carries a second, human-readable identifier. Format: `ORD-{YYYY}-{NNNNNN}`, a per-year sequence zero-padded to six digits (`ORD-2026-000001`), computed from a count of existing rows already carrying that year's prefix — comfortably inside `VARCHAR(20)`. This count-based generator is the minimum collision protection, not proof of concurrency safety (**R-1**): two administrators creating an order in the same instant can race it, so the UNIQUE index has the last word — `CreateOrder` catches the resulting `23000`/`1062` `QueryException` and retries the whole transaction, up to five attempts, with a freshly recomputed number each time, rather than ever surfacing the collision. `order_number` is never mass-assignable and never caller-supplied; it is derived and written with `forceFill()` from the action alone.

### Delete behaviour — the same three-way rule stated once

`orders` and `order_items` are the first pair of tables in this codebase to exercise all three of this project's foreign-key delete behaviours **at once**, which is what makes the rule behind them statable as one rule rather than left to be inferred from three separate examples scattered across the schema. See [migrations.md](migrations.md#the-three-way-delete-behaviour-rule-cascade-restrict-or-null) for the full statement and every table on either side of it.

### Nothing is resolved that this story does not own

A newly created order's `sales_region_id`, `shipping_rate_id` and `tax_rate` are all `null` (never `0`/`0.000` — see above); `flagged_for_review` is `false`; `tax_amount` and `shipping_amount` are `0.00`; and `total` equals `subtotal`. Every one of these is asserted by a dedicated test rather than left to inspection, because a populated column here would look exactly like a working feature while silently masking stories 0037/0053/0054's actual, not-yet-built work.

### Authorization

Gated by [`App\Policies\OrderPolicy`](../../app/Policies/OrderPolicy.php) — see [architecture/authorization.md](../architecture/authorization.md#orderpolicy--the-twelfth-policy) for the full roster entry. `orders.*` are already-seeded module permissions (`RolePermissionSeeder::MODULES` has carried `orders` since task 0002) — no catalog change, no new permission, no re-seed. `CreateOrder` self-authorizes `create` as its own first statement, through `App\Actions\Auth\LogRefusedPrivilegedAttempt` rather than a bare `Gate::authorize()`, since this story ships no route and no Livewire component — the action is the only reachable enforcement point that exists today.
