### `blog_categories`

Source: `database/migrations/2026_09_23_185219_create_blog_categories_table.php` (story 0058) — the blog category taxonomy ([PRD](../PRD/sections/epic-4-blog.md#epic-4--blog) Epic 4). A standalone catalog with no relationships to anything at all — no FK in, no FK out — and **physically independent of [`product_categories`](schema-products/categories-and-products.md#product_categories)**: no shared table, model, namespace or polymorphic taxonomy. It is in the [ER diagram](schema.md#er-diagram) as a standalone `BLOG_CATEGORIES` entity block (the diagram covers every application table, relationships or not); `blog_posts.blog_category_id` (story 0061) gave it its first relationship line — the same arc `product_categories` and `shipping_carriers` completed.

Model: [`App\Models\BlogCategory`](../../app/Models/BlogCategory.php). Columns in real physical order:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `CHAR(36)` PK | UUIDv7 (`HasUuids`), per [ADR 0001](../decisions/0001-uuid-primary-keys.md) — a plain greenfield UUID table, nothing for the ADR to add |
| `name` | `VARCHAR(255)` | the administrator-editable display name, stored as typed after a Unicode-aware trim (`BlogCategoryValidationRules::trimName()` — PHP's `trim()` leaves non-breaking and zero-width spaces, which the normaliser would then fold to a plain space and use to dodge the duplicate check). A name that folds to nothing or to edge whitespace (invisible characters, or a symbol-only name such as `™`) is refused. `BlogCategory::NAME_MAX_LENGTH` is the PHP-side constant this length must move with; a migration cannot reference it directly, so the two are cross-referenced by comment |
| `normalized_name` | `VARCHAR(255)`, **unique** | the folded key the `UNIQUE` index guards and every lookup compares against — see below. Omitted from `#[Fillable]`; derived, never supplied |
| `created_at` / `updated_at` | `TIMESTAMP` nullable | standard Eloquent timestamps |

**Uniqueness lives on `normalized_name`, never on `name`, and there is deliberately no `unique('name')`.** Both the index and every application-side comparison use the output of the one shared [`App\Actions\NormalizeForSearch`](../../app/Actions/NormalizeForSearch.php) (`trim` → lower → ASCII-fold → collapse whitespace), so there is no second definition of "the same category name" to drift from the first, and the connection's collation drops out of the correctness argument entirely. It also closes a real race a PHP-only pre-flight cannot: two concurrent requests submitting "Guías" and "guías" both pass their pre-flight, and an index on the raw `name` would not stop the second insert because the strings are byte-distinct — both fold to `guias`, so the index on `normalized_name` does. `CreateBlogCategory` and `RenameBlogCategory` catch `QueryException` code `23000` and rethrow it as a `ValidationException` on `name`, so the race surfaces as a validation error rather than a 500. A consequence worth knowing: the fold covers accents as well as case, so "Guías" and "Guias" cannot coexist. **`product_categories` still uses the older `unique('name')` plus PHP-comparison shape** — recorded here, not changed by story 0058.

**`normalized_name` is derived by a model event, not by each action.** `BlogCategory::booted()` registers a `saving` hook that rewrites the column whenever a save touches `name` **or** `normalized_name` itself (the second half stops `$category->normalized_name = 'x'; $category->save()` persisting a key that no longer matches the name); an unrelated save leaves it alone. `booted()`, not `boot()` — [`App\Models\Role`](../../app/Models/Role.php)'s `boot()` is a vendor-hook-ordering workaround that does not apply to a model extending `Model` directly. Any change to the normaliser is a re-derive event for every stored `normalized_name`, and an amendment to story 0022's D13, never a local edit.

**The fold can be longer than its input, so `normalized_name`'s 255 is a ceiling, not headroom.** `Str::ascii()` transliterates rather than mapping one to one: measured by folding every Unicode codepoint through `NormalizeForSearch`, the worst case is 5 characters for a single character (`၌` → `hnaik`), with `ß` → `ss` and `€` → `EUR` the everyday cases. A name of exactly 255 `ß` folds to 510. Giving the column headroom is not viable — utf8mb4 caps an index key at 768 characters, below 255 × 5 — so `App\Concerns\BlogCategoryValidationRules::foldedNameFits()` refuses any name whose *folded* form exceeds 255 with a clean validation error on `name`, instead of a silently truncated uniqueness key or a raw `22001`. `tests/Feature/Blog/CreateBlogCategoryTest.php` pins the boundary exactly (127 × `ß` + `a` folds to 255 and is accepted; 128 × `ß` folds to 256 and is refused). **[`blog_tags`](#blog_tags) has the identical exposure at its own length, and resolves it the same way.**

**No `SoftDeletes` — a hard delete.** A lookup-table row has none of the reasons [`users`](schema-users-auth.md#soft-deletes) soft-deletes, and a trashed "Guías" would squat its name forever since `Rule::unique()` does not apply the soft-delete scope. `tests/Feature/Models/BlogCategoryTest.php` pins the trait's absence and `DeleteBlogCategoryTest` pins that the freed name is immediately reusable.

**Indexes — exactly two, both present by requirement.** `primary` on `id` and `blog_categories_normalized_name_unique`. No FK *out* (the inbound FK from [`blog_posts`](#blog_posts) lives on that table), so InnoDB's mandatory-FK-index rule does not apply here; no index on `created_at`/`updated_at`, the same cardinality reasoning the other near-empty admin catalogs give. `tests/Feature/Models/BlogCategoryTest.php` asserts the exact column and index list via `Schema::getIndexes()`.

**The in-use delete guard is shipped by story 0061, in `DeleteBlogCategory` itself.** The action counts `$category->posts()->withTrashed()->count()` and refuses with a `ValidationException` keyed `blogCategoryId` and a `trans_choice()` message (`blog.categories.delete_blocked`) when the count is above zero — a hard block with the count and no confirm-and-proceed path, at every privilege level including Super Admin (it is a domain invariant, not an authorization rule). The count is unfiltered by status (a draft occupies the category) **and unfiltered by `deleted_at`**: a trashed post is still a physical row holding a live foreign key, so `restrictOnDelete()` refuses regardless, and an unscoped count would read 0, pass the guard, hit the FK and report "used by 0 posts". The FK is the last word behind the count: a `1451` from a post assigned between the count and the `DELETE` is converted to the same refusal (`deleteOrFail()` rather than `delete()` so Larastan can trace the `QueryException`, and the recount is floored at 1 because a failed `deleteOrFail()` rolls back the racing assignment it ran inside). The refusal is logged with the snake_case reason `category_still_in_use`. See [`blog_posts`](#blog_posts).

**A later story owns translatable names.** PRD assumption 14 lists category and tag names as translatable content; whichever shape Epic 5 chooses needs its own migration, and would move `normalized_name` and its derivation hook onto the translations table with per-locale uniqueness. Accepted cost, not an oversight.

### `blog_tags`

Source: `database/migrations/2026_09_23_231411_create_blog_tags_table.php` (story 0059) — the blog tag taxonomy ([PRD](../PRD/sections/epic-4-blog.md#epic-4--blog) Epic 4). A standalone catalog with no relationships to anything — no FK in, no FK out — and **physically independent of both [`blog_categories`](#blog_categories) and [`product_categories`](schema-products/categories-and-products.md#product_categories)**: no shared table, model, namespace or polymorphic taxonomy. It is in the [ER diagram](schema.md#er-diagram) as the `BLOG_TAGS` block; the [`blog_post_tag`](#blog_post_tag) pivot (story 0061) gave it its first relationship line.

Model: [`App\Models\BlogTag`](../../app/Models/BlogTag.php). Columns in real physical order:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `CHAR(36)` PK | UUIDv7 (`HasUuids`), per [ADR 0001](../decisions/0001-uuid-primary-keys.md) — `Blog Tags` is one of the ADR's seven *named* entities, so no amendment to the policy was needed (see [Amendment 8](../decisions/0001-uuid-primary-keys.md#amendment-8-2026-09-24--blog_tags-is-the-fifth-of-the-original-seven-to-ship)) |
| `name` | `VARCHAR(100)` | the editable display name, stored as typed after the same Unicode-aware trim `blog_categories` uses (`BlogTagValidationRules::trimName()`). `BlogTag::NAME_MAX_LENGTH` (100) is the PHP-side constant this length and the validation `max:` must move with. 100 rather than `blog_categories`' 255: a tag is a short label typed into an autocomplete, not free-text prose |
| `normalized_name` | `VARCHAR(255)`, **unique** | the folded key the `UNIQUE` index guards and every lookup compares against. Omitted from `#[Fillable]`; derived by a `saving` hook, never supplied. `BlogTag::NORMALIZED_NAME_MAX_LENGTH` (255) |
| `created_at` / `updated_at` | `TIMESTAMP` nullable | standard Eloquent timestamps |

Every mechanism `blog_categories` documents above applies unchanged, and is not restated: uniqueness on `normalized_name` with no `unique('name')`, the shared [`NormalizeForSearch`](../../app/Actions/NormalizeForSearch.php) as the only fold, the `saving` hook in `booted()` (not `boot()`) that also re-derives when `normalized_name` itself is dirty, the `23000` → `ValidationException` race guard, and no `SoftDeletes`. What is different, or additional:

**Two width rules, and the second one is a validation rule rather than a column size.** `name` is 100 and `normalized_name` is 255, but the width is not what keeps a name from overflowing: measured by folding every Unicode code point through `NormalizeForSearch`, one code point can fold to **5** characters (`၌` → `hnaik`), so a legal 100-character name can fold to 500 and no column width up to 255 is a guarantee. `BlogTagValidationRules::foldedNameFits()` therefore refuses any name whose *folded* form exceeds 255 — 51 × `၌` folds to exactly 255 and is accepted, 52 folds to 260 and is refused — so an in-policy name can never reach a raw `22001` or a truncated key. A 500-wide column would also have fitted the index (500 × 4 bytes is under InnoDB's 3072-byte key limit); the validation bound was chosen because it is a guarantee that does not depend on a column size staying where it is.

**Two name-rule methods, because create and find-or-create disagree about what an existing name means.** `BlogTagValidationRules::nameRules()` is the format rules plus a uniqueness closure and is what `CreateBlogTag`/`RenameBlogTag` use, where a collision is a refusal. `nameFormatRules()` is the format rules alone and is what `FindOrCreateBlogTag` uses, where a collision is a *hit*. Using the first in the second would refuse the action's own primary use case. `tests/Unit/Concerns/BlogTagValidationRulesTest.php` pins that the second is the first minus exactly one closure.

**`FindOrCreateBlogTag` resolves a lost insert race by re-fetching, where `CreateBlogTag` refuses.** Both catch `QueryException` code `23000`. For a create, a duplicate is a refusal; for a find-or-create, losing the race means someone else already created what the caller asked for, which is a success — so it re-queries `normalized_name` and returns the winning row. `tests/Feature/Blog/FindOrCreateBlogTagTest.php` drives the collision through the real unique index (a competing row inserted from the `creating` hook) and asserts the outcome.

**Deleting is unconditional, and the cascade that makes "removed from every post that used it" true belongs to the [`blog_post_tag`](#blog_post_tag) pivot.** There is no in-use guard, and `DeleteBlogTag` is complete as shipped — no later story extends it, unlike `DeleteBlogCategory`. PRD's *"removed from every post that used it"* is honoured by the database, not by the action, which is why the hard delete matters: a soft delete is an `UPDATE`, so a cascading foreign key would never fire. **Kept by story 0061:** `blog_post_tag` declares `foreignUuid('blog_tag_id')->constrained()->cascadeOnDelete()` (`DeleteBlogTagTest` asserts it against the real pivot, including for a trashed post). Copying `sales_regions.parent_id`'s `restrictOnDelete()` habit would turn every in-use tag deletion into a database error and silently contradict this story's shipped "an in-use tag deletes" behaviour — a pivot row carries no state of its own (the `passkeys.user_id` case, not the `sales_regions.parent_id` one). The promise is written into `DeleteBlogTag`'s own docblock, where 0061's author will be reading.

**Indexes — exactly two on `blog_tags` itself.** `primary` on `id` and `blog_tags_normalized_name_unique`, the same list `blog_categories` has. The unique index doubles as the read path for story 0063's autocomplete: `WHERE normalized_name LIKE 'term%'` is a prefix scan on a real BTREE index. `tests/Feature/Models/BlogTagTest.php` asserts the exact column and index list via `Schema::getIndexes()`.

**A later story owns translatable names.** PRD assumption 14 lists category and tag names as translatable content; story 0074 moves `name`/`normalized_name` onto a translations table with per-locale uniqueness, which is why this file records the single-language shape as a starting point rather than a final one.

### `blog_posts`

Source: `database/migrations/2026_09_24_162607_create_blog_posts_table.php` (story 0061) — Epic 4's central entity ([PRD](../PRD/sections/epic-4-blog.md#epic-4--blog)). Model: [`App\Models\BlogPost`](../../app/Models/BlogPost.php). A plain greenfield UUID table per [ADR 0001](../decisions/0001-uuid-primary-keys.md) ([Amendment 9](../decisions/0001-uuid-primary-keys.md#amendment-9-2026-09-24--blog_posts-is-the-last-of-the-original-seven-to-ship)). Columns in real physical order:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `CHAR(36)` PK | UUIDv7 (`HasUuids`) |
| `blog_category_id` | `CHAR(36)`, **NOT NULL**, FK → `blog_categories.id` `restrictOnDelete()` | a post has exactly one category. Not `cascadeOnDelete()` (it would silently delete every post in a deleted category) and not `nullOnDelete()` (it would force the column nullable and end "exactly one category"). The block is a database invariant behind `DeleteBlogCategory`'s count guard, so a seeder or query-builder delete is refused too |
| `title` | `VARCHAR(255)` | `BlogPost::TITLE_MAX_LENGTH`, in lockstep with the validation `max:` and `slug`'s width. Deliberately **no uniqueness rule** on `title` (two posts may share one) |
| `slug` | `VARCHAR(255)`, **unique** | derived from `title` by `BlogPost::booted()`'s `saving` hook (`Str::slug()`, only when `title` is dirty), never accepted from a caller: omitted from `#[Fillable]`. Unique so two posts cannot compete for one URL. As wide as `title` because `Str::slug()` transliterates and is not length-preserving. A colliding title is refused as a `ValidationException` on `title` (pre-flight `withTrashed()` check, with the unique index's `1062` as the last word), and so is a title whose slug would be empty or too wide |
| `body` | `MEDIUMTEXT`, nullable | sanitized WYSIWYG HTML (see below). `mediumText`, not `LONGTEXT`, matching `products.description`: the validation rule stays the binding limit. Nullable because a Draft may be saved before its body is written; Published and Scheduled require one |
| `status` | `VARCHAR(20)`, default `'draft'` | `App\Enums\BlogPostStatus` (`draft`/`published`/`scheduled`), string + enum rather than a native `enum`, like `users.status`. Unlike `sales_regions.kind` it **has** a default: every row comes from a human filling a create form, and Draft is the natural starting state |
| `published_at` | `TIMESTAMP` nullable | one column whose meaning is fixed by the status beside it: Draft → always null; Scheduled → a strictly future instant; Published → a past-or-present instant. Omitted from `#[Fillable]`. A Draft save nulls it whatever was submitted; a Published save with no date stamps `now()` (an already-published post keeps its date); `after:now` is not re-applied to a Scheduled post re-saved with the date it already holds, so an overdue scheduled post stays editable. A `TIMESTAMP` holds 1970-01-01 to 2038-01-19, so a Published date must be `after:1970-01-01` and a Published or Scheduled one `before:2038-01-19` (`BlogPost::PUBLISHED_AT_AFTER` / `PUBLISHED_AT_BEFORE`), otherwise the INSERT fails with a raw 1292 error. A Published request whose date is strictly in the future is stored as **Scheduled** with that date and announces nothing (the sweep announces it later), while a date at or before `now()` stays Published — this amends 0061's D-6, which accepted such a post as live ([0061a](../../ai-spec/tasks/done/0061a-blog-post-publish-with-future-date-schedules.md), D-1); editing an already-Published post to a future date is refused on `published_at` instead (D-4) |
| `created_at` / `updated_at` | `TIMESTAMP` nullable | standard Eloquent timestamps |
| `deleted_at` | `TIMESTAMP` nullable | `SoftDeletes` — see below |

**`BlogPost` is the third soft-deleting model, after [`users`](schema-users-auth.md#soft-deletes) and `customers` (the task file called it the second; story 0042's `Customer` had already taken that place), and unlike `users` it overrides no `delete()`.** A post is authored content whose accidental deletion must be recoverable (the two taxonomies hard-delete). A trashed post **keeps its slug**, which stays reserved (`Rule::unique()` and the unique index both see trashed rows), so a restore returns it to its own URL and never collides. It also **keeps its `blog_post_tag` rows** (a soft delete is an `UPDATE`, so the pivot cascade does not fire), which is what makes a restore lossless; a tag hard-deleted meanwhile cascades away even from a trashed post, so the post restores without it. `DeleteBlogPost` soft-deletes, `RestoreBlogPost` (gated on `blog.edit`) restores, and no force-delete path exists.

**Consequences of the soft delete elsewhere.** A category's in-use count must say `withTrashed()` (it counts what the restricting FK counts; see [`blog_categories`](#blog_categories)), whereas a tag's "used by N posts" screen count deliberately excludes trashed posts (`withCount('posts')` applies the `SoftDeletingScope`). The scheduler sweep of story 0064 must not use `withTrashed()`, so a deleted scheduled post never goes live.

**Indexes — exactly four.** `primary` on `id`, `blog_posts_slug_unique`, `blog_posts_blog_category_id_foreign` (the FK's own, created by InnoDB) and the composite `blog_posts_deleted_at_status_published_at_index` on `(deleted_at, status, published_at)`. **`deleted_at` leads** because the `SoftDeletingScope` puts `deleted_at IS NULL` into every query on the table, so the sweep `WHERE deleted_at IS NULL AND status = 'scheduled' AND published_at <= ?` is a leftmost-prefix match; the same rule [`users.status`](schema-users-auth.md#users) states. Neither `status` nor `published_at` earns a standalone index. It is speculative headroom rather than a measured need, kept because this is the one blog table with an unbounded growth story. **There is deliberately no hand-written index on `blog_category_id`**: it would duplicate the FK's own (the shape of the `users_uuid_unique` debt). Index reality was verified with `php artisan db:table blog_posts`, not by reading the migration.

**No `normalized_*` column and no call to `NormalizeForSearch`.** `title` carries no uniqueness rule, and `Str::slug()` is already a lowercasing, accent-stripping transform, so a `normalized_slug` would be a fold of a fold. The two transforms serve different jobs (URL-safe and hyphenated vs. search fold) and must not be unified.

**The body is sanitized on write, on both paths.** `CreateBlogPost` and `UpdateBlogPost` trim the body and pass it through the one existing sanitizer, [`SanitizeProductDescription`](../../app/Actions/Products/SanitizeProductDescription.php), and its one allow-list in `config/html-sanitizer.php` (consumed, never forked), **before** validation, so `required` judges the stored value; an empty result is stored as null. A bare `<img src alt>` inserted from the shared gallery survives it. Any future writer bypassing the actions (a seeder, an import) reopens the stored-XSS exposure, because the guarantee lives in the action, not the column. The blog list must select explicit columns, never `SELECT *`, so `body` stays out of every list row.

**Deliberate deviations from the task's written signatures.** (a) `CreateBlogPost` takes `?string $status` (null means Draft) and `UpdateBlogPost` `string $status`, and both take `?string $body` and `?string $blogCategoryId`, rather than a typed `BlogPostStatus` / `string`: the task's own tests require an omitted status to save as Draft and a forged one to be a `ValidationException` (`Rule::enum()`), which a typed enum parameter cannot receive (a typed enum surfaces as an uncaught `\ValueError`, task 0015's finding F8). Validation error keys are the snake_case column names (`title`, `body`, `blog_category_id`, `status`, `published_at`, `tag_names`); only `DeleteBlogCategory`'s key is camelCase (`blogCategoryId`), being a hand-off contract for story 0062. (b) `App\Actions\Blog\NotifyBlogPostPublished` is a **no-op placeholder created by story 0061**: 0061 must call it from two sites (an update into Published, and a creation already Published, dispatched after the commit) but 0065, which owns the real notification, depends on 0061. 0065 keeps the `__invoke(BlogPost): void` signature and fills the body in. (c) One save may carry at most `BlogPost::MAX_TAGS` (50) tag names (`tag_names`), because each unknown name mints a `blog_tags` row inside the save's single transaction.

**A later story owns translatable content.** Epic 5's retrofit moves `title`, `slug` and `body` onto a translations table, dropping this story's `slug` unique index in that migration.

### `blog_post_tag`

Source: `database/migrations/2026_09_24_162609_create_blog_post_tag_table.php` (story 0061) — the many-to-many pivot between [`blog_posts`](#blog_posts) and [`blog_tags`](#blog_tags). It has no model class: it is reached through `BlogPost::tags()` and `BlogTag::posts()`. Own file, later timestamp than `blog_posts`, because it foreign-keys into both tables.

| Column | Type | Notes |
| --- | --- | --- |
| `blog_tag_id` | `CHAR(36)`, FK → `blog_tags.id` `cascadeOnDelete()` | first column of the composite primary key |
| `blog_post_id` | `CHAR(36)`, FK → `blog_posts.id` `cascadeOnDelete()` | second column of the composite primary key |

**Both foreign keys cascade**, because a pivot row carries no state of its own and is worthless once either parent is gone (the `passkeys.user_id` case, not the `sales_regions.parent_id` one). Story 0059's `DeleteBlogTag` is unconditional *because* `blog_tag_id` cascades — never `restrictOnDelete()`. The asymmetry the post soft delete introduces: the `blog_tag_id` cascade fires (tags hard-delete), the `blog_post_id` cascade does not fire for a soft delete.

**Composite primary key `(blog_tag_id, blog_post_id)`, no surrogate `id`, no timestamps, no position** — the shape of `role_has_permissions`. `blog_tag_id` leads so the tag-filtered post list is a contiguous range scan of the clustered index; `WHERE blog_post_id = ?` is served by the index InnoDB creates for that FK (`blog_post_tag_blog_post_id_foreign`). No hand-written index on either FK column (verified with `php artisan db:table blog_post_tag`: exactly the primary key and that one FK index).

**Written by exactly one class**, `App\Actions\Blog\SyncBlogPostTags`, shared by `CreateBlogPost` and `UpdateBlogPost`, which resolves every submitted name through `FindOrCreateBlogTag` and then `sync()`s. `sync()` is a full replace: a name omitted from the submitted set is detached from that post (the tag row survives). That is safe only while the editor's tag field shows every tag the post holds; a filtered or paginated tag field would turn an omission into a silent revoke. The post write and the tag sync are one transaction, so a refusal while resolving a tag (an actor with `blog.edit` but not `blog.create` naming a new tag) leaves neither the post's columns nor any pivot row.

_Last updated: 2026-09-24 — Story 0061a (publishing with a future date schedules the post): the `published_at` row now records that a Published request with a future date is stored as Scheduled, and that a live post cannot be moved into the future by a date edit._
