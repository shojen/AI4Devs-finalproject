## A `GeographyEntryFactory` override to `name` silently left `normalized_name` stale, making a search test fail against real search code — 2026-09-07

- **Context**: story 0034 (shipping zones UI), writing `tests/Feature/Shipping/SearchGeographyEntriesTest.php` for `App\Actions\Shipping\SearchGeographyEntries` (D-4) — a resolver that matches a normalized search term against `geography_entries.normalized_name` with a prefix `LIKE`. Per the task file's own test-data strategy, rows were built with `Database\Factories\GeographyEntryFactory`'s default state (a plain country row) plus its `community()`/`municipality()` states rather than seeding the real ~8,300-row catalog, overriding the faked `name` with explicit PRD names (`GeographyEntry::factory()->create(['name' => 'España'])`) for traceability.
- **What happened**: every search-by-prefix test failed — searching a normalized `"esp"` found nothing, even though a row named "España" genuinely existed. The failure looked exactly like a bug in the resolver's own `LIKE`/index logic, which is what made it worth tracing rather than dismissing as a fixture problem.
- **Root cause**: `GeographyEntryFactory::definition()`/`community()`/`municipality()` each compute `normalized_name` **inside their own state closure**, from a name they generate themselves (`fake()->unique()->country()`, etc.) — not from whatever `name` the caller later passes to `create([...])`. Overriding `name` via `create(['name' => 'España'])` replaces the display name but leaves `normalized_name` computed from the original faked value, so the row exists with `name = 'España'` and `normalized_name = 'somefakedcountryname'`. The resolver's `LIKE 'esp%'` predicate is applied against `normalized_name`, so it correctly finds nothing — the fixture was internally inconsistent, not the code under test.
- **Fix applied**: every test building a `GeographyEntry` row with an explicit `name` also passes the matching `'normalized_name' => app(NormalizeForSearch::class)($name)'` — wrapped in three small helpers (`makeCountryEntry()`, `makeCommunityEntry()`, `makeMunicipalityEntry()`) in `tests/Feature/Shipping/SearchGeographyEntriesTest.php`, so every call site stays a one-line override rather than repeating the `normalized_name` computation inline. The factory itself was **not** changed — it is owned by story 0032, out of this story's scope, and "recompute `normalized_name` from whatever `name` ends up persisted" is a real design option for a future story to make, not a bug to patch around silently.
- **How to avoid it next time**: **when a factory computes a derived column (a normalized/slugged/hashed copy of another field) inside its own `definition()`/state closure, overriding the source field via `create([...])` does NOT recompute the derived one — pass both explicitly, every time, or the row is internally inconsistent in a way that only a test exercising the derived column will ever notice.** This is a narrower instance of a shape already implicit elsewhere in this codebase (`sales_regions.slug`, `product_variants.combination_hash`/`sku`) wherever a factory or seeder writes a derived value once at creation time — the fix is always the same: compute the derived value from the override at the call site, never trust the factory's own internal generation to have "already handled it" once any of its inputs are overridden.

## A `flux:fieldset` wrapping a Flux field silently swallows its auto-rendered validation error — 2026-09-07

- **Context**: story 0031a (product variant generator — the cartesian combination builder UI), building the axis-picker modal in [`resources/views/livewire/products/variant-builder.blade.php`](../../resources/views/livewire/products/variant-builder.blade.php). `attributeTypeIds` (a `flux:checkbox.group`) is deliberately named to equal `GenerateProductVariantCombinations`'s own validation bag key (D-17.1), specifically so a Flux field auto-renders its bound error with no explicit `flux:error` in the template — the one place on this whole screen where that shortcut is meant to work. The first draft wrapped the checkbox group in a separate `flux:fieldset` carrying its own `:legend`, matching how a plain HTML `<fieldset>` groups a checkbox list.
- **What happened**: a refused generation (over the cap, an empty type, nothing selected) threw the expected `ValidationException` keyed on `attributeTypeIds`, and the modal correctly stayed open per D-17.3 — but the error message itself never rendered anywhere on screen. No PHP error, no console error, no failed request; `Livewire::test()->call('generateCombinations')->assertHasErrors('attributeTypeIds')` passed (the error genuinely lands in the bag), which is exactly what made the gap easy to miss — every server-side signal said the refusal worked, and only looking at the actual rendered HTML showed the message was gone.
- **Root cause**: reproduced by reading the real vendor source rather than guessing, per this log's own [hedge rule](archive-2026-08-23-to-2026-08-26.md#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24). `flux:with-field` — the mixin every `flux:checkbox.group`/`flux:input`/etc relies on to auto-render its bound `<flux:error>` slot — wraps its whole label/description/error block in a single conditional:

  ```blade
  {{-- vendor/livewire/flux/stubs/resources/views/flux/with-field.blade.php --}}
  <?php if (isset($label) || isset($description) || isset($descriptionTrailing)): ?>
      <flux:field :attributes="$fieldAttributes">
          {{-- ...label, description, $slot... --}}
          <flux:error :attributes="..." />   {{-- the whole error slot lives INSIDE this branch --}}
      </flux:field>
  <?php else: ?>
      {{ $slot }}   {{-- no flux:field wrapper at all -- and no error slot -- when none of the three is set --}}
  <?php endif; ?>
  ```

  A `flux:checkbox.group` with no `:label`/`:description`/`:description:trailing` prop of its own never enters the `if` branch — it falls straight to the bare `{{ $slot }}` else-branch, with **no** `<flux:error>` anywhere in its output, regardless of whether the property name matches the error bag key. Wrapping the group in a separate `flux:fieldset` with its own `:legend` does not help: `flux:fieldset`'s `:legend` is not one of the three props `with-field` inspects, so from `flux:checkbox.group`'s own perspective nothing was ever set, and the property-name-equals-bag-key shortcut (D-17.1's whole reason for choosing that name) silently does nothing.
- **Fix applied**: `:label` and `:description` moved directly onto `flux:checkbox.group` itself, with the wrapping `flux:fieldset` removed — matching [`resources/views/livewire/roles.blade.php`](../../resources/views/livewire/roles.blade.php)'s own existing precedent (`<flux:checkbox.group wire:model="..." :label="__('Permissions')">`), which had shipped the correct shape since task 0011 with nothing pointing at it as the reason. Re-verified by execution: the same refused-generation test now shows the error rendered, with `assertSee` against the real HTML rather than only `assertHasErrors`.
- **How to avoid it next time**: **a Flux field's auto-rendered error slot (`flux:with-field`) exists only when the field itself carries `:label`, `:description`, or `:description:trailing` — a wrapping `flux:fieldset`/`flux:field` with its own heading does not satisfy that condition, however visually equivalent the two look.** When relying on the property-name-equals-bag-key shortcut this project already uses elsewhere ([conventions/naming.md](../conventions/naming.md), D-17.1 here), put `:label`/`:description` directly on the bound Flux component, never on a separate wrapping element. And more generally, matching this log's now-repeated Flux/Blaze lesson: **a passing `assertHasErrors()` (or any assertion against component *state*) proves the error was raised — it proves nothing about whether the *template* renders it.** Verify a validation-error-rendering claim against the real compiled HTML (`assertSee`, or a browser test), the same discipline the two `@disabled`/`@js()` entries below already establish for a different Flux/Blaze compile-time trap.

## A `.env.testing` missing most of `.env`'s content produced a wide spray of unrelated-looking Feature test failures — 2026-09-06

- **Context**: story 0032 (shipping geography catalog seed), opening a brand-new `git worktree` for the story per [worktree-databases.md](../testing/worktree-databases.md)'s setup steps.
- **What happened**: `.env.testing` was hand-written from scratch rather than copied from `.env` — six lines (`APP_ENV`, `DB_*`), following step 3's *content* without first doing step 1's literal *copy*. The story's own new tests (which touch no session, no encrypted cookie, no Vite asset — pure database seeding with no HTTP layer at all) passed cleanly throughout, which masked the gap. Running the **full** unscoped suite as this project's own quality-gate rule requires surfaced 116 failures spread across `ProductCategories\IndexTest`, `Users\IndexTest`, `SalesRegions\IndexTest`, `Products\AttributeTypesIndexTest`, `Media\UploadTest`, `Settings\ProfileUpdateTest` and others — modules this story never touched. The first failure signature (`Failed asserting that an instance of class Illuminate\View\ViewException is an instance of class Illuminate\Auth\Access\AuthorizationException`) reads exactly like a real authorization regression: a Livewire component's own exception being swallowed and replaced by a *rendering* failure, not an auth one.
- **Root cause**: two missing pieces, found one after the other, neither hinted at by the symptom. **(1)** `.env.testing` had no `APP_KEY` at all — Laravel's `LoadEnvironmentVariables` loads `.env.testing` in place of `.env` (not merged) once `APP_ENV=testing`, so every session/cookie/encryption-touching code path failed with `No application encryption key has been specified`, and because that exception fires *while rendering a Blade view* (session/error-page machinery), PHPUnit reported it as the wrapping `Illuminate\View\ViewException` rather than the real cause — which is what made it look like an authorization bug. **(2)** Once `APP_KEY` was restored (copying `.env`'s real value), the next failure was `Vite manifest not found at: public/build/manifest.json` — a fresh worktree checkout has no `public/build/` (gitignored, never built) and no `public/storage` symlink (also gitignored), and nothing in the setup steps had built either yet. Both gaps are silent precisely because the *first* test files exercised (this story's own) never render a page or an uploaded asset — the gap was invisible until the unscoped, whole-suite run touched a screen that does.
- **Fix applied**: `.env.testing` rewritten as a full copy of `.env` with only `APP_ENV`/`DB_HOST`/`DB_DATABASE` changed (matching every other worktree's `.env.testing` — confirmed by diffing against a sibling worktree's file), then `npm install && npm run build` and `php artisan storage:link` run once. The full suite went from 116 failures to 0 (1921/1924 passed, 3 pre-existing skips) with **no application code changed** — proving the failures were entirely environmental. [worktree-databases.md](../testing/worktree-databases.md) gained an explicit warning on step 1 and a new step 6 covering the build/link prerequisite.
- **How to avoid it next time**: **when opening a new worktree, follow [worktree-databases.md](../testing/worktree-databases.md)'s setup steps as a literal copy-then-edit, not a "write the six lines I know matter" shortcut** — `.env.testing` needs `APP_KEY` and everything else `.env` carries, not only the `DB_*`/`APP_ENV` lines this doc's own step 3 calls out (that step lists what to *change*, not the complete list of what the file needs). Separately: **run `npm run build` and `php artisan storage:link` once per fresh worktree checkout, before trusting any Feature test result** — both are silently absent from a `git worktree add`, and a test suite that happens to never render a page or serve a file will not reveal either gap. Most generally: **when a scoped or early test run is green but a class of failure appears only once the full suite runs, suspect the environment before suspecting a regression** — a symptom that spans many unrelated modules at once (here: `ViewException` standing in for a dozen different real causes) is the signature of a setup gap, not a code change, and the fix is to run the exact failing test file *alone* with a clean cache before writing up a finding as a real regression.

## Playwright's `selectOption` fires `change` unconditionally, so no `->select()`-driven browser test can be the regression net for a null-`<select>` desync — 2026-09-06

- **Context**: story 0031 (product variants — the variant builder inside the product editor), designing the browser-test detector for D-9's null-`<select>` desync trap — two native `<select>`s per combination row, bound to array paths, the worst case in the codebase yet for [the 2026-08-16 null-`<select>` desync entry](archive-2026-07-21-to-2026-08-17.md#a-null-livewire-property-bound-to-a-native-select-silently-dropped-the-users-own-pick--2026-08-16). Phase 1's `frontend-qa` re-verified, by reading the actual Pest browser-testing plugin source rather than reasoning about it, whether any of the three obvious tests for this bug class can actually fail against it — independently re-verified by `product-owner` before being adopted.
- **What happened**: none of the three can. `Livewire::test()->set(...)` writes the property directly with no DOM in play, so it was already known to be blind. `assertValue()`/`assertSelected()` resolve to Playwright's `inputValue()` → `select.value`, which returns `''` both when the disabled placeholder is correctly selected **and** when `selectedIndex === -1` (the bug) — indistinguishable. And `visit(...)->select(...)` — `InteractsWithElements::select()`, a one-line pass-through to Playwright's `selectOption` (`vendor/pestphp/pest-plugin-browser/src/Api/Concerns/InteractsWithElements.php:117-122`, `$this->guessLocator($field)->selectOption($option);`) — cannot fail against the bug either: the browser driver's injected `selectOption` implementation sets `select.value`, sets `option.selected = true`, then dispatches `input` **and** `change` **unconditionally**, which destroys any pre-existing `selectedIndex === -1` state before it can be observed and manufactures the very `change` event whose *absence* is what the original 2026-08-16 bug was about. Worse: a shipped test's own inline comment claims the opposite. `tests/Browser/UsersIndexTest.php` (around lines 114-117) argues that picking the first real option after the disabled placeholder "is the only choice that actually exercises the fix" (`$roleId` defaulting to `''` rather than `null`) — false: `->select()` fires `change` regardless of which option is picked, so that test passes identically whether `App\Livewire\Users\Index::$roleId` defaults to `''` (the real fix) or to `null` (the reintroduced bug). It remains a legitimate round-trip test; it was never the regression net its own comment claims it is.
- **Root cause**: every Pest/Playwright helper in this family either writes the property directly (never touching the DOM) or drives the `<select>` through `selectOption`, which is written to make a real user's pick land reliably — including firing the DOM events a real click would fire — rather than to probe the DOM's own pre-interaction state. That design choice is exactly what makes the whole family structurally blind to a bug that only exists **before** any interaction happens: a `null`/`undefined`-bound property desyncing `selectedIndex` from the `<option selected>` placeholder the markup declares. `UsersIndexTest.php`'s comment was written as if picking a *different* option (versus the first) were the risk; the real risk is that any `->select()` call at all repairs the desync as a side effect of firing `change`, no matter which option is picked.
- **Fix applied**: no test file was edited to correct the false claim — `tests/Browser/UsersIndexTest.php:114-117`'s comment is left as it stands, and this entry is the correction, per this project's audit-authored-page convention of recording a wrong claim rather than silently rewriting code outside the scope of the pass that found it. The **real** detector — used for the first time in `tests/Browser/Products/VariantBuilderTest.php` (case B1) — reads `selectedIndex` directly, **before any interaction**:

  ```php
  // tests/Browser/Products/VariantBuilderTest.php
  $page->assertScript(
      'document.querySelector(\'[name="combinationRows.0.typeId"]\').selectedIndex',
      0                       // 0 = the disabled placeholder is genuinely selected
  );                          // -1 = wire:model assigned null/undefined -- the bug
  ```

  `assertScript()` strict-compares against a live-page `evaluate()`, so it fails the instant a bound value is `null`, before any user action, with no event-timing dependency and no flakiness. `selectedIndex` is the only DOM property of the three approaches above that actually separates the two states.
- **How to avoid it next time**: **a "does the picked value round-trip through the browser correctly" test and a "was this specific pre-interaction DOM-desync bug prevented" test are not the same test, and a helper that fires a synthetic `change`/`input` event as a side effect of "picking a value" can never be the second kind.** When a regression's whole mechanism is "a bound value never had the chance to diverge because nothing touched it yet," the detector must read a DOM property **before** any simulated interaction — `assertScript()` against `selectedIndex`, never `assertValue()`/`assertSelected()`/`->select()`. Reach for this shape whenever a native `<select>` (or any element whose pre-interaction state is the thing under test) is bound to a value that could legitimately be absent. And more generally: **before trusting a shipped test's own inline comment about what it proves, re-derive the mechanism independently** — read the actual driver/helper source, as this story's `frontend-qa` did for `InteractsWithElements::select()`, rather than accepting a plausible-sounding claim at face value. This is the same lesson [the 2026-08-24 hedge entry](archive-2026-08-23-to-2026-08-26.md#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24) and [the 2026-08-29 "verified" entry](2026-08-28-to-2026-08-31.md#one-docs-pass-reported-two-gaps-that-were-not-there-both-marked-verified--2026-08-29) both already establish, arriving from a third direction: a **test's own inline rationale**, not a review comment or a docs pass, was the confidently wrong claim this time.

## GitHub Actions' Ubuntu runner ships `libheif` with no AVIF encoder, so Imagick silently wrote a 0-byte `.avif` — 2026-09-06

- **Context**: `feature-entrega2-ARP` branch, no story in progress — just pushing to GitHub after `sail artisan test` had reported the whole suite green locally.
- **What happened**: the same suite failed in the `tests` GitHub Actions workflow, with exactly one failure: `Tests\Unit\Actions\Media\GenerateImageConversionsTest > the generated .avif file is genuinely AVIF, asserted on the ISO-BMFF ftyp brand bytes` — `expect(substr($avifBytes, 4, 4))->toBe('ftyp')` got `''` instead. `substr()` of an empty/near-empty string returns `''`, so the real fact is that `$result['avif_path']`'s stored content was essentially **0 bytes** on the runner, not merely mis-formatted. `App\Actions\Media\GenerateImageConversions::__invoke()` never noticed anything wrong: `$disk->put($avifPath, $image->encode(new AvifEncoder)->toString())` writing an empty string still returns `true`, so the `?: throw new RuntimeException(...)` guard next to it (see [conventions/base-standards.md](../conventions/base-standards.md), story 0019 Phase 4 finding F-3) never fires — an empty write and a successful write are indistinguishable to that check.
- **Root cause**: since a recent GitHub-hosted Ubuntu runner image update, `libheif` ships with AVIF **decode** support only — its AVIF **encoder** plugins (`libheif-plugin-aomenc` for the AV1/libaom codec, and siblings) were split into separate packages that Ubuntu does **not** install by default, confirmed against [actions/runner-images#13728](https://github.com/actions/runner-images/issues/13728) (closed by GitHub as "not planned" — this is accepted upstream behavior, not a transient outage). Imagick therefore still *registers* AVIF as a known format (an `extension_loaded('imagick')`/`Imagick::queryFormats('AVIF')` check would report success) but silently produces an empty blob the moment it actually tries to **encode** one, rather than throwing. This project's own Sail image (`docker/8.5/Dockerfile`) installs `php8.5-imagick` via a plain `apt-get install`, which pulls the AVIF encoder plugin in as a `Recommends` dependency — so the encoder has always been present locally, and this gap was invisible until the first real CI run exercising it. It is the same underlying codepath, but a different mechanism, from [the 2026-08-28 Imagick resource-limit entry](2026-08-28-to-2026-08-31.md#an-imagick-resource-limit-was-requested-in-the-wrong-unit-masked-by-the-hosts-own-policyxml-silently-clamping-it--2026-08-28) — that one was a wrong resource-limit *unit* masked by a stricter local `policy.xml`; this one is a missing *codec* on the CI host that Sail's own `apt-get install` happens to satisfy as a side effect nobody asked for.
- **Fix applied**: added an `Install libheif AVIF encoder plugin` step to [`.github/workflows/tests.yml`](../../../.github/workflows/tests.yml) (`sudo apt-get update && sudo apt-get install -y libheif-plugin-aomenc`), placed immediately after the existing `Setup PHP` step (which already carries the `extensions: imagick` correctness input from story 0019 — see [testing/ci/pipeline-integration.md](../testing/ci/pipeline-integration.md)) and before `Run Tests`, so both matrix legs (PHP 8.4 and 8.5) get the encoder before any test runs. The step is deliberately independent of `Setup PHP`'s own extension-resolution mechanism (`shivammathur/setup-php`), since the missing piece is a system library plugin, not a PHP extension.
- **How to avoid it next time**: **when a test that decodes or encodes through a system-library-backed format (an image/video codec, a font renderer, a compression algorithm) passes under Sail but fails only in CI, suspect the underlying system library the extension links against before suspecting the test or the application code — and check decode and encode as two separately-installable capabilities, not one.** A format being *registered* (`queryFormats()`, `extension_loaded()`) proves nothing about whether every operation on it is wired to a real codec; only exercising the actual operation (as this project's own byte-signature assertion already does, per [security/image-upload-processing.md](../security/image-upload-processing.md)) catches the gap. This is the **second** Imagick/AVIF-specific CI-vs-local environment mismatch on this exact codepath in two weeks — a future change touching `GenerateImageConversions` or its CI step should treat "verify on a real GitHub Actions run, not only Sail" as a standing requirement for this one action, not a one-off diagnostic.

## `DB::transaction($fn, attempts: N)` retried a closure that mutated a model created outside it, producing a silent lost update reported as success — 2026-09-04

- **Context**: story 0029 (product variants — core backend). The same remediation that added `product_variants`' cross-table SKU-collision locking also added `attempts: 3` to three `DB::transaction()` calls (`CreateProduct`, `CreateProductVariant`, `UpdateProduct`), so the fixed lock order those transactions rely on converges under a real deadlock instead of 500-ing on the first collision.
- **What happened**: `appsec-auditor`'s Phase 4 re-audit — re-auditing the fix as new code, per the entry below on this same log — reproduced that `UpdateProduct`'s own retry was unsafe. Its closure captures `$skuChanged = $product->sku !== $sku` and then calls `$product->update([...])`, where `$product` is an `Eloquent` model **created outside the closure** and passed in as a parameter. Executed rather than reasoned about: on attempt 1, `update()` runs and `syncOriginal()` fires; on attempt 2 (after a rollback from a genuine `1213` or, far more likely, a `Lock wait timeout exceeded`), `$product->sku !== $sku` now reads `false` and `isDirty()` after `fill()` also reads `false` — so `update()` issues **no SQL at all**, the SKU re-derivation cascade is skipped entirely (`$skuChanged` gates it), and the action **returns a `Product` whose in-memory attributes show the new values** while nothing was actually written or rolled forward. A silent lost update, reported to the caller as a success. `App\Actions\Products\SyncProductGallery` shares the exact same shape (`forceFill(...)->save()` on the same outside-the-closure instance), so the featured-image/gallery write is lost with it.
- **Root cause**: `attempts: N` makes the closure **retryable**, and a retry restores the database to its pre-attempt state but does **not** reset any PHP object the closure mutated on a prior attempt — `Model::update()`/`save()` calls `syncOriginal()` on success regardless of whether the surrounding transaction later rolls back, so a second attempt reads its own first attempt's dirty-tracking as the baseline and silently no-ops. This is invisible by construction: `save()` on a model with nothing dirty is a **successful** no-op, not an error, so nothing throws and nothing logs. The two other `attempts: 3` sites in the same remediation (`CreateProduct`, `CreateProductVariant`) do **not** have this problem, because both build the row they mutate **inside** the closure via `forceCreate()` — a retried attempt there re-does real work rather than skipping it, the distinguishing property that makes `attempts: N` safe on one sibling and unsafe on another that looks identical from the outside.
- **Fix applied**: `UpdateProduct`'s `DB::transaction()` call now takes **no** retry parameter at all, with a comment above it naming this hazard so nobody re-adds `attempts: N` without re-deriving the analysis first — see [`app/Actions/Products/UpdateProduct.php`](../../app/Actions/Products/UpdateProduct.php). The alternative fix considered and rejected was the key-passing shape `App\Actions\SalesRegions\SetSalesRegionActive` already established (pass **keys** into the closure, re-fetch every row the closure mutates from inside it, on every attempt) — not adopted here because `UpdateProduct` returns the caller's own `$product` instance and its cascade reads `$skuChanged` from a pre-mutation attribute, so re-shaping the action's return contract to close this window costs more than removing the retry outright. Full reproduction, the executed before/after table, and a second, coupled finding (`attempts` is silently inert on a **nested** `DB::transaction()` — only the outermost transaction's `attempts` ever fires, so `App\Livewire\Products\Editor::save()`'s own outer transaction, once story 0031 ships it, must **not** get an `attempts:` of its own without first fixing this same closure shape one level up) are in [security/derived-column-invariants.md](../security/derived-column-invariants/retry-and-transaction-hazards.md#what-the-remediation-introduced-a-retried-transaction-is-a-retry-safe-unit-or-it-is-a-lost-update).
- **How to avoid it next time**: **adding `attempts: N` to a `DB::transaction()` call is a change to the closure's contract, not a flag — before adding it, check that every model, collection or accumulator the closure writes to was either created *inside* it or is re-fetched by key at the top of it, on every attempt.** The two safe shapes in this codebase: build/insert the row inside the closure (`forceCreate()`/`create()`, as `CreateProduct`/`CreateProductVariant` do), or pass primitive keys into the closure and re-read every row from the database as the closure's own first statement (as `SetSalesRegionActive` does). An Eloquent model instantiated *outside* the closure and mutated *inside* it is the common, easy-to-miss case, and it fails **silently** rather than loudly — there is no exception to catch, because a non-dirty `save()` is defined to succeed.

## An action's own parameter default reintroduced the omission ambiguity its stricter collaborator was built to close — 2026-09-01

- **Context**: story 0024, `App\Actions\Products\CreateProduct`/`UpdateProduct` wrapping `App\Actions\Products\SyncProductGallery` — the single writer of `products.featured_media_id` and every `product_media` row, whose own contract (D-17) is deliberately strict: the ordered gallery array it receives is the **complete, authoritative** new state, never a delta, so an omitted id is a detach and an empty array is "clear the whole gallery".
- **What happened**: the first implementation gave `CreateProduct`'s/`UpdateProduct`'s `$featuredMediaId`/`$orderedGalleryMediaIds` parameters ordinary PHP defaults (`= null`, `= []`) — the reflexive shape for "this field is optional". `appsec-auditor`'s Phase 4 audit round 1 flagged it as **F-1** (Medium): any caller that simply omitted the two arguments — a future queued job, a partial form submit, a test written before the gallery UI existed — would reach `SyncProductGallery` with an empty array and a `null` featured id, silently detaching every existing image and nulling the featured image, with no error and no way to distinguish "the caller meant to clear the gallery" from "the caller never mentioned it". The re-audit found the identical shape a second time (**F-6**) on `UpdateProduct`'s `$description` parameter, which had kept `CreateProduct`'s `= null` default even though the two actions are not equivalent for that field: on **create**, omitting `description` and "no description" are the same real state (a brand-new product genuinely starts empty), so the default is safe there and was deliberately kept; on **update**, omitting it does not mean "clear the description" — it usually means the caller never touched that field — so the identical-looking default silently wipes an existing description on a partial-field update.
- **Root cause**: `SyncProductGallery`'s whole design point is that **omission from its input is a decision, never left ambiguous** — that is what "complete, authoritative array" means. A default on the *wrapping* action's own signature reopens exactly the ambiguity the stricter collaborator exists to remove, one layer closer to the real caller: the collaborator can no longer tell "the actor explicitly submitted an empty gallery" from "the actor never mentioned the gallery at all", because both now produce the identical call. The `$description` case shows the same root cause without any collaborator in the picture at all — a full-replacement field on an **update** path has the identical property (omission from the payload is ambiguous between "clear it" and "leave it"), so the rule is not really about `SyncProductGallery` specifically.
- **Fix applied**: both `CreateProduct` and `UpdateProduct` now require `$featuredMediaId`/`$orderedGalleryMediaIds` with **no default** — a caller must always state intent, matching `SyncProductGallery`'s own contract. `UpdateProduct`'s `$description` parameter lost its `= null` default (F-6); `CreateProduct`'s keeps it, deliberately, with a docblock recording *why* the two actions are allowed to differ on this one parameter. See [`app/Actions/Products/CreateProduct.php`](../../app/Actions/Products/CreateProduct.php) and [`UpdateProduct.php`](../../app/Actions/Products/UpdateProduct.php).
- **How to avoid it next time**: **a default is safe on a parameter only when omitting it and the default's own value denote the *same real-world state* for every call site that will ever use it — never merely "this field is optional" as a convenience.** Two concrete checks. **(a)** When an action wraps a collaborator whose contract treats its input as complete and authoritative (a full-replace `sync()`, an ordered array, any "this is everything" shape), the wrapping action must not supply a default for the parameter it forwards — the collaborator's own strictness is undone the moment something upstream of it can omit the value silently. **(b)** On an **update** path specifically, a default that was correct on the matching **create** action does not transfer by symmetry — "no value yet" (create) and "value not being touched" (update) are different states, and only the first one is safely represented by a default. This is [the "absence in a payload from a partially-visible form is not a decision" family](archive-2026-08-17-to-2026-08-21.md#a-guard-took-the-state-it-was-guarding-as-a-parameter-reopening-its-own-hole-one-level-up--2026-08-20) arriving from a new direction: there the ambiguity lived in the *payload a partially-visible UI form submits*; here it lives one layer lower, in the *action's own parameter defaults*, with no form or UI involved at all.
