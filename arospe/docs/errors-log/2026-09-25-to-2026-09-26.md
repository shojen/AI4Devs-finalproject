## `expectsOutputToContain()` matches at most one expected substring per output line, not per multi-substring line — 2026-09-30

- **Context**: story 0081, `tests/Feature/Console/Commands/GenerateDemoDataTest.php`'s refusal-message assertions for `demo:generate-data` outside the `local`/`testing` allow-list — three separate `expectsOutputToContain()` calls, each checking for one of `"local"`, `"testing"`, `"--force"`.
- **What happened**: `backend-expert`'s first draft printed all three substrings on a single refusal line. Only the first `expectsOutputToContain()` assertion passed; the other two failed with a misleading "Output does not contain [X]" even though `X` was genuinely present in the printed text.
- **Root cause**: `Illuminate\Testing\PendingCommand`'s Mockery-based `createABufferedOutputMock()` sets up one `doWrite()` expectation per call to `expectsOutputToContain()`, and each expectation consumes exactly one `doWrite()` invocation (one printed line) to test against — never re-scanning a line a prior expectation already matched against. A command that writes several expected substrings on the *same* line satisfies only one expectation; the rest see a `doWrite()` call whose line doesn't contain their substring (because it was already consumed) and fail, even though the substring is genuinely present in the command's real output taken as a whole.
- **Fix applied**: `App\Console\Commands\GenerateDemoData::handle()` (`app/Console/Commands/GenerateDemoData.php`) splits its refusal message into four separate `$this->error()`/`$this->line()` calls, one output line per expected substring, matching the existing convention in `tests/Feature/Console/Commands/PublishScheduledBlogPostsTest.php`. Verified by reading `Illuminate\Testing\PendingCommand`'s source directly, not assumed; kept as-is through Phase 5 code review (non-blocking suggestion F-A), not re-litigated.
- **How to avoid it next time**: when a command's test asserts multiple substrings via `expectsOutputToContain()`, each expected substring must be printed on its **own** output line (its own `doWrite()` call) — never combined onto one line, however natural that reads as prose. This is a test-mechanic constraint, not a bug in the command under test.

## `App::setLocale()` silently mutates `config('app.locale')`, poisoning an unseeded config-tier fallback assertion in a later request — 2026-09-28

- **Context**: story 0066, `tests/Feature/Localization/UiLocaleResolutionTest.php`'s leak-forward test ("a previous authenticated request does not leak its locale into an immediately following guest request") — two `$this->get()` calls in one test method: an authenticated request for a user with `ui_locale` `'es'`, then a guest request expected to resolve to the config-pinned default `'en'`. Unlike the file's other fallback-tier tests, no `locale_settings` row was seeded.
- **What happened**: the guest request resolved to `'es'` instead of the pinned `'en'`, even though `App\Http\Middleware\SetUiLocale` (the production code under test) called `App::setLocale()` unconditionally on both requests exactly as designed.
- **Root cause**: `Illuminate\Foundation\Application::setLocale()` (`vendor/laravel/framework/src/Illuminate/Foundation/Application.php:1600`) has a side effect beyond setting the translator's locale — it also runs `$this['config']->set('app.locale', $locale)`. The first (authenticated, `'es'`) request's `App::setLocale('es')` therefore overwrote `config('app.locale')` from the test's pinned `'en'` to `'es'`. With no `locale_settings` row present, `App\Models\LocaleSetting::defaultUiLocale()`'s tier-3 fallback reads that same, now-poisoned `config('app.locale')`, so the guest request's resolution incidentally depended on the first request's side effect — a Laravel implementation detail unrelated to the leak-forward property the test set out to pin.
- **Fix applied**: the test now seeds an explicit `LocaleSetting::factory()->create(['default_ui_locale' => 'en', ...])` row before the two-request sequence — the same pattern the file's other fallback-tier tests already use, for exactly this reason (R-13/tier-masking). This routes both requests through tier 1 (the persisted admin default), which `App::setLocale()`'s config mutation cannot affect, so the test purely pins the leak-forward property again.
- **How to avoid it next time**: a test that calls (directly, or through middleware) `App::setLocale()` more than once in the same process, and also asserts a fallback that reads `config('app.locale')`, cannot rely on an unseeded config-tier fallback across that boundary — `App::setLocale()` itself mutates that config key as a side effect. Seed the real persisted row the fallback chain is meant to prefer (here, `LocaleSetting::factory()->create([...])`) so the assertion exercises the intended tier instead of an already-mutated config value. This is the same "test asserted against ambient/mutated state" trap as the `SUPER_ADMIN_EMAIL` precedent (see this doc's topic index, Testing/QA section).

## A hand-injected constructor's real class type isn't satisfied by a same-shaped test double with no inheritance relationship — 2026-09-27

- **Context**: story 0064c. `App\Listeners\ActivateVerifiedUser`'s constructor became `public function __construct(private readonly ActivateInactiveUser $activateInactiveUser) {}` — a real, concrete class type, kept concrete (not an interface) because `tests/Feature/Providers/EventListenerRegistrationTest.php` needs real container auto-resolution to keep working. `tests/Unit/Listeners/ActivateVerifiedUserTest.php` was rewritten around `new ActivateVerifiedUser($fake)`, where `$fake` was a standalone `ActivateInactiveUserFake` class matching the real action's `__invoke(User): bool` signature but with no `extends`/`implements` relationship to `App\Actions\Users\ActivateInactiveUser`.
- **What happened**: a full run of the 8 relevant test files came back 69/80 green, with all 11 failures concentrated in that one Unit file — including the two guard-only tests that never even reach a call to the fake.
- **Root cause**: PHP enforces a class-type constructor parameter unconditionally, before any test body runs. `new ActivateVerifiedUser($fake)` threw a `TypeError` at construction because `ActivateInactiveUserFake` was not an instance of `App\Actions\Users\ActivateInactiveUser`, so every test in the file failed for that one reason regardless of what each one actually asserted.
- **Fix applied**: `ActivateInactiveUserFake` (`tests/Unit/Listeners/ActivateVerifiedUserTest.php`) now `extends ActivateInactiveUser`, with its own constructor that deliberately does not call `parent::__construct()` (the real one needs `App\Actions\Auth\LogRefusedPrivilegedAttempt`, unavailable in `tests/Unit` — no app/database is booted there, per `tests/Pest.php`), and an overridden `__invoke()` that records the call count and emulates the real contract. No production code changed: the constructor's concrete type and `EventListenerRegistrationTest`'s need for it were both correct already.
- **How to avoid it next time**: once a constructor parameter is a real, concrete class (not an interface or callable), any test double standing in for it must satisfy that type — `extends`/`implements` the real class/interface, or a real mock of it (`Mockery::mock(RealClass::class)`, as this same file already does for `User`). A standalone class that only matches the method signature passes review but throws `TypeError` at construction, and the resulting failure looks like a mass, unrelated regression rather than what it is: one type mismatch in a test double.

## An explicit `Event::listen()` on top of Laravel 13's listener auto-discovery double-registers a listener — 2026-09-26

- **Context**: story 0064a. `AppServiceProvider::configureEventListeners()` registered `ActivateVerifiedUser` and both `RejectNonActiveUserLogin` handlers by hand, while `Application::configure()` already calls `->withEvents()` and discovers everything under `app/Listeners`.
- **What happened**: `php artisan event:list` showed `Verified` bound to `ActivateVerifiedUser` **and** `ActivateVerifiedUser@handle`, and `Authenticated` bound to `RejectNonActiveUserLogin@handleAuthenticated` twice. Nothing failed: the second run of each returned early, and `docs/security/login-status-enforcement.md` claimed discovery was off.
- **Root cause**: two registration mechanisms for one listener, and a doc that asserted the framework's behaviour instead of checking it. Only a listener that *sends* something (story 0065's notification) would have made the duplicate visible.
- **Fix applied**: the explicit lines and `configureEventListeners()` are deleted; discovery is the only mechanism. `tests/Feature/Providers/EventListenerRegistrationTest.php` reads the real dispatcher and fails on any `App\` listener bound twice or a known binding missing, and counts container resolutions per dispatch (2 before, 1 after).
- **How to avoid it next time**: never register a listener by hand; give it a public `handle*` method with a typed event. That name is load-bearing: a rename silently unregisters the listener, so add a positive binding to the registry test. Prove a double run by counting resolutions with the real dispatcher (never `Event::fake()`), because the second run's early return hides it from query counts.

## An empty last page after a delete, or a forged `?page=`, was rendered as "no records exist" — 2026-09-26

- **Context**: story 0063, `App\Livewire\BlogPosts\Index` (`app/Livewire/BlogPosts/Index.php`, `resources/views/livewire/blog-posts.blade.php`) — the first paginated list in the Blog area, with the page number bound to the URL by `WithPagination`.
- **What happened**: the review found two ways to land on a page that holds no rows although posts exist: deleting the only row on the last page (the component re-renders with the same `page` value), and a hand-edited or stale `?page=99`. The view chose between the table and the empty state with `$this->posts->count() > 0`, and `count()` is the number of rows *on this page*, so both cases showed "No blog posts have been created yet" over a list that still had posts.
- **Root cause**: the empty state was keyed off the current page's row count instead of the paginator's total, and nothing clamped a page number past the last page.
- **Fix applied**: the view now tests `$this->posts->total() > 0`, and `posts()` re-queries on the real last page (`setPage($paginator->lastPage())`) when the current page is empty, past page 1, and the total is above zero. Pinned by `tests/Feature/Blog/BlogPostsIndexTest.php`.
- **How to avoid it next time**: on any paginated list, key the empty state off `total()`, never `count()`/`isEmpty()` of the page, and clamp a page past the end to the last real page inside the query method. A list that can lose rows in place (delete, restore, a filter change) needs both. A filter change must also `resetPage()`, because `WithPagination` does not do it for an arbitrary property change. See [api/blog.md](../api/blog.md#blog-postsindex-blog-postscreate-blog-postsedit--the-fifteenth-to-seventeenth-permission-gated-routes).

## A `#[Url]`-bound property is forged input, and validating it against a capped option list rejects real ids — 2026-09-26

- **Context**: story 0063, the `category` and `tag` list filters (`#[Url(as: 'category')] public string $categoryFilter`, `#[Url(as: 'tag')] public string $tagFilter`) — the first `#[Url]` properties in this repo.
- **What happened**: a `#[Url]` property is filled from the query string on every request and is client-writable through Livewire like any public property, so it arrives as arbitrary text. The first draft sanitized it against the dropdown's own option set, which is deliberately capped (`FILTER_OPTIONS_LIMIT = 500`): a real category or tag id beyond the cap would have been reset to "no filter" as if it were forged.
- **Root cause**: the option list is a rendering convenience with a size bound; it is not the set of valid values.
- **Fix applied**: `sanitizeFilters()` asks the database (`whereKey($id)->exists()`, after an `is_string` check) and resets an unknown id to `''`; it runs in `mount()` and in each `updatedCategoryFilter()` / `updatedTagFilter()`, so both the initial URL and a later client write are covered, and the update hooks also `resetPage()`.
- **How to avoid it next time**: sanitize a `#[Url]` (or any client-written) identifier in `mount()` **and** its `updated<Property>()` hook, against the source of truth in the database and never against a capped or filtered list of choices. Unknown values fall back to the neutral "no filter" value, never a 500 and never a query built on the forged value. See [api/blog.md](../api/blog.md#blog-postsindex-blog-postscreate-blog-postsedit--the-fifteenth-to-seventeenth-permission-gated-routes).

## A UI hint disabled the button but not the keyboard, so Enter still submitted what the server would refuse — 2026-09-26

- **Context**: story 0063, the blog post editor's tag chip field (`app/Livewire/BlogPosts/Editor.php`, `resources/views/livewire/blog-posts/editor.blade.php`). An actor without `blog.create` may attach existing tags but not mint new ones; the "add" button is rendered `disabled` with a tooltip for a NEW name.
- **What happened**: the review (finding S1) showed the control was disabled but the text input still carried `wire:keydown.enter.prevent="addTypedTag"`. Pressing Enter added a chip for a name the actor may not create; the refusal only came at Save, where `FindOrCreateBlogTag`'s `AuthorizationException` is a hard 403 for the whole page and the typed form is lost.
- **Root cause**: the hint was attached to one path (the button) while the same action was reachable through another (the keyboard), and the real control lives on the server at the end of the save.
- **Fix applied**: the guard moved into the mutation itself. `addTag()` refuses a name that matches no existing tag (folded) when `canCreateTags()` is false, with a visible message, so every path (button, Enter, suggestion) goes through it. The server-side refusal is unchanged and remains the control. Pinned by `tests/Feature/Blog/BlogPostsEditorTest.php` ("an actor who cannot create tags cannot add a NEW name as a chip from the keyboard, and sees why").
- **How to avoid it next time**: a UI hint that mirrors an authorization rule belongs in the method every path calls, not only in the markup of the one control that was noticed. Disabling a button never disables `wire:keydown`, a suggestion click or a direct `wire:click` call. It stays a hint: the action's own refusal is still the control.

## Chromium drops `:00` seconds from a `datetime-local` value, so a browser test that types a zero-seconds instant reads back a different string — 2026-09-26

- **Context**: story 0063, `tests/Browser/BlogPosts/EditorJourneyTest.php` and the editor's publication date (`type="datetime-local" step="1"`, hydrated at seconds precision in `Editor::mount()` so that retitling an overdue Scheduled post resubmits the stored instant unchanged).
- **What happened**: the journey writes a scheduled post, saves it, reopens it and compares the date field with what it typed. With a value ending in `:00`, Chromium serializes the input's `.value` without the seconds, so the reopened value differs from the typed one for a reason that has nothing to do with the application.
- **Root cause**: the `datetime-local` value format omits a zero seconds part; the test's expectation assumed the string round-trips verbatim.
- **Fix applied**: the journey forces non-zero seconds into its scheduled instant (`substr($scheduledFor, 0, -2).'07'`), with a comment saying why. The component still hydrates `Y-m-d\TH:i:s`.
- **How to avoid it next time**: in a browser test that types and re-reads a `datetime-local` value, use a non-zero seconds part, or compare instants rather than strings. Keep hydrating such a field at the precision the stored value has: a minute-precision hydration would resubmit a different instant.
