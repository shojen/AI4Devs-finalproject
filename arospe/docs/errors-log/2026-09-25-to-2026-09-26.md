## An empty last page after a delete, or a forged `?page=`, was rendered as "no records exist" — 2026-09-26

- **Context**: story 0063, `App\Livewire\BlogPosts\Index` (`app/Livewire/BlogPosts/Index.php`, `resources/views/livewire/blog-posts.blade.php`) — the first paginated list in the Blog area, with the page number bound to the URL by `WithPagination`.
- **What happened**: the review found two ways to land on a page that holds no rows although posts exist: deleting the only row on the last page (the component re-renders with the same `page` value), and a hand-edited or stale `?page=99`. The view chose between the table and the empty state with `$this->posts->count() > 0`, and `count()` is the number of rows *on this page*, so both cases showed "No blog posts have been created yet" over a list that still had posts.
- **Root cause**: the empty state was keyed off the current page's row count instead of the paginator's total, and nothing clamped a page number past the last page.
- **Fix applied**: the view now tests `$this->posts->total() > 0`, and `posts()` re-queries on the real last page (`setPage($paginator->lastPage())`) when the current page is empty, past page 1, and the total is above zero. Pinned by `tests/Feature/Blog/BlogPostsIndexTest.php`.
- **How to avoid it next time**: on any paginated list, key the empty state off `total()`, never `count()`/`isEmpty()` of the page, and clamp a page past the end to the last real page inside the query method. A list that can lose rows in place (delete, restore, a filter change) needs both. A filter change must also `resetPage()`, because `WithPagination` does not do it for an arbitrary property change. See [api/blog.md](../api/blog.md#blog-postsindex-blog-postscreate-blog-postsedit--the-fifteenth-to-seventeenth-permission-gated-routes).

## A `#[Url]`-bound property is forged input, and validating it against a capped option list rejects real ids — 2026-09-26

- **Context**: story 0063, the `category` and `tag` list filters (`#[Url(as: 'category')] public string $categoryFilter`, `#[Url(as: 'tag')] public string $tagFilter`) — the first `#[Url]` properties in this repo.
- **What happened**: a `#[Url]` property is filled from the query string on every request and is client-writable through Livewire like any public property, so it arrives as arbitrary text. The first draft sanitized it against the dropdown's own option set, which is deliberately capped (`FILTER_OPTIONS_LIMIT = 500`): a real category or tag id beyond the cap would have been reset to "no filter" as if it were forged.
- **Root cause**: the option list is a rendering convenience with a size bound; it is not the set of valid values.
- **Fix applied**: `sanitizeFilters()` asks the database (`whereKey($id)->exists()`, after an `is_string` check) and resets an unknown id to `''`; it runs in `mount()` and in each `updatedCategoryFilter()` / `updatedTagFilter()`, so both the initial URL and a later client write are covered, and the update hooks also `resetPage()`.
- **How to avoid it next time**: sanitize a `#[Url]` (or any client-written) identifier in `mount()` **and** its `updated<Property>()` hook, against the source of truth in the database and never against a capped or filtered list of choices. Unknown values fall back to the neutral "no filter" value, never a 500 and never a query built on the forged value. See [api/blog.md](../api/blog.md#blog-postsindex-blog-postscreate-blog-postsedit--the-fifteenth-to-seventeenth-permission-gated-routes).

## A UI hint disabled the button but not the keyboard, so Enter still submitted what the server would refuse — 2026-09-26

- **Context**: story 0063, the blog post editor's tag chip field (`app/Livewire/BlogPosts/Editor.php`, `resources/views/livewire/blog-posts/editor.blade.php`). An actor without `blog.create` may attach existing tags but not mint new ones; the "add" button is rendered `disabled` with a tooltip for a NEW name.
- **What happened**: the review (finding S1) showed the control was disabled but the text input still carried `wire:keydown.enter.prevent="addTypedTag"`. Pressing Enter added a chip for a name the actor may not create; the refusal only came at Save, where `FindOrCreateBlogTag`'s `AuthorizationException` is a hard 403 for the whole page and the typed form is lost.
- **Root cause**: the hint was attached to one path (the button) while the same action was reachable through another (the keyboard), and the real control lives on the server at the end of the save.
- **Fix applied**: the guard moved into the mutation itself. `addTag()` refuses a name that matches no existing tag (folded) when `canCreateTags()` is false, with a visible message, so every path (button, Enter, suggestion) goes through it. The server-side refusal is unchanged and remains the control. Pinned by `tests/Feature/Blog/BlogPostsEditorTest.php` ("an actor who cannot create tags cannot add a NEW name as a chip from the keyboard, and sees why").
- **How to avoid it next time**: a UI hint that mirrors an authorization rule belongs in the method every path calls, not only in the markup of the one control that was noticed. Disabling a button never disables `wire:keydown`, a suggestion click or a direct `wire:click` call. It stays a hint: the action's own refusal is still the control.

## Chromium drops `:00` seconds from a `datetime-local` value, so a browser test that types a zero-seconds instant reads back a different string — 2026-09-26

- **Context**: story 0063, `tests/Browser/BlogPosts/EditorJourneyTest.php` and the editor's publication date (`type="datetime-local" step="1"`, hydrated at seconds precision in `Editor::mount()` so that retitling an overdue Scheduled post resubmits the stored instant unchanged).
- **What happened**: the journey writes a scheduled post, saves it, reopens it and compares the date field with what it typed. With a value ending in `:00`, Chromium serializes the input's `.value` without the seconds, so the reopened value differs from the typed one for a reason that has nothing to do with the application.
- **Root cause**: the `datetime-local` value format omits a zero seconds part; the test's expectation assumed the string round-trips verbatim.
- **Fix applied**: the journey forces non-zero seconds into its scheduled instant (`substr($scheduledFor, 0, -2).'07'`), with a comment saying why. The component still hydrates `Y-m-d\TH:i:s`.
- **How to avoid it next time**: in a browser test that types and re-reads a `datetime-local` value, use a non-zero seconds part, or compare instants rather than strings. Keep hydrating such a field at the precision the stored value has: a minute-precision hydration would resubmit a different instant.
