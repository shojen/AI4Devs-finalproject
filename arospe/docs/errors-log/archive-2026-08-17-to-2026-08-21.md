## Wrapping existing code in a `DB::transaction()` moved a cache flush nobody had written — 2026-08-21

- **Context**: task 0012 (module/sidebar access gating). Its Phase 4 audit re-read `App\Livewire\Roles\Index` because the story's cache-staleness tests exercise it, and found a Medium in code the story neither wrote nor changed. The rule it violates has been documented on this project's own security pages since task 0002 — [security/authorization-patterns.md](../security/authorization-patterns/bypass-cache-and-guards.md#flush-the-permission-cache-after-the-transaction-commits-never-inside-it), *"Flush the permission cache after the transaction commits, never inside it"* — complete with the ✅ two-flush code shape and the reason (`config/permission.php` caches the whole roles+permissions graph for 24 hours on the **shared** `database` store).
- **What happened**: `saveRole()` and `deleteRole()` shipped with the ❌ shape that page names — the permission cache flushed only *inside* their `DB::transaction()`, never after the `COMMIT`. On the shared store this fails **open** on a revocation: a concurrent request landing in the window between the in-transaction flush and the commit misses the cache, reads the pre-commit rows, and re-caches the escalated grant for 24 hours. It survived story 0010's three-round Phase 4 audit, the whole of story 0011, and a Phase 5 code review of each.
- **Root cause**: **the flush at issue was never written by this repo.** Neither method contains a flush the author chose to place; `syncPermissions()` fires one internally, and `App\Models\Role`'s `deleted` event fires the other. Both were correctly post-commit until story 0010's own Phase 4 finding F4 — an unrelated atomicity concern ("a failure between the rename and the permission sync must not leave a role persisted with the wrong set") — wrapped the existing statements in `DB::transaction()`. That wrapper relocated a side effect **with no flush line appearing, moving or disappearing anywhere in the diff**, so a reviewer grepping the change for `forgetCachedPermissions` found nothing and correctly concluded there was nothing to check. Compounding it, the regression is untestable by construction: `phpunit.xml` pins `CACHE_STORE=array`, making the permission cache per-process in tests, so the suite was 618/618 green with the window wide open — and stays 618/618 green today if either fix line is deleted.
- **Fix applied**: `app(PermissionRegistrar::class)->forgetCachedPermissions()` added immediately after each `DB::transaction()` call in [`app/Livewire/Roles/Index.php`](../../app/Livewire/Roles/Index.php) (commit `0a53acb`), each under a multi-line comment naming the finding and linking the rule — the mitigation for a fix no test can pin, matching `RolePermissionSeeder`'s identical precedent. The security page now also carries the three real call sites and the generalized ⚠️.
- **How to avoid it next time**: **adding a `DB::transaction()` around existing code is a change to every side effect that code already performed — audit each of them, including the ones the diff does not show.** Vendor calls are exactly where this bites, because their side effects are invisible at the call site: a cache flush, an event dispatch, a queued job, a broadcast, a `Storage` write, or a mail send that was outside a transaction is now inside one, and each has its own correct side of the commit. Two habits. **(a)** When a finding's remedy is a *wrapper* rather than a new statement, list what the wrapped code calls and what each of those does beyond returning — this is the cheapest form of the "[audit the remediation as new code](archive-2026-08-17-to-2026-08-21.md#two-of-the-three-security-audit-rounds-found-the-flaw-in-the-previous-rounds-fix--2026-08-19)" rule already recorded below, applied to the one shape where the diff itself hides the change. **(b)** Before writing the fix, grep `docs/security/` for the call you are about to move — the rule broken here was already written down, with the correct code, on a page the breaking story cited for other reasons. This is the third direction of the doc/code drift family this log records: [a doc outliving the feature it denied](archive-2026-07-21-to-2026-08-17.md#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13), [a doc outliving the bug it described](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), and now **code drifting away from a rule the doc still states correctly** — the only one of the three that a re-read of the doc cannot catch, because the doc is not wrong.

## A count-based assertion over rendered HTML counted a wrapper element it never meant to include — 2026-08-21

- **Context**: task 0011 (Roles & permissions UI). Its Phase 4 security audit established a rule worth keeping — that a **presence** assertion ("this permission's checkbox is still there") cannot catch a *second*, unrelated checkbox also going missing, so the regression test for "the catalog renders in full except one withheld value" must assert a **count**: rendered checkboxes == catalog size, minus exactly the withheld set. Two such tests were added to `tests/Feature/Roles/IndexUiTest.php`.
- **What happened**: both were written as `substr_count($html, 'value="')` — every `value="` attribute in the whole rendered page. Phase 5 flagged it (finding **F-4**) as correct only by coincidence: nothing *else* in the create/edit modal happens to emit that attribute today, so a future `flux:select` or hidden input would move the number with no real omission occurring. The obvious fix — scope it to the checkbox element — then walked into a second trap of its own: the Flux-rendered element is `<ui-checkbox …>`, but `flux:checkbox.group` also emits a `<ui-checkbox-group>` wrapper, whose opening tag **starts with the same string**. Counting `'<ui-checkbox'` therefore over-counts by exactly one, and does so silently: the number is off by a constant, so the test still passes or fails as a block and never looks wrong.
- **Root cause**: the assertion was designed from what the *Blade source* writes (`<flux:checkbox value="…">`) rather than from what the browser receives. Flux components are not one-to-one with their rendered output — a group renders a custom element of its own — and a substring count has no notion of element boundaries, so a child's tag name being a prefix of its parent's is invisible to it. The generic hazard is that a count assertion fails **quietly by a constant**: unlike a presence assertion, which is either satisfied or not, an over-count that is stable across runs reads as the true number and gets baked into whatever expectation makes the test green.
- **Fix applied**: both assertions rescoped to `substr_count($html, '<ui-checkbox ')` — with the **trailing space**, which is what excludes `<ui-checkbox-group` — after tracing the actual rendered markup rather than the stub (commit `48dbf54`). The expected values (`$catalogSize - 1` for a non-Super-Admin, `$catalogSize` for a Super Admin) are unchanged and were re-verified against the real render. The security rule the tests exist for is in [security/authorization-patterns.md](../security/authorization-patterns/payload-omission-and-registries.md#a-control-omitted-from-the-dom-is-safe-only-for-the-one-value-whose-guard-preserves-an-omission).
- **How to avoid it next time**: **a count assertion over rendered HTML must be scoped by a string that cannot match a sibling or wrapper element, and both the selector *and* the expected number must be read off the real rendered output before the test is trusted.** Three concrete habits. **(a)** Dump the HTML once and grep it, rather than deriving the selector from the Blade source — this repo's two 2026-08-16 Flux/Blaze entries below already establish that a Flux component's real output cannot be predicted from its stub, and the same holds for its element names. **(b)** When the selector is an element name, include the delimiter that ends it (`'<ui-checkbox '`, not `'<ui-checkbox'`); custom-element naming makes `<x>` a prefix of `<x-group>` routinely, and Flux's `*.group` components are the standing example. **(c)** Prove the count can be wrong: temporarily remove one item and confirm the number moves by exactly one. A count assertion that has never been observed changing is the same vacuous-coverage failure as [the `arch()` rule below](archive-2026-08-17-to-2026-08-21.md#a-pest-arch-rule-over-an-array-of-namespaces-shipped-green-while-proving-nothing--2026-08-18), arriving through a different door.

## Both of this project's per-change quality gates are scoped by default, and both silently passed — 2026-08-20

- **Context**: task 0010 (Roles & permissions management — backend). The story's own code was implemented, tested and merged onto `feature-entrega2-ARP`; its Phase 4 security audit and Phase 5 code review then ran against that merged state.
- **What happened**: two independent gates that [conventions/base-standards.md](../conventions/base-standards/workflow-and-quality-gates.md#quality-gates) names as mandatory reported success while the thing they exist to catch was present.
  - **The test gate.** Only the Roles-scoped tests were ever run (`php artisan test --filter=…`, which the same conventions page recommends as "the narrowest relevant test(s) first"). The **full** suite was not run once between the story's first merge and the Phase 4 re-audit — and when it finally was, `tests/Feature/Authorization/SuperAdminRoleConfigSourceOfTruthTest.php` was **red**, on a completely unrelated pre-existing test this story had broken.
  - **The formatting gate.** `vendor/bin/pint --dirty --format agent` — the exact command the conventions page mandates — reported clean while three test files carried real violations (`fully_qualified_strict_types`, `ordered_imports`). A plain `vendor/bin/pint --format agent` found them immediately. They reached Phase 5 as finding **F-1**, blocking.
- **Root cause**: the same one twice — **each gate's default scope is narrower than the change it is gating, and a narrowed gate reports "pass", not "not checked".** `--dirty` inspects only files with *uncommitted* changes, so it becomes a no-op the moment the work is committed: the more disciplined the committing, the less the gate sees. `--filter` inspects only the tests whose names match, so it can never observe a change's effect on the rest of the suite. Both are correct as *iteration* tools and both are wrong as *completion* gates, and nothing in their output distinguishes the two uses. The test failure additionally had two compounding causes, each individually invisible: story 0010's own holder-count guard applies to **every** role rather than only to the custom roles the story was about, and the developer's ambient `SUPER_ADMIN_EMAIL` provisioned a second, unaccounted-for Super Admin holder — the identical ambient-config sensitivity [the 2026-08-12 entry below](archive-2026-07-21-to-2026-08-17.md#a-test-asserted-against-a-fixture-address-that-the-local-env-also-pointed-super_admin_email-at--2026-08-12) already names, in a test written before that entry existed.
- **Fix applied**: the Pint violations were fixed by an unscoped `vendor/bin/pint --format agent` run (commit `fcff6dd`, "style(roles): fix Pint violations and correct three stale docblocks"). [`tests/Feature/Authorization/SuperAdminRoleConfigSourceOfTruthTest.php`](../../tests/Feature/Authorization/SuperAdminRoleConfigSourceOfTruthTest.php) gained `config(['auth.super_admin.email' => null]);` in its `beforeEach` (matching what `tests/Feature/Seeders/DatabaseSeederTest.php` already did) and an explicit `removeRole()` before the deletion its scenario is actually about, each with a comment naming the cause. [conventions/base-standards.md](../conventions/base-standards/workflow-and-quality-gates.md#quality-gates) now distinguishes the iteration form of each gate from the completion form.
- **How to avoid it next time**: **a gate that takes a scope argument must be run twice — narrow while iterating, and unscoped before the work is declared done — and "the narrow run passed" is never evidence about anything outside its scope.** Concretely, before a story leaves Phase 3: run `vendor/bin/pint --format agent` (no `--dirty`) and `php artisan test` (no `--filter`), in that order, and treat those two runs — not the filtered ones — as the record. Two corollaries. **(a) `--dirty` is inversely coupled to commit hygiene**, so it fails hardest exactly when the workflow is being followed best; never let it be the last formatting check on a committed branch. **(b) A guard that a story adds "for its own feature" almost never applies only to that feature.** `guardAgainstHolders()` was specified as part of the roles-CRUD story and reads as scoped to it, but it is a model-event listener on `App\Models\Role` and therefore binds every role in every test in the repo. When a story registers a model event, an observer, a global scope, or middleware, the blast radius is the whole suite by construction — that alone is sufficient reason to run it.

## A planned test asserted a refusal by `verified`, a middleware that refuses nobody in this app — 2026-08-20

- **Context**: task 0040, moving `users.index` out of `routes/web.php` into its own `routes/users.php`. Phase 1's QA contribution specified one new test to guard the relocation: an unverified user hitting `route('users.index')` should be redirected to `route('verification.notice')`, so that hand-copying the `Route::middleware(['auth', 'verified'])->group(...)` block into a new file could not silently drop `verified`.
- **What happened**: Phase 3's red-test step wrote that test and it did not behave as a red test at all. Proven mechanically rather than argued: with `verified` temporarily removed from the new file's group entirely, the test's outcome was **bitwise identical** to the unmodified group — same 403 from `can:users.view`, same message. The assertion it was built on could never distinguish a correct relocation from one that had lost `verified`, so it was reverted rather than kept, and this story shipped with no new test at all.
- **Root cause**: `App\Models\User` does not implement `Illuminate\Contracts\Auth\MustVerifyEmail` — the import sits commented out at the top of [`app/Models/User.php`](../../app/Models/User.php) — and Laravel's stock `EnsureEmailIsVerified` only acts when `$request->user() instanceof MustVerifyEmail`. That condition is `false` for every actor in this app, so `verified` is a **structural no-op on every route that carries it**; account usability is enforced at sign-in through `users.status` instead. None of that was newly discovered here: [architecture/authentication.md](../architecture/authentication/features-registration-and-status.md#account-status-and-activation) has stated it in one plain sentence since task 0007. The test was designed from the middleware's *name* and from the route group's *appearance*, and nobody opened the doc that already answered the question.
- **Fix applied**: no code change — the test was reverted and the story's "Tests to perform" section rewritten with a Phase 3 correction note recording why the case was dropped rather than left as dead coverage (`ai-spec/tasks/.../0040-move-users-route-to-own-file.md`). The four pre-existing HTTP-level tests in `tests/Feature/Users/IndexTest.php` (guest → login redirect, no permission → 403, permission → 200, Super Admin bypass → 200) already cover every outcome that actually holds, and re-running them unmodified *is* the regression check for a pure relocation.
- **How to avoid it next time**: **before writing a test that asserts a middleware refuses someone, confirm that middleware can refuse anyone in this app — a middleware being present on a route is not evidence that it is live.** The cheap proof is the one Phase 3 ran: delete the middleware, re-run the test, and see whether the outcome changes; if it does not, the test carries no signal no matter which way it is written. `verified` is the known dead one here and will stay dead until `User` implements `MustVerifyEmail`, so any future story that copies an `auth` + `verified` group into a new area file — task 0010's `routes/roles.php` is the next one — must not plan a `verified` test either. This is the same class as the vacuous `arch()` rule two entries below (an assertion that cannot fail is not coverage); the added angle is that the control under test may not exist at all, and that the answer was already written down in the doc that owns it — check [architecture/authentication.md](../architecture/authentication.md) before designing an auth-middleware test case.

## A guard took the state it was guarding as a parameter, reopening its own hole one level up — 2026-08-20

- **Context**: task 0009, `App\Actions\Roles\EnforceAdministratorPermissionGrant` — the action that refuses a role-save payload newly granting `roles.manage-administrators` to anyone but the Super Admin. Three Phase 4 audit rounds; each round's findings were against the **previous round's fix**, not against the original implementation.
- **What happened**: round 1 found F1 — the guard only asked whether the submitted payload *contained* the protected permission. Since `Role::syncPermissions()` replaces a role's entire permission set, and story 0011's toggle is never rendered to a non-Super-Admin at all, a broad administrator editing an unrelated field on a role that legitimately held the permission submitted a payload **omitting** it, silently revoking a Super Admin's grant. The fix introduced a "before" snapshot so the action could diff. Round 2 then failed that fix: the snapshot arrived as a caller-supplied `array $currentPermissionNames` parameter (N2 — a caller asserting an untrue "before" makes a new grant look pre-existing), the two snapshots were normalised asymmetrically so the diff silently mismatched (N3), and the membership check did not flatten nested arrays/Collections the way `syncPermissions()`'s own vendor code does, proven live to bypass the guard entirely (N1). Round 3 passed, after one more: the replacement `?Role $role` parameter had shipped with a `= null` default, so a forgotten third argument at a future call site would silently mean "nothing is currently granted" (NR1).
- **Root cause**: two, compounding. (1) **The guard trusted its caller for the very state it existed to protect.** "What does this role currently hold" is the input the whole decision turns on; accepting it as a parameter makes the guard only as strong as every present and future call site. (2) **Each fix was reviewed against the finding it answered rather than as new code with its own attack surface** — the diff logic was read as "does this close F1?", and it did, so nobody asked where its *new* inputs came from. F1 itself had a third root cause worth naming separately: nothing in the payload distinguishes "the actor chose to remove this" from "the actor was never shown this", and a full-replace `sync*()` collapses the two.
- **Fix applied**: the `array $currentPermissionNames` parameter was replaced by `?Role $role` (nullable, **no default**), and [`app/Actions/Roles/EnforceAdministratorPermissionGrant.php`](../../app/Actions/Roles/EnforceAdministratorPermissionGrant.php) now loads the "before" state itself with `$role->load('permissions')` — removing N2 and N3 structurally rather than validating around them. `normalizeNames()` applies the identical `Collection::make(...)->flatten()` pass `HasPermissions::collectPermissions()` uses, so no shape can be invisible to the check while still being honoured by the sync. F1's own resolution — *preserve* an omitted-but-already-granted permission rather than deny the request — was **not** derivable from the spec, and was decided by the human mid-audit (asked explicitly, chose preserve); the choice is recorded in the code's docblock, in [architecture/authorization.md](../architecture/authorization/grant-meta-rules-and-ui-hints.md#who-may-grant-a-permission--the-meta-rule-layer), and in the task file's implementation record. Both durable rules are in [security/authorization-patterns.md](../security/authorization-patterns/ability-coverage-and-guards.md#a-full-set-sync-behind-a-partially-visible-form-must-preserve-what-the-actor-cannot-see).
- **How to avoid it next time**: three concrete rules. **(1) A guard must derive the state it guards, never accept it** — take the model and read it (`load()`, not `loadMissing()`), and treat any "current state" parameter in an authorization signature as the finding itself. **(2) The "audit the remediation as new code" rule from the entry below is not a one-off — it is now the observed norm.** Two consecutive stories have needed three Phase 4 rounds, each catching the previous round's own fix, so budget for the extra rounds rather than treating round 2 as a formality. What this story adds to it: the highest-risk remediation is one that introduces a **new input** (a parameter, a snapshot, a cache), because that input's provenance was never in scope for the original review. **(3) When a full-replace `sync*()` is driven by a form that shows the actor only part of the set, absence is not a decision** — diff both directions and authorize adding and removing separately, and when "preserve" versus "deny" is a product judgement rather than a security one, stop and ask the human instead of picking; an unrecorded choice reads as an oversight to the next auditor.

## A security page documented the vulnerable code as current, because it was written before its own fix — 2026-08-20

- **Context**: task 0016 (the `sales_regions` catalog). Phase 4's `appsec-auditor` wrote a new section into [security/seeder-safety.md](../security/seeder-safety.md#a-catalog-seeder-must-fail-loudly-rather-than-commit-a-structurally-invalid-catalog) — "A catalog seeder must fail loudly rather than commit a structurally invalid catalog" — quoting the two fail-open shapes it had just found in `SalesRegionSeeder`: `'parent_id' => $spain?->id`, and a repair `update()` whose zero-row outcome went unchecked.
- **What happened**: those findings were fixed later in the same story (both lookups now `throw_if(...)`), but the page was not revisited. It shipped stating *"Two shapes to look for, both present in `SalesRegionSeeder` today"* above a verbatim quote of code that no longer existed, described as accepted low risk. Phase 5's `code-reviewer` caught it as finding F-1. A reader following the page's own citation to `database/seeders/SalesRegionSeeder.php` would have found neither the `?->` nor the unchecked `update()` there.
- **Root cause**: the security pages are authored **during** Phase 4, from the auditor's vantage point, where the vulnerable shape genuinely *is* the current code — so the present tense is accurate at the moment it is written and silently false by the time the story closes. Nothing in the workflow re-reads a Phase 4 page after Phase 5's fixes land: the change→doc mapping routes Phase 6 to the docs describing *the story's* change, and this page had already been written, so it read as done. The failure is invisible in review because the page is internally coherent — only opening the cited file disproves it.
- **Fix applied**: the section was rewritten as an explicit ❌ before / ✅ after pair — the pre-fix shape labelled as no longer in the repo, the shipped `throw_if(...)` guards quoted from the real file, plus the third guard (`assertValidCountryFixture()`) the same audit added. The underlying rule was correct and is unchanged.
- **How to avoid it next time**: **a security page written during Phase 4 documents a state that Phase 5 is expected to change, so Phase 6 must re-verify every code quote in it against the file it cites — treat an audit-authored page as unsynced by default, not as already done.** Two concrete habits: write a vulnerability write-up as a ❌/✅ pair from the start, so the fix has a slot waiting for it instead of needing the framing sentence rewritten; and never describe a *found* finding in the present tense ("both present today") — say "as found" and name the state it is in now. This is the [bare-negative-claim entry](archive-2026-07-21-to-2026-08-17.md#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13)'s failure class arriving from the opposite direction: there a doc outlived the feature it denied, here a doc outlived the bug it described.

## Two of the three security-audit rounds found the flaw in the *previous* round's fix — 2026-08-19

- **Context**: task 0008a, which relocated the Administrator-tier authorization out of `App\Livewire\Users\Index` and into [`App\Actions\Users\CreateUser`](../../app/Actions/Users/CreateUser.php) / [`UpdateUser`](../../app/Actions/Users/UpdateUser.php). Phase 3 implemented the Phase 1 spec exactly, and the full suite was green.
- **What happened**: Phase 4 took **three** rounds to reach PASS, and the second round's findings were all against code the *first* round had just written. Round 1 found that the relocation was partial — the guard covered the Administrator tier, but assigning the **Super Admin** role through either action was completely ungated, and a name-only `UpdateUser` edit reached `$user->save()` with no authorization at all (F1). Round 2 then found two Mediums in F1's own fix: the new `Gate::authorize('update', $user)` ran *above* the `roles` reload that had been added for a different finding, so a caller passing a stale `->with('roles')`-hydrated instance could evade `UserPolicy::update()`'s Super Admin-target exclusion (N1); and the new Super Admin refusal checked only the **submitted** role, never whether the target *currently held* Super Admin — so a Super Admin actor, whose `Gate::before` bypass makes any `Gate`-mediated check moot, could demote another Super Admin through `syncRoles()` (N2). Only round 3 passed.
- **Root cause**: three compounding causes, none of them carelessness. **(1) A relocation is scoped by what moved, not by what the destination now owns.** The spec said "move the Administrator guard", so the Administrator guard moved — and nobody asked what *else* an action that now owns its own authorization is responsible for. The Super Admin tier had never been the component's job, so it was nobody's. **(2) A fix is new code, written under the framing of the finding it answers, and inherits none of the original review.** N1's reload existed and was correct; it was added to answer "read the whole roles collection, not an unordered `first()`", so its *placement* was chosen for that question and never re-examined against the `Gate` call sitting above it. **(3) Both new flaws fail open and silently.** A stale relation is indistinguishable from a role the target genuinely does not hold, and a `Gate`-mediated refusal reads as a refusal in every test whose actor is not a Super Admin.
- **Fix applied**: `Role::isSuperAdminRoleRow()` added as the row-shaped counterpart to `isAdministratorRole()`; both actions now `Gate::authorize()` the whole operation and refuse the Super Admin tier by **direct throw** rather than through `Gate`; `UpdateUser` refuses a target that currently holds Super Admin as well as a submission that assigns it, moves `$user->load('roles')` to the literal first statement of `__invoke()`, compares status against `getRawOriginal()`, and wraps its writes in `DB::transaction()`. The two durable rules are written up in [security/authorization-patterns.md](../security/authorization-patterns/ability-coverage-and-guards.md#a-rule-that-must-bind-a-super-admin-actor-must-be-a-direct-throw-not-a-gate-check) and [the section below it](../security/authorization-patterns/ability-coverage-and-guards.md#authorization-that-consults-a-relation-must-reload-it-before-the-first-check-reads-it); the shipped placement is documented in [architecture/authorization.md](../architecture/authorization/administrator-tier.md#the-guard-belongs-to-the-action-not-to-the-caller).
- **How to avoid it next time**: **re-audit a security fix as new code, not as a diff against a finding — and keep re-auditing until a round finds nothing.** A round that only re-tests the reported finding will confirm the fix and miss what the fix introduced; budget for the extra rounds rather than treating round 2 as a formality. Two concrete checks that would each have caught a finding here on the first pass. **(a) When a guard moves into a class, enumerate every privileged value that class can now write — not only the one the story is about.** "Which role can this action assign?" has three answers here (ordinary, Administrator, Super Admin) and the story's title only named one. **(b) For every authorization check, name the statement that last wrote the state it reads, and confirm it runs above it.** Relation hydration, `getOriginal()` vs `getRawOriginal()`, and an in-memory attribute a caller may have pre-staged are all state a check silently trusts; ordering is part of the guard, not an implementation detail. See also the `getPrevious()`-not-`getOriginal()` entry below — the same class of "which source is this reading, and when?" mistake, from a third direction.

## A Pest `arch()` rule over an array of namespaces shipped green while proving nothing — 2026-08-18

- **Context**: task 0008. The story's central invariant is that `App\Models\Role` is the *only* role model class application code may use — a direct `Spatie\Permission\Models\Role` import reaches the same `roles` table carrying none of the Super Admin guards, so it is a live bypass. That invariant was to be enforced by an architecture test rather than by convention, covering the two PSR-4 roots the story touches (`App` and `Database\Seeders`).
- **What happened**: the obvious form shipped first — `expect(['App', 'Database\Seeders'])->not->toUse(Role::class)` — and it passed. It would have gone on passing if `Database\Seeders` alone had imported the raw Spatie model, which is exactly the regression the test exists to catch. A test whose whole job is to fail on a specific import was structurally incapable of failing on half its stated scope.
- **Root cause**: Pest's `expect(array $targets)` evaluates the rule **disjunctively** across the given targets — it is satisfied as soon as *any one* target passes, not when all of them do. Nothing in the API signals this; an array of namespaces reads as "apply this rule to each of these". Verified against the real repo rather than reasoned about: `expect(['App', 'Database\Seeders'])->not->toUse(Gate::class)` passes today even though `Gate` **is** imported in `app/Livewire/Users/Index.php` — `Database\Seeders` doesn't import it, and that one satisfied target carries the whole assertion.
- **Fix applied**: split into two separate single-namespace rules in [`tests/Unit/ArchitectureTest.php`](../../tests/Unit/ArchitectureTest.php), one per PSR-4 root, with the counter-example above recorded in the file as a comment so nobody re-merges them. The convention it enforces is documented in [architecture/authorization.md](../architecture/authorization/super-admin.md#one-role-model-class-in-application-code).
- **How to avoid it next time**: **write one `arch()` rule per namespace — never pass an array of targets to `expect()` — and prove every architecture test can actually fail before trusting it.** A `->not->toUse()` assertion is a *negative* claim, so it is green both when the invariant holds and when the test is vacuous, and nothing in the output distinguishes the two. The proof is cheap and takes one run: temporarily add the forbidden import to a file in each namespace the rule claims to cover, confirm the test goes red for *each* one separately, then revert — the same regression-proof discipline this project already applies to browser tests (see [testing/frontend/README.md](../testing/frontend/README.md)). This generalises past `arch()`: any assertion that passes by default deserves a deliberate failure before it is counted as coverage.

## A listener read the pre-save value with `getOriginal()`, which `save()` had already overwritten — 2026-08-17

- **Context**: task 0007 Phase 4 (`appsec-auditor`). The story turned `users.status` from a badge label into an access-control state, which made [`App\Listeners\ActivateVerifiedUser`](../../app/Listeners/ActivateVerifiedUser.php) — the single `Inactive` → `Active` transition — a privilege-granting control for the first time. Its only guard was `$user->status !== UserStatus::Inactive`, and both the listener and [architecture/authentication.md](../architecture/authentication/features-registration-and-status.md#account-status-and-activation) described that guard as what "stops a verification from silently undoing an administrator's suspension".
- **What happened**: two mistakes, one on top of the other. First, the guard was written against the wrong half of the problem: it does cover `Suspended`, but `Inactive` is *also* a state an administrator sets deliberately from the Users editor, and for that state the condition is not a guard — it is the trigger. Since `App\Actions\Users\ConfirmEmailChange` fires `Verified` from the deliberately session-less `email-change.confirm` route, a deactivated user could reactivate themselves with nothing but a 60-minute-old pending-email link (verified by execution: `BEFORE: status=inactive` → `AFTER: status=active`). Second, the audit's own first fix — `is_null($user->getOriginal('email_verified_at'))` — was **wrong**, and only broke `EmailVerificationTest` and `PasswordResetTest` once it was actually run; reading it, it looks obviously correct.
- **Root cause**: `Model::save()` ends in `finishSave()`, which calls `syncOriginal()` unconditionally after *every* successful save. Every caller that fires `Verified` writes `email_verified_at` and calls `save()` before firing the event on that same instance, so by the time the listener runs, `getOriginal()` already holds the value that was just written. A `getOriginal()`-based guard therefore always finds a non-null "original" and refuses every legitimate first verification — it fails closed, which is why it produced test failures rather than a security hole, but it would have silently disabled activation entirely. What does survive is `$this->previous`, populated by `syncChanges()` from inside `performUpdate()` *before* `finishSave()` runs, and read with `getPrevious()`.
- **Fix applied**: `ActivateVerifiedUser` now requires the user to have *never* been verified, read from `getPrevious()` and failing closed when the key is absent. Both producers — [`app/Actions/Fortify/ResetUserPassword.php`](../../app/Actions/Fortify/ResetUserPassword.php) and [`app/Actions/Users/ConfirmEmailChange.php`](../../app/Actions/Users/ConfirmEmailChange.php) — carry a comment recording that their `save()` must remain the last dirty write before the event. The full rule and its four constraints are in [security/login-status-enforcement.md](../security/login-status-enforcement.md#status-is-now-an-access-control-state--every-inactive--active-transition-is-a-privilege-grant).
- **How to avoid it next time**: two rules, both concrete. **(1) In a listener or observer that runs after `save()`, the pre-change value is `getPrevious()`, never `getOriginal()`** — `getOriginal()` means "as of the last sync", and a successful save *is* a sync. It comes with constraints worth checking before relying on it: it only carries attributes that were dirty on the last save (so `array_key_exists()` first and fail closed), `syncChanges()` replaces it wholesale on each dirty save, `performInsert()` never populates it, and a `ShouldQueue` listener loses it entirely because `SerializesModels` re-fetches the model. **(2) When a column stops being descriptive and starts denying access, re-audit every write to it as a privilege grant** — including the ones that were reviewed and approved while it was still cosmetic. Ask what the state *denies* and who can undo it, not what it is called; a single enum case carrying two meanings ("never proved their mailbox" and "an administrator turned this off") cannot be guarded by testing the case alone.

## A task file's relative links broke silently when it moved to `in-progress/`/`done/` — 2026-08-17

- **Context**: reviewing `ai-spec/tasks/done/0006-users-list-editor-ui.md` after closure, following up on a user-reported broken link: `[PRD Epic 1](../../docs/PRD/PRD.md#epic-1--users-roles--permissions)`.
- **What happened**: the link's anchor fragment was correct (`docs/PRD/PRD.md`'s own generated table of contents uses the identical `#epic-1--users-roles--permissions` slug), but the path resolved to `ai-spec/docs/PRD/PRD.md` — a file that doesn't exist. Auditing every other `done/` task file for the same `](../../docs/...)` pattern found the identical break in five more: `0002`, `0003`, `0004`, `0005`, and `0006b` (20 broken links in `0006b` alone).
- **Root cause**: a task file's relative links are written once, at Phase 1, from `./ai-spec/tasks/<file>.md` — two directory levels below the repo root, so `../../docs/...` correctly reaches `docs/`. Phase 3 step 0 and Phase 7 then move the file to `./ai-spec/tasks/in-progress/<file>.md` or `./ai-spec/tasks/done/<file>.md` — **three** levels below the repo root — without anyone revisiting the links already written inside it. `../../docs/...` now resolves one directory too shallow. Nothing in the move itself surfaces this: `git mv`/a plain file move changes only the file's location, never its content, so the broken link sits silently until someone actually clicks it.
- **Fix applied**: `sed 's#\.\./\.\./docs/#../../../docs/#g'` across the six affected files in `ai-spec/tasks/done/`, verified afterward by resolving every `](...)` target in each file against the filesystem from the file's real (post-move) location. `docs/workflow.md` now documents this as a mandatory step — see its new [Link-integrity check on every stage move](../workflow/task-files-links-and-ordering.md#link-integrity-check-on-every-stage-move) section, cross-referenced from Phase 3 step 0 and Phase 7.
- **How to avoid it next time**: **a file move that changes directory depth invalidates every relative link the file contains, even though nothing about the move touches the file's content.** Whenever `product-owner` moves a task file between `./ai-spec/tasks/`, `in-progress/`, and `done/` (a depth change from two to three directory levels), `docs-keeper` must re-resolve every relative link in the moved file — the path against the filesystem, and any `#fragment` against a real heading in the target — before considering the move complete. The same check applies to any other file this project ever moves between directories at different depths, not just task files.
