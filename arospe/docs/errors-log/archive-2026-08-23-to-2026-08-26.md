## Two `@directive(...)` calls in one Blade component tag's attribute string silently fail to compile — 2026-08-26

- **Context**: story 0018 (Sales Regions UI), Phase 5 code review finding N8 — a non-blocking "pick one, `@js()` matches `users.blade.php`" style nit against three `wire:click="setActive({{ \Illuminate\Support\Js::from(...) }}, {{ \Illuminate\Support\Js::from(...) }}, '')"` calls on `<flux:switch>` row controls, converted to `wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')"` for consistency with the file's other single-argument `@js()` calls (`openEditModal(@js(...))`, `setDefault(@js(...))`).
- **What happened**: every row's active/inactive toggle switch became a silent no-op — no PHP error, no JavaScript console error, no failed HTTP request. `Livewire::test(Index::class)->call('setActive', ...)` (direct component call) worked correctly, so the story's own component-level Feature tests never caught it; only a browser test asserting a *rendered outcome* after a real click did, and even that took several rounds to isolate because every earlier symptom (a stale count, an unchanged `is_active`) looked exactly like ordinary async/timing flakiness — the same failure shape this repo has genuinely hit before (see the `->waitForEvent('networkidle')` entries below). Dumping the real compiled HTML settled it: `wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')"` rendered **byte-for-byte as written**, `@js(...)` completely unprocessed, so Livewire tried to parse a JavaScript-illegal action-call string and dropped it.
- **Root cause — as recorded at the time, and now known to be wrong; see the correction below**: minimally reproduced outside this story's own markup — `<x-button wire:click="foo(@js($id), @js($flag))" />` against a trivial `<button {{ $attributes }}>` component renders the attribute unprocessed, verified via `Blade::render()`. The conclusion drawn was: *a single `@directive(...)` call inside a Blade component tag's plain attribute string compiles correctly; two of them in the same attribute value do not*, attributed to `ComponentTagCompiler::getAttributesFromAttributeString()` regex-scanning the raw attribute string before the general compiler pass runs. That framing also required a carve-out for this repo's own `x-show="matchesFilter(@js(...), @js(...))"` on a `<flux:table.row>`, which has two and works — and the carve-out was a hedge ("not a value fed into the component tag's own attribute list the same way") rather than a mechanism, which is the tell. **What is not in doubt, and is the whole practical content of this entry:** the conversion really did make every row toggle a silent no-op in a real browser, reverting to `{{ \Illuminate\Support\Js::from(...) }}` really did fix it, and a `{{ }}` echo compiles in every shape tested.
- **Fix applied**: reverted the three converted `wire:click="setActive(...)"` attributes in [`resources/views/livewire/sales-regions.blade.php`](../../resources/views/livewire/sales-regions.blade.php) to `{{ \Illuminate\Support\Js::from(...) }}` (the pre-existing, proven-correct form), each with an inline comment recording the finding so a future pass doesn't "fix" them back to `@js()` for consistency a second time. `openEditModal(@js(...))` and `setDefault(@js(...))` — each carrying exactly **one** `@js()` call — were left unchanged; they were never the problem.
- **How to avoid it next time**: **prefer `{{ }}` echo expressions over `@directive(...)` calls for any dynamic value inside a Blade *component tag* attribute** (`<x-foo attr="...">`, `<flux:foo attr="...">`) — the correction below narrows *why* (the count is not the discriminator, and an anonymous `<x-…>` tag is the shape that provably breaks), but the safe form is unchanged and is what the repo ships. Use `{{ }}` echo expressions instead when more than one dynamic value must land in the same attribute string (`{{ \Illuminate\Support\Js::from($a) }}, {{ \Illuminate\Support\Js::from($b) }}` is the safe, already-idiomatic form here), or split the attribute across `:wire:click="..."` colon-bound dynamic syntax if the whole value is a single PHP expression. A "pick one style for consistency" cleanup on a component-tag attribute is not risk-free — verify the compiled HTML output (not just the absence of a PHP/console error) before trusting it, exactly as [the entry above](#a-verification-record-that-lists-two-of-three-quality-gates-is-a-record-of-two-gates--2026-08-26) already argues for the quality gates: a passing component-level test here proved nothing, because `Livewire::test()->call(...)` never goes through the compiled Blade view's `wire:click` attribute at all.

> **Correction — 2026-08-26, same day, during story 0018's Phase 6 docs pass.** This entry was verified before being carried forward, per this log's own [re-verify-what-a-story-wrote-about-itself rule](archive-2026-08-17-to-2026-08-21.md#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), and **the stated rule does not reproduce — in either direction.** Executed against `HEAD` in this project's own container, twice over: once through `Blade::render()` and once through the **real file-view compilation path** (a throwaway view registered with `View::addNamespace()`, so the `ComponentTagCompiler` + cached-compile route the app actually uses, not just the string compiler).
>
> | Shape | Result |
> | --- | --- |
> | `<flux:switch wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')" />` — **the exact shipped expression**, two `@js()`, array subscripts, leading `!` | **compiles**, both paths → `wire:click="setActive('ID1', true, '')"` |
> | `<flux:button wire:click="openEditModal(@js($region['id']))" />` — one `@js()` | compiles, both paths |
> | `<flux:table.row x-show="matchesFilter(@js(...), @js(...))" />` — the "carve-out" | compiles; **needed no carve-out** |
> | `<x-placeholder-pattern wire:click="foo(@js($a))" />` — an anonymous `x-` component, **one** `@js()` | **UNCOMPILED**, literal `@js(...)` in the output |
> | `<x-app-logo wire:click="foo(@js($a), @js($b))" />` — anonymous, two | UNCOMPILED |
> | any of the above with `{{ \Illuminate\Support\Js::from(...) }}` | compiles, every time |
>
> So the count is not the discriminator; the *component* is. A `flux:` tag compiles `@js()` at any count, and a plain anonymous `<x-…>` tag compiles it at **no** count. Neither half of "one is fine, two are not" survives, and the hedge about `x-show` was explaining something that never needed explaining. **What made the shipped screen go dead is therefore not established**, and it is deliberately not being guessed at here — the broken state was never committed (the Phase 5 commit contains the comment and the already-reverted markup, so `git show` cannot reconstruct it), and this project's own [hedge rule](#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24) says an unverified mechanism written up confidently is worse than an open question written up plainly.
>
> **What survives unchanged, and is what to act on:** the incident, the symptom (a silent no-op with no PHP error, no console error and no failed request), the fix, and the two rules in the bullet above — prefer `{{ }}` echoes for dynamic values in a component-tag attribute, and **verify the compiled output rather than the absence of an error** before trusting any attribute-syntax cleanup. Add one: **`@js()` inside an anonymous `<x-…>` component's attribute is broken outright** — that half *is* now verified by execution, at any count, and it is the shape the original minimal repro actually hit.

## A verification record that lists two of three quality gates is a record of two gates — 2026-08-26

- **Context**: story 0017 (Sales Region tax configuration backend). [conventions/base-standards.md](../conventions/base-standards/workflow-and-quality-gates.md#quality-gates) names three gates every PHP change passes, in order: `php artisan test`, `vendor/bin/pint`, and **Larastan level 7** (`phpstan.neon`, over `app/`, `bootstrap/app.php`, `config/`, `database/`, `routes/`). The story ran three separate, explicitly-recorded verification passes before review — the Phase 3 reconciliation, the Phase 4 fix, and the Phase 4 re-audit round 2 — each ending in a written line of the form *"full suite re-run unscoped: N/N passed; `pint --test --format agent` (unscoped): passed"*.
- **What happened**: **gate 3 was never run.** Not run-and-passed, not run-and-deferred — absent from all three records, and nobody noticed across two `appsec-auditor` rounds and the story author's own re-verification. `code-reviewer` ran it for the first time at Phase 5 and it **failed**: two errors, both in `App\Livewire\SalesRegions\Index::save()`, where `SalesRegion::find($replacementDefaultId)` widens to `SalesRegion|Collection|null` because `Model::find()` accepts an array-ish key and `$replacementDefaultId` came straight out of `$validated[...]` as `mixed`. Real, shipped code, three phases past implementation, in the method the whole story is about.
- **Root cause**: **the record was of what was run, and it was read as a record of what passed.** Two gates reported green, the sentence describing them was long and specific and quantified (`869/869 passed, 2434 assertions`), and a specific, confident record is exactly what stops a reader asking what is *not* in it. Two things made it survivable for so long. The two gates that were run are the two with **loud, immediate, per-file feedback loops** — the ones a developer reaches for while iterating anyway — while Larastan is the one nothing else prompts you to run. And the missing gate is not silent forever: `.github/workflows/tests.yml` runs `composer types:check`, so CI would have failed this eventually. That is the mitigation, not the excuse — it means the omission cost a late catch rather than a shipped bug, and it also means nobody could have inferred the gap from a green local run, because there is no green local run to inspect.
- **Fix applied**: every value read out of `$validated` in `Index::save()` is now narrowed to `(string)` at the point of use, matching `App\Livewire\Users\Index::save()`'s own existing convention for the same read; re-run clean (commit `df377d0`). The story's Phase 5 section records the first clean Larastan run it ever had.
- **How to avoid it next time**: **a verification record must name all three gates and the result of each, including "not run" — a gate absent from the record is a gate that did not run, and should be read that way by whoever reads it next.** Concretely, the closing line of any phase that claims verification is three clauses, never two:

  ```bash
  php artisan test                    # unscoped — not --filter
  vendor/bin/pint --format agent      # unscoped — not --dirty
  vendor/bin/phpstan analyse          # level 7, per phpstan.neon — the one nothing else reminds you of
  ```

  Three notes on why this is a *different* entry from [the scoped-gates one below](archive-2026-08-17-to-2026-08-21.md#both-of-this-projects-per-change-quality-gates-are-scoped-by-default-and-both-silently-passed--2026-08-20) rather than a restatement of it. **(a)** That entry is about a gate that **ran** and reported "pass" while looking at almost nothing; this one is about a gate that never ran at all, which no amount of widening a `--filter` or dropping a `--dirty` would have caught. **(b)** It generalises past this repo's three commands: **an omission is invisible in a record of positives.** A phase that lists what it did, however precisely, carries no information about what it skipped — so any checklist worth having is enumerated by the checklist, not reconstructed from the report. **(c)** The rule binds a *reviewer* as much as an author: `code-reviewer`'s Phase 5 opening move should be to diff the phases' verification records against the three-gate list, which is the cheapest check in this whole workflow and the one that found this.
## A missing `.env.testing` file let a self-healing `migrate:fresh` wipe the shared dev database — 2026-08-26

- **Context**: no story — routine iteration on the full Pest suite from two separate Claude Code sessions on 2026-08-24, one running `./vendor/bin/sail artisan test` directly and one dispatching a `backend-expert`/`backend-qa` pair to run "revert-checks + full suite".
- **What happened**: the first session's suite run failed with `deleted_at column not found`, diagnosed (reasonably, on the symptom alone) as "the test database is in a corrupted state from a previous concurrent run". It ran `./vendor/bin/sail artisan migrate:fresh --env=testing --force` to reset it — and that command dropped and recreated all 16 tables in the **real development database**, `arospe`, not a testing one. `information_schema.TABLES` showed the table-creation timestamps land in an identical 4-second window twice more that same day (07:29 and again at 23:43, the second during the background suite-run agent's own work), each time wiping whatever had accumulated since — roles, permissions, the sales-region catalog, and every user, including the self-registered account created in between. Nobody noticed until a later session opened the app against an empty `arospe` two days later.
- **Root cause**: this repo's `phpunit.xml` sets `DB_DATABASE=testing`, but that `<env>` block only takes effect when Pest/PHPUnit itself boots the framework — it does nothing for a bare `artisan` command. Laravel's `--env=testing` flag makes `LoadEnvironmentVariables` look for a `.env.testing` file; when none exists (this project never had one), it silently falls back to loading the plain `.env`, whose `DB_DATABASE` is `arospe`. So `--env=testing` looked like the correct, safety-conscious way to reset "the test database" and was in fact indistinguishable from omitting the flag entirely. The agent's self-diagnosis ("the DB is corrupted, let me refresh it") was a reasonable read of the symptom and is not the mistake — the mistake is that the command it reached for to fix that had no guardrail stopping it from targeting production-adjacent data.
- **Fix applied**: created `.env.testing` (gitignored, one per checkout — see `.gitignore`) pointing `DB_DATABASE=testing` at a dedicated database, verified by re-running the exact failing command (`migrate:fresh --env=testing --force`) and confirming it now creates tables in `testing` while `arospe` is untouched. Restored `arospe` with `php artisan db:seed` (roles, the 38-permission catalog, the sales-region catalog, and the Super Admin grant). Documented the per-checkout requirement, and the further requirement that **each `git worktree` needs its own database name** (`testing1`, `testing2`, …) since all worktrees share one MySQL container, in [testing/worktree-databases.md](../testing/worktree-databases.md).
- **How to avoid it next time**: **a database-flag whose safety depends on a file that might not exist is not a guardrail — verify the fallback path, not just the happy path, before trusting a `--env=` / `--database=` flag to isolate anything.** For this specific gap: never run `artisan migrate:fresh` (or any other destructive artisan command) against `--env=testing` without first confirming `.env.testing` exists and points somewhere other than the shared dev database — `cat .env.testing | grep DB_DATABASE` before the destructive command, not after. Two corollaries for anyone opening a new worktree: read [testing/worktree-databases.md](../testing/worktree-databases.md) before running tests there, and if a suite run ever fails with a symptom that looks like "the schema is stale/corrupted", treat that as a signal to check *which* database actually received the last `migrate:fresh` before running another one — the diagnosis in this incident was right, but nobody checked which database the fix would land on.

## A scope exclusion named screens while the story edited a class those screens share — 2026-08-24

- **Context**: story 0015b, adding a structured `Log::warning` line to every authorization and rate-limit refusal on the Users and Roles admin screens. Its task file carried an explicit exclusion — *"The `settings/*` screens and `App\Livewire\Settings\*` are not in scope"* — written before its own **Q5** decision, which brought five **domain actions** into scope so that a future non-dashboard caller would inherit the logging. Both statements were reviewed and both passed Phase 2's INVEST gate.
- **What happened**: `appsec-auditor`'s Phase 4 audit **FAILed** the first implementation on a Medium (F-1). `App\Actions\Users\RequestEmailChange` — one of the five actions Q5 brought in — is called by `App\Livewire\Users\Index` (in scope, permission-gated) **and** by `App\Livewire\Settings\Profile::updateProfileInformation()` (`settings/profile`, `auth`-only, self-service, no permission gate at all). Instrumenting the action therefore instrumented the excluded caller, and the new log call sat on a rate-limit refusal branch: since `RateLimiter::attempt()` does not consume once the limit is exhausted, every retry past the third re-entered that branch for free. Any authenticated user could drive unbounded log writes at zero cost, from a screen the story had declared out of scope, using a hardening feature as the amplifier.
- **Root cause**: **the exclusion was phrased in terms of *screens*, and the story's unit of change was a *class*.** Those are only the same thing while nothing is shared, and the whole point of Q5 — the [action-owns-the-rule convention](../conventions/directory-structure/controllers-and-authorization-rule.md#an-authorization-rule-belongs-to-the-action-not-to-one-of-its-callers) — is that these actions are deliberately callable from more than one place. Nobody reconciled the two sentences because each is correct read alone; the contradiction only exists in the intersection, and nothing in the task file, the INVEST review or the implementation brief asks who else calls a file being edited. The consequence direction is what made it a security finding rather than noise: an in-scope caller is permission-gated and self-limiting, while the inherited one is reachable by every authenticated account in the app.
- **Fix applied**: not a scope exclusion — a **log ceiling**, so both callers keep the same trace, bounded. A second, 1-attempt `RateLimiter::attempt()` on a distinct key prefix gates the **log call only**, never the real limit, at `RequestEmailChange`'s three refusal sites and (for symmetry, so the shape cannot silently diverge later) `CreateUser`'s rate-limit site — see [`app/Actions/Users/RequestEmailChange.php`](../../app/Actions/Users/RequestEmailChange.php). Phase 5 finding **R-3** then narrowed the aggregate limiter's ceiling key from target-only to `(target, actor)`, matching its two siblings, so a second administrator's refusal against an already-logged target is still recorded. The pattern and its three rules are documented in [architecture/authorization.md](../architecture/authorization/step-up-and-refusal-logging.md#a-shared-actions-rate-limit-refusal-needs-a-log-ceiling).
- **How to avoid it next time**: **before writing a scope exclusion, resolve it against the *files* the story will edit — `grep -rn "ClassName" app/` for every class in scope — and state the exclusion in terms of classes, not screens.** A screen-shaped exclusion is unenforceable the moment the story touches shared code, and this repo's conventions actively produce shared code: an action exists precisely so more than one caller can reach it. Two corollaries. **(a) Adding an unbounded side effect to a shared class is a capability grant to its *least*-privileged caller, not its most.** Ask who the weakest caller is, then ask what they can now make happen for free — a log write, a mail send, a queued job, a cache write all qualify. **(b) When the answer is "this caller shouldn't get the feature", prefer *bounding* the side effect over *excluding* the caller** — the exclusion re-splits one rule into two implementations, which is the drift this project's conventions spend most of their effort preventing. This is the shared-code half of the family recorded below: [wrapping existing code in a `DB::transaction()`](archive-2026-08-17-to-2026-08-21.md#wrapping-existing-code-in-a-dbtransaction-moved-a-cache-flush-nobody-had-written--2026-08-21) is about a change the diff hides, where this one is fully visible in the diff — what is hidden is the caller list of the file it lands in.

## A reviewer's "correction" replaced an accurate technical explanation with a wrong one, unverified — 2026-08-24

- **Context**: story 0015a's Phase 5 code review. `code-reviewer` flagged Larastan level 7 failing on `App\Livewire\Users\Index::isAdministratorRoleSelected()`'s `isset($this->roleId)` check (finding F-1), and in the same finding challenged the *docblock's* explanation of why the check is needed — it said a forged `->set('roleId', null)` leaves a direct `$this->roleId` read throwing `Livewire\Exceptions\PropertyNotFoundException`, and the reviewer called this "likely wrong for a public typed property with a default value", without executing anything to confirm.
- **What happened**: acting on that unverified challenge, the docblock was rewritten to say the property is cleared "via reflection" and that a direct read throws PHP's own native "must not be accessed before initialization" `Error` instead. This is what got committed (`30fdecc`). It was wrong on both counts, and worse than the text it replaced: the original `PropertyNotFoundException` claim was **correct**. A second, independent `code-reviewer` pass verified this by execution — `unset()`-ing the property and reading it directly from inside the class threw exactly `PropertyNotFoundException`, because `HandleComponents::setComponentPropertyAwareOfTypes()` does a plain `unset($component->$property)` (no reflection), and PHP routes a read of an `unset()` *declared* property through the magic methods even from inside the declaring class — `Livewire\Component::__get()` throws `PropertyNotFoundException`, and `isset()` observes that state only because `Component::__isset()` catches it internally, not because nothing is thrown.
- **Root cause**: a review finding phrased as "likely wrong" was treated as a confirmed defect and answered with a plausible-sounding replacement, without either side running the one command that would have settled it (a `tinker` call reading the property after `unset()`). The generic mechanism this repo already tracks — [a patch is only valid against the tree it was written on](#a-deferred-storys-findings-were-claims-about-a-tree-that-no-longer-existed-and-one-of-them-would-have-reopened-a-bug-in-this-log--2026-08-23) — applies here in a narrower form: **a review finding phrased with a hedge ("likely", "probably") is a claim to verify, not a claim to act on directly**, and verifying it is cheap when the claim is about concrete runtime behaviour.
- **Fix applied**: a third review pass verified the real mechanism by execution and the docblock in `app/Livewire/Users/Index.php` was corrected back to the accurate explanation (no reflection; `PropertyNotFoundException` via `Component::__get()`/`__isset()`), with a note recording that a Phase 5 pass previously replaced it with a wrong one. The `@phpstan-ignore isset.property` suppression itself was never wrong — only the prose explaining why it is needed.
- **How to avoid it next time**: **when a review finding hedges its own technical claim ("likely", "should be", "I'd expect"), verify it by execution before writing a fix around it — a hedge is a flag that nobody ran the code, not a lower-confidence fact to trust anyway.** For a claim about which PHP exception a specific line throws, the cheapest verification is always the same: reproduce the exact state (`unset()` the property, call the method, read `get_class($e)`) rather than reasoning from how the mechanism *ought* to work. This is a case of the review process itself introducing a defect that the original text did not have — worth watching for specifically when a review's fix is to *documentation or a comment* rather than to behaviour, since no test can catch a wrong sentence the way `phpstan`/`pest` catch a wrong `if`.

## A deferred story's findings were claims about a tree that no longer existed, and one of them would have reopened a bug in this log — 2026-08-23

- **Context**: story 0015, the consolidated follow-up for the eleven non-blocking findings story **0004**'s Phase 4 audit and re-audit raised against the Users CRUD backend (F4–F13, F17/F18). The task file had been written at 0004's closure and sat in `ai-spec/tasks/` while stories 0005, 0006, 0008, 0008a, 0009 and 0013 shipped — five of them editing the exact four files it was about.
- **What happened**: the story reached its Phase 2 INVEST gate and **failed** it (blocking findings B1–B6). Re-verifying each finding against `HEAD` by opening the cited file found that **six of eleven were wrong**, in three different ways. Half-done: F4 asked to lock two properties and one (`$deletingUserName`) was already `#[Locked]`; F17 asked to rename a flag story 0008a had already renamed. Structurally invalid: F12 asked to fix a null-collision inside `Index::authorizeRoleChange()`, a method 0008a **deleted** — along with the `administratorRoleId()` lookup it compared against — so the described comparison existed in no form at all. Ineffective-as-described: F10 asked for a `DB::transaction()` that 0008a had already added, while the atomicity goal it was added for was still unmet, because the email-change delegation ran *after* the commit. And the sharp one — **F8 prescribed retyping `$status` to `public ?UserStatus`, which would have reintroduced [the `<select>` desync bug recorded in this very log](archive-2026-07-21-to-2026-08-17.md#a-null-livewire-property-bound-to-a-native-select-silently-dropped-the-users-own-pick--2026-08-16)**, where a user's first-option pick is silently discarded while the correct value stays on screen. Its supporting claim was also false: it cited an existing test dataset row that has never existed. F8's *finding* was real; only its prescribed patch was harmful.
- **Root cause**: **a deferred finding is a claim about a tree, and the task file freezes while the tree does not.** Nothing in the workflow re-reads a stored task before Phase 3, so its text arrives carrying the authority of an audit that genuinely was correct — about code from six stories ago. Two properties made it worse than ordinary staleness. First, findings were written as **prescribed patches** ("retype this property to `?string`") rather than as **properties that must hold** ("a forged status value must fail validation, not raise `\ValueError`"); a patch encodes assumptions about the surrounding code, so when that code moves the patch does not merely stop applying — it can become actively harmful, which is exactly what F8 did. Second, the ones that were already fixed fail *silently* on implementation: re-adding `#[Locked]` to an already-locked property is a no-op nobody reviews, so the wasted work is invisible rather than caught.
- **Fix applied**: the whole file was rewritten before any code was written (commit `66a5b88`), with every surviving finding re-verified by reading the real file at `HEAD` and each disposition recorded in a new **"What re-verification changed"** table — F4 halved, F7 re-scoped, F8's instruction explicitly *withdrawn* in writing with the errors-log entry it would have violated cited inline, F10 re-scoped to the ordering with a no-mail-on-rollback constraint, F12 recorded as **closed by 0008a and dropped**, F17 reduced to its test half, F13 split out to its own story `0015a`, F18 deferred by human decision. The line numbers it kept are labelled a reading aid, with Phase 3 required to re-locate each site.
- **How to avoid it next time**: **before a deferred story enters Phase 3, re-verify every finding it carries against `HEAD` by opening the file it cites — and record the disposition of each, including "already closed", in the task file itself.** Four concrete habits. **(a)** Write a finding as the **property that must hold**, never as the patch that would have held it; a patch is only valid against the tree it was written on, and there is no way to tell from reading it. **(b)** Treat a line number in a stored task as a reading aid, never a locator — if the cited line does not contain what the finding describes, the finding is stale until proven otherwise, not merely misnumbered. **(c)** When a deferred instruction contradicts something already in `docs/` — this log, a security page, a convention — **the docs win and the instruction is withdrawn in writing**, so the next reader sees a decision rather than an omission. **(d)** Record the closed findings rather than deleting them; "F12 was closed by 0008a" is the sentence that stops it being re-raised by the next audit. This is a fourth direction of the drift family this log already tracks — [a doc outliving the feature it denied](archive-2026-07-21-to-2026-08-17.md#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13), [a doc outliving the bug it described](archive-2026-08-17-to-2026-08-21.md#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), [code drifting from a rule the doc still states correctly](archive-2026-08-17-to-2026-08-21.md#wrapping-existing-code-in-a-dbtransaction-moved-a-cache-flush-nobody-had-written--2026-08-21) — and the one with the longest fuse, because a backlog item can sit stale for months while looking exactly as authoritative as the day it was filed.
