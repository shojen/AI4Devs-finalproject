### `customers.index` — the ninth permission-gated route

Stories 0041/0042/0043 (backend: `customers` table, `App\Models\Customer`, `App\Concerns\CustomerValidationRules`, `CreateCustomer`/`UpdateCustomer`, soft delete, the "new customer" notification) and story 0044 (the real screen — list, create/edit and delete-confirmation modals, the sidebar entry). Declared in its own [`routes/customers.php`](../../routes/customers.php), the same shape every other area file uses:

```php
// routes/customers.php
use App\Livewire\Customers\Index as CustomersIndex;
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:customers.view`, not Spatie's `permission:` -- Livewire 4's
    // PersistentMiddleware allowlist carries Laravel's `Authorize` (`can:`)
    // but not Spatie's `PermissionMiddleware`, so a `permission:`-gated route
    // would protect the initial GET only, leaving every save()/deleteCustomer()
    // /livewire/update round-trip unauthorized. See
    // docs/architecture/authorization.md.
    Route::livewire('customers', CustomersIndex::class)
        ->middleware(['can:customers.view'])
        ->name('customers.index');
});
```

The `can:`-not-`permission:` rule is identical to every other gated route's, and the inline comment restating it is deliberate duplication — a reader auditing one route file must not have to open another to learn why. See [architecture/authorization.md](../architecture/authorization.md#gating-a-livewire-route-use-can-never-permission).

Eleven consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route** (same reason as every other gated route's: `verified` isn't Livewire-persistent either, and `/livewire/update` never replays route middleware). [`App\Livewire\Customers\Index`](../../app/Livewire/Customers/Index.php) re-authorizes through [`App\Policies\CustomerPolicy`](../../app/Policies/CustomerPolicy.php) — never a raw permission string — as the first statement of `mount()` (`viewAny`), both modal openers `openCreateModal()`/`openEditModal()` (`create`/`update`, disclosure gates, not only mutating ones), `save()` (`create` or `update` depending on which form mode is active) and `deleteCustomer()` (`delete`). `CreateCustomer`/`UpdateCustomer` authorize the identical ability again internally, as defence in depth — the component's own check is not a substitute for theirs.
- **`copyShippingToBilling()` is the one method on this component with no `Gate` call, and that is D-1's own decision, not an omission.** It moves six of the client's own form properties into six others, discloses nothing not already on the client and persists nothing; the write it precedes is gated in `save()`.
- **The view behind it renders the whole screen.** [`resources/views/livewire/customers.blade.php`](../../resources/views/livewire/customers.blade.php) — the *flat* path Livewire resolves for `App\Livewire\Customers\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name); there is no `livewire/customers/index.blade.php` — renders: a header with the live `trans_choice('customers.index.summary', …)` count and a primary "New customer" button (rendered disabled with a tooltip when `Gate::denies('create', Customer::class)`); a **four-column** `flux:table` (D-6) — Customer (name over email, the `users.blade.php` two-line cell), Phone, Shipping location (city + country, or an em dash when neither is set), and an icon-only edit/delete actions column — deliberately **not** the fifteen writable columns, since city + country is the smallest discriminator for looking a customer up and billing address is modal-only; one create/edit modal serving both modes, its inner content wrapped in `@if ($showModal)` so only one "Cancel" control is ever in the DOM, with fields grouped identity → shipping address → billing address (preceded by the "Same as shipping" copy button, D-1); a delete-confirmation modal naming the target, wrapped in `@if ($showDeleteModal)`; and an explicit `customers.index.empty` state rather than a bare table with no rows.
- **The country fields are a plain `flux:input`, `maxlength="2"`, not a `sales_regions`-fed picker (D-2).** `sales_regions.code` is administrator-editable and nullable, so a picker sourced from it would silently make a legal customer country unreachable through the UI — the same reasoning 0041's own D-9 applies to the backend's validation. Revisit only on a product signal, and only against the full ISO catalog if it happens.
- **Per-row `canEdit`/`canDelete` hints are flat `Gate::allows('update'|'delete', $customer)` checks with no self-row or ownership carve-out (D-3)** — the same abilities the two modal openers and `deleteCustomer()` authorize with. Unlike the Users screen's row hints, there is no accepted enabled-then-refused drift here: `CustomerPolicy::update()`/`delete()` ignore their `$target` entirely, so the hint can never disagree with what a click does. It remains a UI hint layered on top of the component's own `Gate::authorize()` calls, never a substitute for them — [architecture/authorization.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer](../architecture/authorization.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer).
- **The delete code path lives in this component by necessity, not by design (D-4).** There is no `DeleteCustomer` action — `deleteCustomer()` authorizes against `CustomerPolicy::delete()` and then calls `$customer->delete()` on the resolved model **instance**, never the query builder, so 0042's `SoftDeletes` trait is always honoured. The method's own docblock records the placement so a later story extracting the action knows to move the guard with it, the identical shape `App\Livewire\Users\Index::deleteUser()` already establishes for the same reason.
- **This screen does not adopt step-up authentication, and that is a stated non-application rather than a gap (D-7).** None of task 0015a's five step-up-gated Users operations has a Customers counterpart: a customer holds no role and no account status, `customers.email` is contact data with no login/reset-token/session/passkey keyed to it, and deleting a customer removes a passive record without revoking anyone's access. See [architecture/authorization.md#what-it-protects-and-what-it-deliberately-does-not](../architecture/authorization.md#what-it-protects-and-what-it-deliberately-does-not) for the full reasoning and the table this screen was checked against.
- **Its row actions are icon-only, so they are not selectable by visible text.** Each carries an `aria-label` plus `data-test="edit-customer-{id}"` / `data-test="delete-customer-{id}"` on **both** the enabled and the disabled branch, and both `wire:click` arguments pass through `@js(...)` — mandatory, not stylistic, per [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md).
- **The disabled-row-action markup reuses two Flux/Blaze rules verbatim from `users.blade.php`.** A disabled action is a separate `@if`/`@else` branch wrapped in an explicit `<flux:tooltip>`, never a conditionally-bound `:tooltip` prop (which `livewire/blaze` renders as present — and so produces an empty tooltip bubble — on every enabled row too); and `cursor-not-allowed!` sits on that `flux:tooltip` wrapper, never on the disabled `<flux:button>` itself, since Flux's own `disabled:pointer-events-none` takes a disabled button out of hit-testing. Both are recorded with their verification method in [errors-log.md](../errors-log.md); do not "simplify" either back into the obvious form.
- **`/customers` is linked from the sidebar only to a holder of `customers.view`.** [`config/modules.php`](../../config/modules.php) gained an `items.customers` entry with `group: null, cluster: null` — the bare top-level shape `items.users` already uses, since Customers is a top-level operational module like Users rather than store configuration or a sub-resource of an existing cluster — `permissions` exactly `['customers.view']`, with matching `lang/{en,es}/navigation.php` leaves. `resources/views/components/sidebar-nav.blade.php` was **not** touched — the registry's "append data, never behavior" claim holding again. See [architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry).
- **Copy lives in the `lang/{en,es}/customers.php` files task 0041 deliberately deferred here (its D-14).** `index` (`summary` — a `trans_choice()` key, never a PHP ternary or two separate keys — `empty`, `shipping_location`, `action_not_allowed`), `form` (the shipping/billing headings, the "same as shipping" copy-affordance label, the six field labels and the country hint), and `delete` (`confirm_title`, `confirm_body`) — key-for-key identical across both locales. Generic chrome (`Save`, `Cancel`, `Name`, `Email`, `Phone`) stays as bare `__('…')` literals matching `users.blade.php`; only domain copy goes in this file.
