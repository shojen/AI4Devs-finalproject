### `blog-tags.index` — the thirteenth permission-gated route

Story 0060 (route, component, view, sidebar entry). The first Blog screen, and the first story to touch `routes/`, `config/modules.php` or `lang/` for the Blog area at all. It consumes [story 0059](../../ai-spec/tasks/done/0059-blog-tags-backend.md)'s model, policy and three actions unchanged.

```php
// routes/blog-tags.php
use App\Livewire\BlogTags\Index as BlogTagsIndex;   // aliased: `Index` is ambiguous across areas

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:blog.view`, not Spatie's `permission:` — Livewire 4's PersistentMiddleware
    // allowlist carries `can:` but not `permission:`. See architecture/authorization.md.
    Route::livewire('blog/tags', BlogTagsIndex::class)
        ->middleware(['can:blog.view'])
        ->name('blog-tags.index');
});
```

The URI is nested (`/blog/tags`) and the name is flat (`blog-tags.index`), matching `sales-regions.index`: it leaves `blog-categories.index` and a bare `blog.index` (the post list) free.

- **Access.** The route gates on `blog.view`; `mount()` re-checks `viewAny` (unlogged, like the other admin screens, because a `can:` refusal is unreachable over HTTP). Create, rename and delete each require their own ability (`blog.create` / `blog.edit` / `blog.delete`), so a role holding `blog.edit` without `blog.view` gets a 403 and its grant is unreachable — the same fail-closed shape [architecture/authorization.md](../architecture/authorization/how-to-gate.md) documents for `users.index`.
- **Every public method authorizes, and every refusal is logged.** `openCreateModal()`, `openEditModal()`, `save()` (per branch), `confirmDelete()` and `deleteTag()` route through [`LogRefusedPrivilegedAttempt`](../architecture/authorization/step-up-and-refusal-logging.md#recording-a-refusal--what-every-gate-owes-the-audit-trail) with `target_type: 'blog_tag'` passed explicitly. This is [`BlogTagPolicy`](../../app/Policies/BlogTagPolicy.php)'s first *component* call site. The actions authorize again themselves — defence in depth, not duplication.
- **Validation lives in the actions, not the component.** `save()` calls `CreateBlogTag` / `RenameBlogTag` and lets their `ValidationException` (keyed `name`) propagate into the error bag; the component composes no validation trait and never calls `$this->validate()`. It never calls `FindOrCreateBlogTag` — that would turn every duplicate refusal into a silent success.
- **The `->ignore()` id is server-authoritative.** `$editingTagId` is `#[Locked]` and assigned only from a row just re-read in `openEditModal()`; `save()` re-reads with `findOrFail()` and hands the model to `RenameBlogTag`. `$tags`, `$deletingTagId` and `$deletingTagName` are `#[Locked]` too.
- **Deleting is unconditional, and that is the contract.** PRD Epic 4: a deleted tag is removed from every post that used it. The delete-confirmation modal names the tag and says so; it renders **no** usage count, blocked state, reassign step or error outlet, and its destructive button is never disabled. This is the deliberate inverse of the product-categories screen. The detach-from-posts half is honoured by the database (story 0061's `blog_post_tag` must `cascadeOnDelete()`), not by this screen.
- **Rows** are `{id, name, canEdit, canDelete}` ordered `name ASC, id ASC`; there is no post or usage-count key (`BlogTag::posts()` exists since story 0061, but the screen does not use it; a plain `withCount('posts')` would exclude trashed posts, which is the right number for a screen). `canEdit`/`canDelete` are `Gate::allows()` UI hints from the same policy methods the mutating methods authorize against. The header's *New tag* button is likewise gated through `@can('create', BlogTag::class)`.
- **`data-test` hooks:** `create-blog-tag-button`, `edit-blog-tag-{id}`, `delete-blog-tag-{id}` (both present on the enabled *and* the disabled branch), `blog-tag-name-input`, `confirm-delete-blog-tag`; the sidebar renders `sidebar-group-content`, `sidebar-cluster-blog` and `sidebar-link-blog_tags`. Both row `wire:click` arguments are single `@js()` calls.
- **Sidebar.** [`config/modules.php`](../../config/modules.php) gained `groups.content`, a nested `clusters.blog` (`group: 'content'`) and `items.blog_tags` (`group: null, cluster: 'blog'`, `permissions: ['blog.view']` — exactly the route's ability). Stories 0062 and 0063 each add one `items.*` entry with `cluster: 'blog'` and declare no new group or cluster (0062 appended; 0063 inserted before `blog_tags`, see below).
- **Topbar.** The view declares the `heading`/`subheading` slots (`blog-tags.index.title`, `topbar.blog_tags.subtitle`); `blog-tags.index` is in `TopbarTest`'s screen dataset, which fails for any authenticated screen missing from it.
- **Copy** lives in `lang/{en,es}/blog-tags.php`; there is deliberately no "blocked" or count copy.

### `blog-categories.index` — the fourteenth permission-gated route

Story 0062 (route, component, view, sidebar entry). It consumes [story 0058](../../ai-spec/tasks/done/0058-blog-categories-backend.md)'s model, policy and three actions and [story 0061](../../ai-spec/tasks/done/0061-blog-posts-core-crud-backend.md)'s delete guard unchanged, and is the screen 0061's `blogCategoryId` error-bag contract was built for.

```php
// routes/blog-categories.php
use App\Livewire\BlogCategories\Index as BlogCategoriesIndex;   // aliased: `Index` is ambiguous across areas

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:blog.view`, not Spatie's `permission:` — see architecture/authorization.md.
    Route::livewire('blog/categories', BlogCategoriesIndex::class)
        ->middleware(['can:blog.view'])
        ->name('blog-categories.index');
});
```

- **Access and authorization** follow the tags screen exactly: the route gates on `blog.view`, `mount()` re-checks `viewAny` (unlogged), and every other public method except the two `close*()` resets routes through [`LogRefusedPrivilegedAttempt`](../architecture/authorization/step-up-and-refusal-logging.md#recording-a-refusal--what-every-gate-owes-the-audit-trail) with `target_type: 'blog_category'`. `deleteCategory()` authorizes in the component too and does not double-log: the helper writes only on refusal. This is [`BlogCategoryPolicy`](../../app/Policies/BlogCategoryPolicy.php)'s first *component* call site.
- **Validation lives in the actions.** `save()` calls `CreateBlogCategory` / `RenameBlogCategory` and lets their `name`-keyed `ValidationException` propagate; the component composes no validation trait, never calls `$this->validate()` and contains no fold logic. `$editingCategoryId` is `#[Locked]` and assigned only from a re-read row; `$categories`, `$blogCategoryId` and `$deletingCategoryName` are `#[Locked]` too.
- **Deleting is hard-blocked with a count, at every privilege level.** While any post — draft, scheduled, published **or trashed** — references the category, `deleteCategory()` throws `ValidationException` keyed **`blogCategoryId`** with story 0061's `trans_choice('blog.categories.delete_blocked')` message. The component catches nothing, so the throw aborts the method before the modal closes and the refusal renders inline (`@error('blogCategoryId')`, `data-test="blog-category-delete-blocked"`). The delete target's property is named `$blogCategoryId` to match that key: Livewire drops an error whose key the component does not declare. A Super Admin is refused identically (a domain invariant, not an authorization rule), and there is **no** force, confirm-and-proceed or reassign control on the screen — reassigning belongs to the post editor (0063). `closeDeleteModal()` clears the `blogCategoryId` error; `closeModal()` clears the `name` error; the two are distinct resets.
- **Rows** are `{id, name, postCount, canEdit, canDelete}` ordered `name ASC, id ASC`. `postCount` is `withCount(['posts' => fn ($q) => $q->withTrashed()])` — the **same** scope the guard counts with, so the row and the refusal cannot state different numbers. A bare `withCount('posts')` excludes soft-deleted posts (verified by execution) and would undercount. The count is informational: it never disables the delete action, and it is not a delete-eligibility gate — the action re-counts at click time.
- **`data-test` hooks:** `create-blog-category-button`, `edit-blog-category-{id}` and `delete-blog-category-{id}` (present on the enabled *and* the disabled branch), `blog-category-post-count-{id}`, `blog-category-name-input`, `confirm-delete-blog-category`, `blog-category-delete-blocked`; the sidebar renders `sidebar-link-blog_categories`. Both row `wire:click` arguments are single `@js()` calls.
- **Sidebar.** [`config/modules.php`](../../config/modules.php) gained `items.blog_categories` (`group: null, cluster: 'blog'`, icon `rectangle-stack`, `permissions: ['blog.view']` — exactly the route's ability), appended to the cluster story 0060 created; no group or cluster was declared.
- **Topbar.** `blog-categories.index` is in `TopbarTest`'s screen dataset (`blog.categories.index.title`, `topbar.blog_categories.subtitle`).
- **Copy** extends `lang/{en,es}/blog.php` under `categories.index`, beside story 0061's `categories.delete_blocked`, which this screen never edits.
- **Known, accepted gap (0061 D-7d).** The refusal counts trashed posts, so an administrator can be blocked by posts that appear in no list; the exit is the [posts screen](#blog-postsindex-blog-postscreate-blog-postsedit--the-fifteenth-to-seventeenth-permission-gated-routes)'s deleted-posts section (story 0063), not this screen.

### `blog-posts.index`, `blog-posts.create`, `blog-posts.edit` — the fifteenth to seventeenth permission-gated routes

Story 0063 (three routes, two components, two views, sidebar entry). The Blog module's headline screen. It writes nothing of its own: it consumes [story 0061](../../ai-spec/tasks/done/0061-blog-posts-core-crud-backend.md)'s `CreateBlogPost`, `UpdateBlogPost`, `DeleteBlogPost` and `RestoreBlogPost` actions, model, scopes and policy, and the tag actions through them.

```php
// routes/blog-posts.php
use App\Livewire\BlogPosts\Editor as BlogPostsEditor;   // aliased: `Index` and `Editor` are ambiguous across areas
use App\Livewire\BlogPosts\Index as BlogPostsIndex;

Route::middleware(['auth', 'verified'])->group(function () {
    Route::livewire('blog/posts', BlogPostsIndex::class)
        ->middleware(['can:blog.view'])->name('blog-posts.index');
    Route::livewire('blog/posts/create', BlogPostsEditor::class)
        ->middleware(['can:blog.view'])->name('blog-posts.create');
    Route::livewire('blog/posts/{blogPost}/edit', BlogPostsEditor::class)
        ->middleware(['can:blog.view'])->name('blog-posts.edit');
});
```

- **Two gates, deliberately different.** All three routes gate on `blog.view` (the plain `can:` alias, for the reason the tags section gives). The finer abilities are authorized in the components: `Index::mount()` re-checks `viewAny` (unlogged, like the other admin screens), while `Editor::mount()` authorizes `create` (no post) or `update` (the route-bound post) through [`LogRefusedPrivilegedAttempt`](../architecture/authorization/step-up-and-refusal-logging.md#recording-a-refusal--what-every-gate-owes-the-audit-trail) with `target_type: 'blog_post'` passed explicitly, so that refusal **is** reachable over HTTP and **is** logged. The outcome: `blog.view` alone gives 200 on the list and 403 on create and edit; `blog.view` + `blog.create` reaches create, `blog.view` + `blog.edit` reaches edit; a Super Admin reaches all three. `save()` re-authorizes at click time. A trashed post's edit URL is a 404 (default route-model binding).
- **The list** (`Index`) is paginated (`PER_PAGE = 25`), ordered `created_at DESC, id ASC` (never by title, which posts do not keep unique). The query selects **explicit columns and never `body` or `slug`**, and eager-loads `category:id,name` and `tags:id,name`, so no row triggers a query. Rows are `{id, title, categoryName, status, date, tags, canEdit, canDelete}`; the date is `published_at` for a post that has one and `created_at` otherwise. The status badge is `zinc` (Draft), `amber` (Scheduled) or `lime` (Published), labelled by `BlogPostStatus::label()`. A Scheduled post already shows its badge and date, so [story 0064](../../ai-spec/tasks/0064-scheduled-post-auto-publish-backend.md)'s sweep needs no change here when it flips a post. Every read of `title`, `category->name` and `tag->name` sits in the two private row mappers, so the translatable-content retrofit (Epic 5) has one place to change.
- **Filters** are `category` and `tag`, two `wire:model.live` selects bound with `#[Url]` (the first `#[Url]` properties in this repo) and composed through 0061's `forCategory()` / `forTag()` scopes. Both are `''`-defaulted strings, never `null`. **They arrive as forged input:** `sanitizeFilters()` runs in `mount()` and in each `updated…Filter()` hook and resets any id that does not exist **in the database** (not in the capped 500-option dropdown) to `''`, never a 500. Each `updated…Filter()` also calls `resetPage()`. `posts()` clamps a page past the end (a forged `?page=99`, or the last row of the last page just deleted) to the real last page, and the empty state keys off `total()`, never the page's row count.
- **Delete** opens a confirmation modal. `confirmDelete()` re-reads the row (`findOrFail()`), authorizes `delete` through the logging helper **before** naming it, and stores its id and title in `#[Locked]` properties (`$deletingBlogPostId`, `$deletingBlogPostTitle`, the latter never `null`). `deleteBlogPost()` re-reads again, authorizes again and calls `DeleteBlogPost`. It is a soft delete, so the post moves to the deleted-posts section. `closeDeleteModal()` also clears the error bag.
- **Deleted posts and restore.** A collapsed section (closed on first paint, independent of the filters) renders **only when trashed posts exist**. It lists at most `TRASHED_LIMIT = 200` rows, most recently deleted first, and says *"Showing the N most recently deleted posts of M"* when it is truncated (the total is its own count query). `restoreBlogPost(string $blogPostId, RestoreBlogPost $restoreBlogPost, LogRefusedPrivilegedAttempt $logRefusedPrivilegedAttempt)` resolves the target `BlogPost::withTrashed()->findOrFail()` (the default query cannot see the row), authorizes `restore` (which is `blog.edit`, not `blog.delete`: 0061 D-20) and calls `RestoreBlogPost`. The per-row control reads the same `Gate::allows('restore')`. **There is no force-delete anywhere**, so this section is the exit 0061 D-7d promised for the category delete guard: a category blocked only by trashed posts is freed by restoring those posts here and reassigning them in the editor, because a trashed post is reachable nowhere else.
- **The editor** (`Editor`, one component for create and edit) is a **routed page, not a modal**: the WYSIWYG is seeded from `$body` once at client initialisation (story 0021 D9), so a fresh page per post makes that safe and lets a save redirect (`blog-posts.index`) instead of resetting the form in place. Properties are all non-null strings (`title`, `blogCategoryId`, `status`, `publishedAt`, `body`, `tagInput`) plus `array $tagNames`; `$blogPostId` is `#[Locked]` and set only from the route-bound post. **`status` is a plain string, not `BlogPostStatus`**: Livewire's enum synthesizer would turn a forged value into an uncaught `ValueError` before validation; the action refuses an unknown status by validation.
- **The publication date.** The `datetime-local` input (`step="1"`, with a translated UTC hint, because the application timezone is UTC) is always in the DOM and revealed only for Scheduled by Alpine's `x-show` on the client-held status. It is hydrated at **seconds** precision (`Y-m-d\TH:i:s`) so retitling an overdue Scheduled post resubmits the stored instant and 0061's "same date" exemption applies (R-9). `save()` sends `publishedAt` **only when the status is Scheduled**: a date typed under Scheduled and left behind under Published must never silently schedule the post (0061a).
- **The body** is the WYSIWYG component embedded once, with a stable `wire:key` and no conditional around it; the view embeds **no** media gallery of its own (the WYSIWYG mounts the one it needs, so a second embed would collide).
- **The tag chip field** is bespoke (`SearchableMultiSelect` is ruled out) and binds **names**. `$tagNames` is the post's complete tag set, hydrated from every tag it holds and resubmitted whole on every save, and the chips render all of it: **never filtered, truncated or paginated**, because `UpdateBlogPost` replaces the tag set with `sync()` and a tag the editor cannot see is one a save silently revokes. Adding trims, ignores blanks, dedupes case- and accent-insensitively (the server's fold) and bounds at `BlogPost::MAX_TAGS`; nothing is created until Save. Suggestions match the folded `normalized_name`, take LIKE wildcards literally, exclude names already on the post and stop at 8. For an actor **without `blog.create`** the add control is disabled with a tooltip for a NEW name, and `addTag()` itself refuses one (so the keyboard's Enter is covered), while existing names still add. That is a hint: the real control is `FindOrCreateBlogTag`'s `AuthorizationException`, which aborts the save (403) and rolls the whole transaction back, post included. The editor reaches tags only through the post actions (an architecture test fences `SyncBlogPostTags` and `FindOrCreateBlogTag` out of `App\Livewire\BlogPosts`).
- **Validation lives in the actions.** The component composes no validation trait and never calls `$this->validate()`. `save()` catches the action's `ValidationException` and **re-keys** it onto declared public properties (`blog_category_id` → `blogCategoryId`, `published_at` → `publishedAt`, `tag_names` and `name` → `tagNames`), because Livewire persists only errors keyed on a declared property; `title`, `body` and `status` already are one. A category-less install shows a callout linking to `blog-categories.index`, and the placeholder option is genuinely disabled (a category is required).
- **`data-test` hooks.** List: `create-blog-post-button`, `category-filter`, `tag-filter`, `title-blog-post-{id}`, `category-blog-post-{id}`, `tags-blog-post-{id}`, `status-badge-blog-post-{id}`, `date-blog-post-{id}`, `edit-blog-post-{id}` and `delete-blog-post-{id}` (each on the enabled *and* the disabled branch), `blog-posts-empty-state`, `trashed-posts-section`, `trashed-posts-toggle`, `trashed-posts-count`, `trashed-posts-list`, `trashed-posts-truncated`, `trashed-blog-post-{id}`, `restore-blog-post-{id}`, `cancel-delete-blog-post`, `confirm-delete-blog-post`. Editor: `blog-post-editor`, `blog-post-title`, `blog-post-category`, `blog-post-no-categories`, `blog-post-status`, `blog-post-published-at` (the reveal wrapper) and `blog-post-published-at-input`, `blog-post-tag-field`, `blog-post-tag-chips`, `tag-chip-{name}`, `tag-chip-remove-{name}`, `blog-post-tag-input`, `blog-post-tag-add`, `blog-post-tag-suggestions`, `blog-post-tag-suggestion-{name}`, `blog-post-save`, `blog-post-cancel`. Every row `wire:click` argument is a single `@js()` call.
- **Sidebar.** [`config/modules.php`](../../config/modules.php) gained `items.blog_posts` (`group: null, cluster: 'blog'`, icon `pencil-square`, `current_when: 'blog-posts.*'` so it stays highlighted on create and edit, `permissions: ['blog.view']`, exactly the routes' ability). It is **inserted before `blog_tags`**, not appended: declaration order is render order, so the Blog cluster renders **Posts / Tags / Categories** ([the registry rule](../architecture/authorization/how-to-gate.md#the-second-half-of-a-module-gate-the-sidebar-registry)). No group or cluster was declared.
- **Topbar.** Both views declare the `heading` / `subheading` slots (`blog-posts.index.title` with `topbar.blog_posts.subtitle`; `blog-posts.editor.title_create` / `title_edit` with `topbar.blog_post_editor.subtitle`), and all three routes are covered by `TopbarTest`.
- **Copy** lives in the new `lang/{en,es}/blog-posts.php` (`index.*`, `editor.*`, `statuses.*`), key-for-key identical across languages. That supersedes the header sentence of `lang/{en,es}/blog.php` saying stories 0062 and 0063 extend it: 0062 did, but the posts screens have their own file, as tags do (`blog-tags.php`). `BlogPostStatus::label()` (`__('blog-posts.statuses.'.$value)`) shipped with this story, the first screen to render a status.
