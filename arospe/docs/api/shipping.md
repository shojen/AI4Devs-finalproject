### `shipping.zones.index` — the sixth permission-gated route

Story 0034 (the screen) and story 0033 (the model, the four actions, `ShippingZoneValidationRules`, `ShippingZonePolicy` it consumes). The first UI story to call `ShippingZonePolicy`, which 0033 shipped with zero call sites, and 0022's `SearchableMultiSelect`'s second real-resolver consumer after `App\Livewire\Products\Editor`'s region picker (story 0027) — the first against a **bigint**-keyed table (`geography_entries`, story 0032) rather than a UUID one, and the first whose resolver runs real, index-bound SQL queries rather than an in-memory filter over a handful of rows. Declared in its own [`routes/shipping.php`](../../routes/shipping.php), the same shape every prior area file uses:

```php
// routes/shipping.php
use App\Livewire\Shipping\Zones;
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:shipping.view`, not Spatie's `permission:` -- same reason as every other
    // gated route in this app. See docs/architecture/authorization.md.
    Route::livewire('shipping/zones', Zones::class)
        ->middleware(['can:shipping.view'])
        ->name('shipping.zones.index');
});
```

Ten consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route (same reason as `users.index`'s in [Users & Roles routes](users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** [`App\Livewire\Shipping\Zones`](../../app/Livewire/Shipping/Zones.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`; `openCreateModal()`/`save()`'s create branch ask `create`; `openEditModal()`/`save()`'s edit branch ask `update` against a freshly `findOrFail()`d target; `confirmDelete()`/`deleteZone()` each ask `delete` against a freshly resolved target. **All six methods gate**, matching [security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — `deleteZone()`'s own gate is defence in depth on top of `confirmDelete()`'s (which already refuses before the modal opens) and `DeleteShippingZone`'s own self-authorization (0033 Phase 4 finding F-1), matching this project's "the component authorizing too is defence in depth, not duplication to remove" convention (Phase 5 code-review finding M-2).
- **The write path is protected twice over, matching the shape `product-categories.index`/`products.index` already established.** All four domain actions — `CreateShippingZone`, `RenameShippingZone`, `SyncShippingZoneGeography`, `DeleteShippingZone` — self-authorize as their own first statement (0033's Phase 4 fix), so this component's own gates are a **second** layer, not the only one; a future Artisan command, queued job or REST controller already inherited the refusal before this screen existed.
- **`SyncShippingZoneGeography` is structurally unreachable from the create branch, and from any ungated method.** `save()`'s create branch never calls it at all — geography coverage is assigned only in the edit modal (D-2), so a tampered `geographyEntryIds` submitted alongside a create is validated (harmless) but never synced, closing what 0033's own hand-off named "the method most likely to ship ungated because it does not look like saving" from a second direction. It is called only from inside `save()`'s already-authorized edit branch, immediately after `RenameShippingZone` — deliberately **not** wrapped in a component-level `DB::transaction()` (Phase 5 code-review finding M-1: D-7 explicitly considered and rejected that wrapper, since 0033 chose the action as the unit of atomicity; a rename succeeding while a concurrent sync fails is the accepted, visible residual D-7 names).
- **The component's public surface**: `$zones` (`#[Locked]` — entirely server-derived), the `#[Locked]` `$editingZoneId` (assigned only from a resolved model's own `id`, never the raw method argument — what makes the id fed to `shippingZoneNameRules()`'s normalised-uniqueness closure server-authoritative), `$showModal`, the plain `string $name` field, the deliberately **not** `#[Locked]` `array $geographyEntryIds` (the picker's `#[Modelable]` binding surface — its safety comes from `geographyEntryIdsRules()`'s existence check plus the total-function reject below, never from locking), and the delete-modal trio `$showDeleteModal`/`#[Locked] $deletingZoneId`/`#[Locked] $deletingZoneName`.
- **The view behind it renders the whole screen.** [`resources/views/livewire/shipping/zones.blade.php`](../../resources/views/livewire/shipping/zones.blade.php) — the **nested** path Livewire resolves for `App\Livewire\Shipping\Zones`, one level *deeper* than the flat `Index`-in-a-subfolder exception's siblings, because the class is not named `Index` (see [conventions/naming.md](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name)'s own boundary note) — renders a header with a "New zone" button (rendered disabled with an "action not allowed" tooltip when `$this->canCreate` is false); a `flux:table` of zones (name, a `trans_choice`'d coverage count or an em dash at zero — never a warning — and icon-only edit/delete row actions gated on the **screen-level** `$this->canEdit`/`$this->canDelete` flags, D-5); a create/edit modal (name always; the geography picker plus a read-only per-level coverage summary only once a zone exists, D-2/D-3); a delete-confirmation modal; and an explicit empty state.
- **The geography picker embed is 0022's whole integration surface, plus exactly one additive prop.** `:option-resolver="\App\Actions\Shipping\SearchGeographyEntries::class"`, `wire:model="geographyEntryIds"`, and `:max-chip-area-height="'12rem'"` (0022's D14 prop, bounding the chip area at the catalog's own 500-entry ceiling) are the entire binding — no markup here defines a bounding mechanism of its own.
- **A save carrying any stale or invalid geography id is rejected in full, never reduced to the valid subset.** `save()` validates `geographyEntryIdsRules()` (0033's own single-closure existence check) and then calls `SearchGeographyEntries::resolveSelected($this->geographyEntryIds)` directly — the same "or its own `resolveSelected()` call" shape `App\Livewire\Products\Editor::save()` already uses for `regionIds`, since Livewire gives a parent no live reference to a mounted child's instance across the request boundary. Catching the resulting `App\Exceptions\UnresolvedSelectionException` and converting it into a `ValidationException` on `geographyEntryIds` happens **before** either `RenameShippingZone` or `SyncShippingZoneGeography` is ever called, so a rejected save leaves both the name and the coverage byte-for-byte unchanged.
- **Row actions gate on screen-level capability flags, not per-row `Gate::allows()` (D-5) — see [architecture/authorization.md](../architecture/authorization.md#shippingzonepolicy--the-eighth-policy-and-the-one-d-9-uses-to-reconcile-the-policy-vs-permission-check-divergence-with-0035) for why this is safe here specifically.** `canCreate()`/`canEdit()`/`canDelete()` are `#[Computed]`, evaluated once per render; `canEdit()`/`canDelete()` check against `new ShippingZone` (an unsaved, query-free instance), since `ShippingZonePolicy::update()`/`delete()` never read their target. The disabled-branch markup reuses the two Flux/Blaze traps every other screen on this page already documents verbatim: an explicit `<flux:tooltip>` wrapper rather than a conditionally-bound `tooltip` prop, and `cursor-not-allowed!` on that wrapper rather than on the `disabled:pointer-events-none` button.
- **Corrected 2026-09-10 (story 0036) — the delete flow now genuinely renders a blocked-delete message, and the sentence below describing the pre-0036 state is quoted rather than silently rewritten, per this project's audit-authored-page convention.** It used to read: *"The delete flow renders whatever `ValidationException` `DeleteShippingZone` raises, with no `zones.delete_blocked` key of its own (D-6). `DeleteShippingZone` ships as a plain `->delete()` today — the in-use-by-a-rate-rule guard is story 0036's, once `shipping_rates` exists — so `@error('shippingZoneId')` renders nothing yet; the key name matches this codebase's own `<model>Id` validation-key convention (`productCategoryId`, `productAttributeTypeId`) rather than the component's own `$deletingZoneId` property name, so 0036 can extend `DeleteShippingZone` with no markup change here."* Story 0036 is that extension: `DeleteShippingZone` now counts `$shippingZone->shippingRates()->count()` and throws a `ValidationException` keyed `shippingZoneId` carrying `trans_choice('shipping.zones.delete_blocked', ...)` when the zone is still referenced (see [database/schema.md](../database/schema-shipping.md#deleting-a-shipping-zone-still-referenced-by-a-rate-rule-is-hard-blocked) and [architecture/shipping.md](../architecture/shipping.md#the-zone-delete-guard)). The predicted "no markup change here" held **almost** literally — 0034's Phase 4 audit (closed by story 0036, finding F-4) required exactly one real change to `App\Livewire\Shipping\Zones` itself: declaring `#[Locked] public ?string $shippingZoneId = null;` as a persistence anchor, since Livewire's `SupportValidation::dehydrate()` filters the persisted error bag through `Utils::hasProperty()` and drops an error keyed on an undeclared property after one round trip. That fix in turn required a **second** one this story's own Phase 4 re-audit found: `confirmDelete()` needed its own `resetErrorBag('shippingZoneId')` (alongside the create/edit openers' pre-existing `resetValidation()` calls) or a blocked-delete message from one zone would render, factually wrong, against the next zone's own delete-confirmation modal. Both the mechanism and the two-failure-mode shape are documented in full on [security/livewire-error-bag-persistence.md](../security/livewire-error-bag-persistence.md) rather than repeated here — read it before adding a second persistence-anchor property anywhere in this app.
- **`/shipping/zones` is linked from the sidebar only to a user holding `shipping.view`.** [`config/modules.php`](../../config/modules.php) gained a **new `groups.shipping` group** (heading `navigation.groups.shipping`, icon `truck`, non-expandable while it holds one entry — the same shape `groups.taxes` uses) plus an `items.shipping_zones` entry (icon `map`, `route` `shipping.zones.index`, `current_when` `shipping.zones.*`, `permissions` **exactly** `['shipping.view']`), with matching `lang/{en,es}/navigation.php` leaves. `resources/views/components/sidebar-nav.blade.php` was **not** touched — the registry's "append data, never behavior" claim holding for a seventh entry in a row (Phase 5 code-review finding L-4: `product-categories.index` was the fourth, `products.index` the fifth, `product-attribute-types.index` the sixth). `tests/Feature/Navigation/SidebarModuleGatingTest.php`'s two generic drift guards (every gated entry's `permissions` exactly matches its route's `can:` middleware; every ungated entry is on an explicit allow-list) cover the new entry with no test file change. **This is the story-0034-as-shipped shape, not the current one: merging into `feature-entrega2-ARP` after story 0080 (sidebar navigation grouping and nesting) had already landed re-targeted this entry into 0080's new nested schema — there is no `groups.shipping` any more, and `items.shipping_zones` instead nests into the same `store_settings` cluster `sales_regions` already uses** (`group: null, cluster: 'store_settings'`), per [`architecture/authorization.md`](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema. The entry's own key, `permissions`, `route` and `current_when` values are unchanged by that move; only its `group`/`cluster` placement and icon (`truck`, kept) moved.

### `shipping.index` — the seventh permission-gated route

Story 0035 (backend — carrier catalog, seeded, enable/disable toggle) and story 0037 (the real screen: the rate table, and the create/edit/delete UI for `ShippingRate` — story 0036's already-audited policy/actions, gaining their first real caller here). **Corrected 2026-09-10 (story 0037) — this subsection previously described a placeholder view, quoted rather than silently rewritten, per this project's audit-authored-page convention.** It used to read: *"Ships with a **placeholder view**, mirroring exactly how `users.index` (task 0004) shipped ahead of task 0006's real markup — the paired Epic 2 frontend story owns the carrier cards, the toggle control and the ACTIVO/INACTIVO badge."* Story 0037 is that paired frontend story, closing the identical 0004→0006 / 0017→0018 / 0028→0030 / 0033→0034 split this doc set has recorded four times before. Declared in the same [`routes/shipping.php`](../../routes/shipping.php) `shipping.zones.index` already lives in, as a **sibling** route rather than a tab inside that screen:

```php
// routes/shipping.php
Route::livewire('shipping', ShippingIndex::class)
    ->middleware(['can:shipping.view'])
    ->name('shipping.index');
```

`App\Livewire\Shipping\Index` is imported aliased (`use App\Livewire\Shipping\Index as ShippingIndex;`), matching every other area file's own handling of the ambiguous `Index` class name.

Story 0035's original eight consequences, unchanged by story 0037:

- **The middleware column understates what protects this route (same reason as above).** [`App\Livewire\Shipping\Index`](../../app/Livewire/Shipping/Index.php) re-authorizes in both of its methods: `mount()` asks `shipping.view` (unlogged, matching `Zones::mount()`'s own reasoning — the route's `can:shipping.view` gate checks the identical ability, so a real HTTP actor who would fail this is refused by the route before ever reaching here), and `toggleCarrier()` re-authorizes `shipping.edit` as a second layer even though the action it calls already self-authorizes — defence in depth, matching every mutating method on `App\Livewire\Shipping\Zones`.
- **No `ShippingCarrierPolicy` exists.** `shipping.view`/`shipping.edit` are authorized directly as permission strings, not through a policy — named once as `App\Models\ShippingCarrier::VIEW_PERMISSION`/`EDIT_PERMISSION` (Phase 5 code-review finding L3), per [naming.md](../conventions/naming.md#permission-names)'s "name a permission once on the class that owns the rule" convention. See [database/schema.md](../database/schema-shipping.md#shipping_carriers) and [architecture/authorization.md](../architecture/authorization.md#shippingzonepolicy--the-eighth-policy-and-the-one-d-9-uses-to-reconcile-the-policy-vs-permission-check-divergence-with-0035)'s D-9 for why: the component is a real, routed enforcement point and the ability is uniform across every carrier row.
- **`toggleCarrier(string $carrierId, bool $active)` authorizes BEFORE resolving the carrier** (Phase 4 security-audit finding F-3) — since the ability is target-independent, the gate runs against the raw, unresolved id at zero extra cost, closing what would otherwise be a 404-vs-403 existence oracle for an actor holding `shipping.view` but not `shipping.edit`.
- **The write path is protected twice over, designed that way from Phase 1.** [`App\Actions\Shipping\ToggleShippingCarrier`](../../app/Actions/Shipping/ToggleShippingCarrier.php) self-authorizes `shipping.edit` as its own first statement (through `App\Actions\Auth\LogRefusedPrivilegedAttempt`, `targetType: 'shipping_carrier'`), so a future Artisan command, queued job or REST controller inherits the identical refusal the dashboard gets.
- **The action takes the DESIRED state, never a blind flip** (Phase 4 security-audit finding F-2) — `__invoke(ShippingCarrier $shippingCarrier, bool $active)`, matching `App\Actions\SalesRegions\SetSalesRegionActive`'s own shape. It re-reads its target under `lockForUpdate()` inside its own transaction rather than trusting the caller's instance, so two concurrent requests serialize on the row lock and the write always applies to the row's true current state, per [security/model-instance-trust.md](../security/model-instance-trust.md).
- **The component's public surface**: `$carriers` (`#[Locked]` — entirely server-derived, four rows of `{id, code, name, description, isActive}`), loaded in `mount()` and reloaded after every toggle. The target carrier is always re-resolved from the database inside `toggleCarrier()` (`ShippingCarrier::query()->findOrFail($carrierId)`), never trusted from `$carriers` — a tampered or since-deleted id refuses with `ModelNotFoundException` rather than a silent no-op.
- **No outbound network call anywhere in this story** (PRD §2.4 AC 5) — `ToggleShippingCarrier` is a pure database write, and `tests/Feature/Shipping/ToggleShippingCarrierTest.php` pins it with `Http::preventStrayRequests()`.
- ~~`/shipping` carries no sidebar registry entry yet~~ — **superseded by story 0037**, see below.

Eleven more consequences from story 0037's own rate-CRUD UI:

- **`ShippingRatePolicy` (story 0036) gains its first real call sites here.** `mount()` also authorizes `Gate::authorize('viewAny', ShippingRate::class)` alongside the carrier check, discharging that policy's own documented hand-off (its docblock and [architecture/shipping.md](../architecture/shipping.md) both name this screen as `viewAny`'s consumer — Phase 4/5 finding, appsec-auditor F-6 / code-reviewer L3). Every mutating method — `openCreateRateModal()` → `create`, `openEditRateModal()`/`saveRate()`'s edit branch/`confirmDeleteRate()`/`deleteRate()` → `update`/`delete` against a freshly `findOrFail()`d target — re-authorizes as a second layer on top of `CreateShippingRate`/`UpdateShippingRate`/`DeleteShippingRate`'s own self-authorization (0036 D-11).
- **`openEditRateModal()`, `saveRate()`'s edit branch and `confirmDeleteRate()`/`deleteRate()` all resolve the target BEFORE authorizing — deliberately the opposite of `toggleCarrier()`'s shape above, and this is not an inconsistency.** A Phase 4/5 finding (appsec-auditor F-2, echoed by code-reviewer) suggested mirroring `toggleCarrier()`'s "authorize against the raw id" shape here too; verified by direct execution that this does **not** generalise: `ShippingRatePolicy::update(User $actor, ShippingRate $target)` requires a real `ShippingRate` instance (unlike `toggleCarrier()`'s bare `shipping.edit` permission string, which Spatie resolves without ever touching a policy), so `Gate::authorize('update', ShippingRate::class)` throws a raw `ArgumentCountError` — *"Too few arguments … exactly 2 expected"* — for **every** caller regardless of permission, not an `AuthorizationException` for an unauthorized one. `App\Livewire\Shipping\Index::openEditRateModal()`'s own docblock records the reproduction. The 404-vs-403 oracle the suggestion worried about is real in principle but not fixable this way for a policy ability that takes a non-nullable model parameter.
- **The create/edit rate modal validates a snake_case array via `Validator::make()`, never `$this->validate()`.** `ShippingRateValidationRules::maxWeightRules()`'s `gte:min_weight_kg` rule looks up its comparison field by that exact key in the array under validation; Livewire's own `validate()` reads its data from the component's camelCase public properties, so calling it directly would silently break the cross-field lookup (confirmed by execution: camelCase data makes `gte:min_weight_kg` accept an invalid min=5/max=2 with zero errors). The resulting `ValidationException`'s error bag is therefore re-keyed from snake_case onto the component's own camelCase properties — `rethrowMappedValidationException()`, via a private `RATE_FIELD_MAP` — before it ever reaches Livewire's own exception handling, closing a real finding (appsec-auditor F-1 / code-reviewer L1): Livewire's `SupportValidation::dehydrate()` persists a `ValidationException` error into the *next* round trip only when its key passes `Utils::hasProperty($component, $key)`, a plain `property_exists()` with no snake↔camel mapping, so an un-re-keyed bag would silently drop six of the form's seven messages after one round trip (see [security/livewire-error-bag-persistence.md](../security/livewire-error-bag-persistence.md)). The same re-keying also restores Flux's automatic per-field `data-invalid` styling, so the view needs no explicit `<flux:error name="...">` elements at all — every field's own `:label` prop is what renders its error.
- **A validation `attributes` translation block (Phase 5 finding M1) is what stops `:attribute` humanizing the raw column name** ("The shipping carrier id field is required.") instead of the field's real label ("Carrier", "Maximum weight (kg)") — `lang/{en,es}/shipping.php`'s `rates.attributes` block, passed as `Validator::make()`'s 4th argument, matching [`lang/en/sales-regions.php`](../../lang/en/sales-regions.php)'s own `attributes` block precedent ([naming.md](../conventions/naming.md#translation-keys)'s documented exception).
- **A blank "no maximum weight" field is normalised to a real database `null` BEFORE `validate()` ever runs, never left to the validator's own rule chain.** Livewire opts every `/livewire/update` request out of Laravel's global `ConvertEmptyStringsToNull`/`TrimStrings` middleware, so a blank form field reaches the component as an untrimmed `''`, never `null`; Laravel's own validator then skips every non-implicit rule (`numeric`/`decimal`/`min`/`max`/`gte`) for a blank string via a *different* mechanism than `nullable`'s own null-check, so an un-normalised `''` would sail through validation untouched and reach a `DECIMAL(8,3)` column as a raw empty string — a 500 under MySQL strict mode, in every environment alike (this repo pins `mysql` everywhere; there is no SQLite/MySQL divergence). See [errors-log.md](../errors-log.md#livewire-skips-convertemptystringstonulltrimstrings-and-laravel-skips-non-implicit-rules-for-a-blank-string--the-two-combine-to-let-a-raw--reach-a-decimal-column--2026-09-10) for the full mechanism, verified against installed vendor source.
- **The rate table is grouped by carrier via `ListShippingRatesByCarrier`'s own eager-loaded query, never a PHP `->groupBy()` over a flat list** — a carrier with zero rates still renders its own (empty) group, and a disabled carrier's rates still render (`is_active` governs rate *resolution*, `App\Actions\Shipping\ResolveApplicableShippingRate`, never rate authoring or listing — D-4/D-9, confirmed unreferenced anywhere on this screen by both a dedicated arch-test line and the security audit's own grep).
- **Open-ended weight brackets render "N kg and above", never "N–null"** (D-8) — `maxWeightKg` stays a real `null` in the component's own array shape rather than being coerced to a string, so the view's null-check picks the right copy rather than string-concatenating a literal `null`.
- **Every `wire:*` id interpolation goes through `@js()` (single-argument) or `\Illuminate\Support\Js::from()` (the two-value carrier-toggle case)** — the established output-encoding rule ([security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md)); disabled row actions carry the same `data-test` hook on both branches, an explicit `<flux:tooltip>` wrapper, and `cursor-not-allowed!` on that wrapper — the two established Flux/Blaze traps this doc set already records, both avoided verbatim.
- **Its `data-test` hooks**: `new-rate-button` (disabled-branch tooltip when `! $this->canCreateRate`), `carrier-card-{id}`/`carrier-status-{id}`/`toggle-carrier-{id}` (story 0035's carrier cards, unchanged), `rates-empty-state` (only when every carrier has zero rates — a per-carrier zero-rate group renders `rate-group-empty-{carrierId}` instead, never the page-wide empty state), `rate-group-{carrierId}`, `rate-zone-{id}`/`rate-weight-{id}`/`rate-price-{id}`, `edit-rate-{id}`/`delete-rate-{id}` (both branches), and the create/edit modal's `rate-name-input`/`rate-carrier-select`/`rate-zone-select`/`manage-zones-link` (a secondary link to `shipping.zones.index`, OQ-C/D-10, so an administrator missing a zone never loses a half-filled rate form)/`rate-min-weight-input`/`rate-max-weight-input`/`rate-price-input`/`rate-delivery-estimate-input`/`save-rate-button`, plus the delete modal's `confirm-delete-rate-button`.
- **Every rate mutation writes a success audit line, not only a refusal one** (Phase 4 finding F-3) — `Log::info('Shipping rate created'|'Shipping rate updated'|'Shipping rate deleted', [...])` in `saveRate()`/`deleteRate()`, matching `App\Livewire\SalesRegions\Index`'s identical precedent for its own tax-rate changes (`shipping_rates.price` is the same kind of customer-facing financial configuration).
- **`/shipping` now carries a real sidebar registry entry**, correcting story 0035's own "no entry yet" note above: [`config/modules.php`](../../config/modules.php) gained `items.shipping_carriers` (icon kept, `route: 'shipping.index'`, `current_when: 'shipping.index'` — the **exact** route name, deliberately never a `shipping.*` wildcard, which would cross-highlight with `shipping.zones.index` — `permissions: ['shipping.view']`), nested in the same `store_settings` cluster `items.shipping_zones` already occupies, with matching `lang/{en,es}/navigation.php` leaves. `resources/views/components/sidebar-nav.blade.php` was not touched — the registry's "append data, never behavior" claim holding again.
