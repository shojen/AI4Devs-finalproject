### `payment-methods.index` — the eighth permission-gated route

Story 0038 (backend) and story 0039 (the real screen — the card grid, the edit modal, the sidebar entry), closing the identical 0004→0006 / 0017→0018 / 0033→0034 / 0035→0037 / 0028→0030 split this doc set has already recorded five times before. Declared in its own [`routes/payment-methods.php`](../../routes/payment-methods.php), the same shape every prior area file uses:

```php
// routes/payment-methods.php
use App\Livewire\PaymentMethods\Index as PaymentMethodsIndex;   // aliased: `Index` is ambiguous across areas,
// exactly like every other area file's own import
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:payment-methods.view`, not Spatie's `permission:` -- same reason as every other
    // gated route in this app. See docs/architecture/authorization.md.
    Route::livewire('payment-methods', PaymentMethodsIndex::class)
        ->middleware(['can:payment-methods.view'])
        ->name('payment-methods.index');
});
```

**Corrected 2026-09-10 (story 0039) — this subsection previously described story 0038's placeholder view, quoted rather than silently rewritten, per this project's audit-authored-page convention.** It used to read: *"The view behind it is a deliberate minimal placeholder. … exists only so `Livewire::test()` has something to render against. The real card/list + edit UI is the paired frontend story (0039) …"* and *"`/payment-methods` carries no sidebar registry entry yet. … Adding the `items.payment_methods` entry … is 0039's job, alongside the real screen."* Story 0039 is that story, closing both gaps.

Twelve consequences for anyone reading this table as a contract — the first three are story 0038's backend contract (unchanged), the rest story 0039's screen:

- **The middleware column understates what protects this route (same reason as `users.index`'s in [Users & Roles routes](users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** [`App\Livewire\PaymentMethods\Index`](../../app/Livewire/PaymentMethods/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`; `openEditModal()` — which discloses the stored IBAN, not only a mutating path — and `save()` each ask `update` against a freshly `findOrFail()`d target, routed through `App\Actions\Auth\LogRefusedPrivilegedAttempt` so the refusal is logged (Phase 4 security audit finding F-3).
- **The write path is protected twice over, and it was NOT designed that way from Phase 1 — this is the one place on this page where the retrofit is worth naming rather than only crediting.** `App\Actions\PaymentMethods\UpdatePaymentMethodIban` shipped with no authorization of its own, on the story's own (incorrect) reasoning that this repo's actions are generally unguarded; Phase 4's security audit found the premise false and the action now self-authorizes `update` as its own first statement — see [database/schema.md](../database/schema-other.md#updatepaymentmethodiban-self-authorizes--corrected-during-this-storys-own-phase-4-audit) for the corrected reasoning, quoted rather than silently rewritten per this project's audit-authored-page convention. A future Artisan command, queued job or Epic 3 order-flow caller now inherits the same refusal the dashboard gets, whichever of it or the component runs first.
- **`save()` writes a success audit line**, matching `App\Livewire\SalesRegions\Index`/`App\Livewire\Shipping\Index`'s own precedent for customer-facing financial configuration — the IBAN is the store's payout destination. The IBAN value itself is never logged.
- **The component's public surface, which story 0039's view consumes**: `$paymentMethods` (`#[Locked]` — entirely server-derived, rows of `{id, code, iban, canEdit}` — `code` is the real `App\Enums\PaymentMethodCode` enum instance, not its string value, so the view calls `$method['code']->label()` directly), the `#[Locked]` `$editingMethodId` (assigned only from `$target->id`, never the raw method argument), `$showModal`, and `$iban` — a plain `string`, never `null` (the never-`null`-property convention this doc set has recorded since the 2026-08-16 `<select>` desync bug). `mount()` / `openEditModal(string $methodId)` / `save()` / `closeModal()` are the whole method surface — **deliberately no `create*`/`delete*` method at all**: bank transfer is the only payment method this phase, and there is no code path anywhere that could add or remove one. `openEditModal()` was extended by story 0039 with one more statement, `$this->resetValidation('iban')`, as its own last line — see the error-bag bullet below.
- **The view behind it renders the whole screen** (story 0039). [`resources/views/livewire/payment-methods.blade.php`](../../resources/views/livewire/payment-methods.blade.php) — the *flat* path Livewire resolves for `App\Livewire\PaymentMethods\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name) — renders: a header naming the screen; a `grid grid-cols-1 sm:grid-cols-2` of `flux:card`s, one per payment method (bank transfer the only one this phase) — each card a heading (`$method['code']->label()`), a `flux:badge` (`lime` "Configured" / `zinc` "Not configured"), either the configured IBAN or a "not configured yet" placeholder, and a labelled Configure/Edit `flux:button` rendered enabled or disabled from that row's `canEdit`; and an edit modal, gated behind `@if ($showModal)` so only one "Cancel" control is ever in the DOM, holding a single `flux:input` bound to `iban`. **Cards, not a `flux:table`** — a deliberate divergence from Users/Roles/etc, decided because a future second payment method will almost certainly have a *different* configurable field than an IBAN, which a fixed-column table would have to absorb as conditional columns; a card renders its own field set, so a second method fills the next grid cell with no redesign.
- **No create or delete affordance exists anywhere in the markup, and none can be added client-side.** There is no button, no method, no route for either — `App\Policies\PaymentMethodPolicy::create()`/`delete()` both return `false` unconditionally (see [database/schema.md](../database/schema-other.md#payment_methods)), so there is no ability behind a control to gate in the first place. The view's own file-banner comment states this as the reason the screen has no such control, rather than an oversight.
- **The displayed IBAN is shown in full, unmasked, and grouped into 4-character blocks at render time only.** This is the store's own *receiving* account — §2.5 defines it as the address the store publishes to customers to transfer payment to, not a secret — so a reveal-to-view interaction would be ceremony protecting nothing. The grouping (`implode(' ', str_split($method['iban'], 4))`) is a pure render-time transform and never touches `$method['iban']` itself or the edit modal's `<flux:input wire:model="iban">`, which binds to the raw, unspaced value — 0038's own normalisation already tolerates spaced or unspaced input on the way in.
- **The outer configured-IBAN display reads the persisted row (`$paymentMethods`), never `$this->iban` — this is the screen's single highest-risk detail, and the reason story 0039 shipped a dedicated browser test (B2) rather than trusting the component-level suite alone.** `save()` mutates `$this->iban` to its normalised form *before* validating, so after a rejected submission that property still holds the rejected attempt. An implementation that rendered the outer summary from `$this->iban` — a plausible, lazy reuse — would display the rejected string as though it were the configured account, while every one of 0038's own tests (which assert `fresh()->iban`, i.e. the database) and even a component-level "the inline error renders" test would stay green regardless. Only a test reading the real page's outer display region after a real rejection catches this class of bug.
- **`data-test="payment-method-modal"` lives on the modal's INNER div, rendered only inside `@if ($showModal)`, never on the outer `<flux:modal>` tag — a markup rule worth generalising past this one screen.** Flux renders `<flux:modal>`'s own root unconditionally, open or closed, so a hook placed on that outer tag is always present in the DOM regardless of `$showModal`'s real value, making any "the modal remains open" / "the modal closed" assertion against it vacuously true. This was found and fixed during this story's own code review — put a modal's structural presence hook on content that is itself conditionally rendered, never on the Flux wrapper that always renders.
- **Its row action is a labelled text button, not icon-only** — unlike Users' row actions, its visible label ("Configure"/"Edit") is its own accessible name, so it needs no `aria-label`. Both the enabled and the disabled branch carry the identical `data-test="configure-bank-transfer"` hook, and the two Flux/Blaze markup traps this doc set already records for every other disabled row action are reused verbatim: an explicit `<flux:tooltip>` wrapper on the disabled branch rather than a conditionally-bound `tooltip` prop, and `cursor-not-allowed!` on that wrapper rather than on the `disabled:pointer-events-none` button. `wire:click="openEditModal(@js($method['id']))"` goes through `@js()`, mandatory rather than stylistic per [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md). Its `data-test` hooks in full: `payment-method-card-{id}` (each card), `configure-bank-transfer` (both branches), `payment-method-configured-iban`, `payment-method-not-configured`, `payment-method-modal` (the inner div, as above), `payment-method-iban-input`, `save-payment-method-button`.
- **`openEditModal()` clears the `iban` error bag as its own last statement, closing a bug that only became reachable once this story's real modal shipped.** Livewire persists a `ValidationException`'s error into the *next* round trip via `SupportValidation::dehydrate()`, so a refused save followed by re-opening the (single) edit modal — without going through `closeModal()`'s own `resetValidation()` — would have rendered a stale `iban` message with no context. Matches [security/livewire-error-bag-persistence.md](../security/livewire-error-bag-persistence.md)'s "every opener, not only every closer" rule, the identical shape `App\Livewire\Shipping\Zones`'s own delete-confirmation fix already established for a different property.
- **`/payment-methods` is now linked from the sidebar to a user holding `payment-methods.view`.** [`config/modules.php`](../../config/modules.php) gained an `items.payment_methods` entry nested in the same `store_settings` cluster `sales_regions`/`shipping_zones`/`shipping_carriers` already occupy (`group: null, cluster: 'store_settings'`, icon `credit-card`, `route: 'payment-methods.index'`, `current_when: 'payment-methods.*'`, `permissions` **exactly** `['payment-methods.view']`), with matching `lang/{en,es}/navigation.php` leaves. `resources/views/components/sidebar-nav.blade.php` was **not** touched — the registry's "append data, never behavior" claim holding again.
- **Copy is appended to the existing `lang/{en,es}/payment-methods.php` files rather than a new file** — 0038 already created them with `names`/`iban` groups; 0039 adds `index` (`heading`, `configured_label`, `not_configured_label`, `configure_action`, `edit_action`, `action_not_allowed`) and `editor` (`title`, `iban_label`, `iban_description`) groups, mirroring `lang/en/users.php`'s `index`/`editor` split. The pre-existing `iban.not_configured` key is reused verbatim for the card's not-configured placeholder rather than duplicated under a new name — resolving the backend story's own open question (OQ-2) by reading the file it actually shipped.
