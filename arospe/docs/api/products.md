### `product-categories.index` — the fourth permission-gated route

Story 0025, this screen's own doc-sync pass. The first UI story to call [`ProductCategoryPolicy`](../architecture/authorization.md#productcategorypolicy--the-fifth-policy-and-the-first-to-gain-its-call-site-in-a-later-story-than-the-one-that-created-it) and the three `app/Actions/ProductCategories/*` actions story 0023 shipped with no consumer. Declared in its own [`routes/product-categories.php`](../../routes/product-categories.php), the same shape `users.index`/`roles.index`/`sales-regions.index` use:

```php
// routes/product-categories.php
use App\Livewire\ProductCategories\Index as ProductCategoriesIndex;   // aliased: `Index` is ambiguous across areas,
// exactly like routes/roles.php's and routes/sales-regions.php's own imports
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as
    // users.index / roles.index / sales-regions.index: Livewire 4's
    // PersistentMiddleware allowlist carries Laravel's `Authorize` (`can:`)
    // but not Spatie's `PermissionMiddleware`, so a `permission:`-gated
    // route would protect the initial GET only, leaving every
    // save()/deleteProductCategory() /livewire/update round-trip
    // unauthorized. See docs/architecture/authorization.md.
    Route::livewire('product-categories', ProductCategoriesIndex::class)
        ->middleware(['can:products.view'])
        ->name('product-categories.index');
});
```

Eleven consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route (same reason as `users.index`'s in [Users & Roles routes](users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** [`App\Livewire\ProductCategories\Index`](../../app/Livewire/ProductCategories/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`, `openCreateModal()`/`save()` ask `create` (or `update` on `save()`'s edit branch), `openEditModal()` asks `update` against a freshly resolved target, and `confirmDelete()`/`deleteProductCategory()` ask `delete` against a freshly resolved target. **All five methods gate**, matching [security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — the story's own OQ-4 had asked whether the two disclosure-only openers needed to gate at all, recommending "follow the shipped Users precedent" of gating only `save()`/`deleteUser()`, but that recommendation cited a snapshot of `Users\Index` from the story's 2026-08-18 Three Amigos debate, before task 0015 (closed 2026-08-24) added authorization to `Users\Index`'s own three modal openers. The shipped screen here gates every opener, which is consistent with the *current* Users precedent rather than the stale one OQ-4 described.
- **The write path is protected twice over, and — like `sales-regions.index` — it was designed that way rather than retrofitted.** All three domain actions — [`CreateProductCategory`](../../app/Actions/ProductCategories/CreateProductCategory.php), [`RenameProductCategory`](../../app/Actions/ProductCategories/RenameProductCategory.php), [`DeleteProductCategory`](../../app/Actions/ProductCategories/DeleteProductCategory.php) — now authorize their own operation as their first statement, discharging the hand-off story 0023 recorded (see [database/schema.md](../database/schema-products.md#product_categories)). Each constructor-injects `App\Actions\Auth\LogRefusedPrivilegedAttempt` and passes `targetType: 'product_category'` explicitly, since `resolveTarget()` auto-resolves only `User` and `Role` instances. A future Artisan command, queued job or REST controller inherits the identical refusal the dashboard gets.
- **In `DeleteProductCategory`, the new authorization call runs *before* the in-use product count, and the order is load-bearing.** The in-use block ([database/schema.md § `product_categories`](../database/schema-products.md#product_categories)) is a domain invariant, not an authorization rule, and stays a `ValidationException` rather than a `Gate` denial — but the count it discloses is data, and computing it before the `delete` gate has run would leak the number to an actor who does not even hold `products.delete`. Reversing the order would turn a clean 403 into a business message ("this category is used by 12 products") available to anyone reaching the method.
- **The component's public surface**: `$productCategories` (deliberately **unlocked** — display-only, documented in its own docblock, the identical rationale [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md) already records for `Users\Index::$users`: every mutating method re-reads its target with `findOrFail()` and re-authorizes, so nothing here is ever read for a decision), the `#[Locked]` `$editingCategoryId` (assigned only from `$target->id`, never the raw method argument — what makes the id fed to `ProductCategoryValidationRules::uniqueNormalisedName()`'s `->ignore()` server-authoritative), `$showModal`, the plain `string $name` form field (never `?string`), and the delete-modal trio `$showDeleteModal`/`#[Locked] $deletingCategoryId`/`#[Locked] $deletingCategoryName`.
- **The view behind it renders the whole screen.** [`resources/views/livewire/product-categories.blade.php`](../../resources/views/livewire/product-categories.blade.php) — the **flat** path Livewire resolves for `App\Livewire\ProductCategories\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name) — renders: a header with a primary "New category" button (no live count/summary line — OQ-2 resolved "no header summary", since nothing in the PRD or the brief asked for one and, unlike Users, there is no second dimension to summarise); a `flux:table` of categories (name, product count, and icon-only edit/delete row actions rendered enabled or disabled from that row's `canEdit`/`canDelete`); a create/edit modal whose only field is `name`; a delete-confirmation modal naming the target; and an explicit empty state (`data-test="product-categories-empty-state"`) when the catalog is empty. Both modals' inner content is wrapped in `@if ($showModal)` / `@if ($showDeleteModal)` so only one "Cancel" control is ever in the DOM, matching `users.blade.php`/`roles.blade.php`.
- **The product count is shown but is never used to disable the delete action.** `loadProductCategories()`'s `productCount` (from `withCount('products')`) is purely informational — pre-disabling delete on `productCount > 0` would visually conflate the in-use refusal (a domain invariant) with the `canEdit`/`canDelete` authorization UI hint, which exists precisely to mirror what a `Gate::authorize()` call would do. Letting the actor attempt the delete and read the exact count in the modal is what satisfies the PRD's own wording, which requires the *message* to state the count.
- **The blocked-delete refusal renders inline in the still-open delete modal.** `deleteProductCategory()` carries no `try`/`catch` around the action call — `DeleteProductCategory`'s `ValidationException`, keyed on `productCategoryId`, is the one exception Livewire already routes into the component's error bag with no plumbing at the call site, and the throw aborts the method before `closeDeleteModal()` ever runs, which is what keeps the modal open by construction rather than by an explicit flag. The view binds `@error('productCategoryId')` to a `<flux:callout variant="danger" data-test="product-category-delete-blocked">`, the same non-field-error-key pattern `settings/security.blade.php`'s `@error('setupData')` block already establishes. `closeDeleteModal()` also calls `resetErrorBag('productCategoryId')`, or a stale block message would leak into the next delete attempt on a different, unblocked category.
- **No confirm-and-proceed or force-delete control exists anywhere on the screen, and none can be added client-side.** `DeleteProductCategory::__invoke()` takes no `bool $force` parameter — the refusal is architecturally impossible to bypass from the UI, not merely absent from this screen's markup (story 0024b's D-14).
- **Its row actions are icon-only, so they are not selectable by visible text.** Each carries an `aria-label` plus a `data-test="edit-product-category-{id}"` / `data-test="delete-product-category-{id}"` hook, present on **both** the enabled and the disabled branch, so a test selects the same control regardless of state. Both `wire:click` arguments are passed through `@js(...)` — mandatory, not stylistic, since a value interpolated into a `wire:*` attribute lands in a JavaScript evaluator that undoes Blade's HTML escaping (see [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md)). The two Flux/Blaze markup rules `users.blade.php`/`roles.blade.php`/`sales-regions.blade.php` already established are reused verbatim: an explicit `<flux:tooltip>` wrapper on the disabled branch rather than a conditionally-bound `:tooltip` prop, and `cursor-not-allowed!` on that wrapper rather than on the `pointer-events-none` disabled button — both documented in [errors-log.md](../errors-log.md).
- **`canEdit`/`canDelete` per row are UI hints, never a layer, and they cannot drift from what a click would do.** `loadProductCategories()` writes `Gate::allows('update'|'delete', $category)` onto each row — the *same* policy methods `save()`/`deleteProductCategory()` authorize against — following [Gate::allows() in a list query is a UI hint, not a layer](../architecture/authorization.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer). Like `SalesRegionPolicy`, `ProductCategoryPolicy::update()`/`delete()` ignore their target entirely, so this hint has **no accepted drift** — a property of the policy having no target-dependent branch, not a guarantee.
- **`/product-categories` is linked from the sidebar only to a user holding `products.view`.** [`config/modules.php`](../../config/modules.php) gained an `items.product_categories` entry (icon `tag`, `route` `product-categories.index`, `current_when` `product-categories.*`, `permissions` **exactly** `['products.view']` — the single ability the route's own `can:` enforces), with matching leaves in `lang/{en,es}/navigation.php`. [`resources/views/layouts/app/sidebar.blade.php`](../../resources/views/layouts/app/sidebar.blade.php) was **not** touched by story 0025 — this is the registry's "append data, never behavior" claim holding for a fourth entry in a row, following the mechanism task 0013 built. Nothing about the route's contract changed — hiding the link is presentation only. **It shipped as a flat item in the `groups.platform` group; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `products` and `product_attribute_types` — see [`architecture/authorization.md`](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema.

### `products.index`, `products.create` and `products.edit` — the fifth permission-gated route family

Story 0027, this screen's own doc-sync pass. The first UI story to call [`ProductPolicy`](../architecture/authorization.md#productpolicy--the-sixth-policy-and-the-second-built-entirely-for-a-screen-that-does-not-exist-yet)'s `viewAny` ability, and the first to give every one of the four Products-domain shared components (`Media\Gallery`, `Components\WysiwygEditor`, `Components\SearchableMultiSelect`, `ProductPolicy` itself) a real caller at once. Declared in a new [`routes/products.php`](../../routes/products.php), the same shape the other five area files use — the first to put **two routes on one component**:

```php
// routes/products.php
use App\Livewire\Products\Editor as ProductEditor;
use App\Livewire\Products\Index as ProductsIndex;
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as every other gated
    // area file: Livewire 4's PersistentMiddleware allowlist carries `can:` but not
    // `permission:`, so every /livewire/update round-trip would run unauthorized under the
    // latter. The finer create/update/delete abilities are authorized inside the components.
    Route::livewire('products', ProductsIndex::class)
        ->middleware(['can:products.view'])
        ->name('products.index');

    Route::livewire('products/create', ProductEditor::class)
        ->middleware(['can:products.view'])
        ->name('products.create');

    Route::livewire('products/{product}/edit', ProductEditor::class)
        ->middleware(['can:products.view'])
        ->name('products.edit');
});
```

**`products.create` and `products.edit` resolve the same `App\Livewire\Products\Editor` class**, which branches on whether `mount()` received a route-model-bound `Product` — the first repeat of a component across two route names in this app (`routes/roles.php`, `sales-regions.php` and `product-categories.php` all alias their one `Index` import for a different reason, ambiguity across areas; here the ambiguity is the *second* route needing the identical component). `Route::livewire()` is a plain `Route::get()` macro, so route-model binding behaves normally and `HasUuids` makes a malformed non-UUID `{product}` a 404 before any query runs.

Thirteen consequences for anyone reading this table as a contract:

- **The middleware column understates what protects these routes (same reason as `users.index`'s in [Users & Roles routes](users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** Both components re-authorize on every method that mutates or discloses. `Products\Index::mount()` asks `viewAny`; `confirmDelete()`/`deleteProduct()` ask `delete` against a freshly `findOrFail()`d target. `Products\Editor::mount()`, `save()` and the two gallery-selection listeners (`setFeaturedImage()`, `addGalleryImages()`) each authorize their own first statement — `create`/`update` on `Product` for `mount()`/`save()`, `viewAny` on `Media::class` for the two listeners (see the `WysiwygEditor` subsection below for why a page-globally-registered `#[On]` listener needs its own gate rather than trusting the host page's `@can` wrapper).
- **`Editor::mount()`'s gate is reachable over HTTP, unlike `Index::mount()`'s.** `Index::mount()` asks `viewAny`, the *same* ability the route's own `can:products.view` already enforces, so a real HTTP actor who would fail it never reaches `mount()` at all — the check is only reachable through a direct `Livewire::test()` call. `Editor::mount()` asks the *finer* `create`/`update` ability: an actor holding only `products.view` passes the route's coarser middleware and reaches `mount()`, where they are refused — a refusal that **is** reachable over HTTP and is logged through `LogRefusedPrivilegedAttempt` for exactly that reason.
- **`ProductPolicy` now has real call sites for all four abilities.** `viewAny` (this story's `mount()`s), `create`/`update` (`Editor::mount()`/`save()`, layered over `CreateProduct`/`UpdateProduct`'s own self-authorization) and `delete` (`Index::confirmDelete()`/`deleteProduct()`, layered over `DeleteProduct`'s). See [architecture/authorization.md](../architecture/authorization.md#productpolicy--the-sixth-policy-and-the-second-built-entirely-for-a-screen-that-does-not-exist-yet) for what "layered over" means here — every gate in this story is a **second** layer, not the only one, since 0024's actions self-authorize.
- **The list query is explicit-column and eager-loaded, never `SELECT *`.** `Products\Index::products()` selects nine named columns (never `description` — a `MEDIUMTEXT` inline in the clustered index the list never renders), eager-loads `category:id,name` and `featuredImage:id,title,path,webp_path,avif_path`, orders by `name` then `id` (the tiebreak, since only `sku` is unique), and paginates at 25 — the first Products-domain screen with real pagination, unlike `Users\Index`/`ProductCategories\Index`'s unpaginated bounded lists.
- **The thumbnail is built from 0019's real column names, at the query site, mirroring `Gallery::toPayloadItem()`.** There is no `url()`-style accessor on `App\Models\Media` — every URL is `Storage::disk('public')->url($media->path)` (and the `webp`/`avif` siblings), built once inside `products()`'s `->through()` closure and again inside `Editor::toPreview()`, never left to the Blade view to reach into the model.
- **Three `wire:model`-bound selects, three different "never-`null`" answers, all load-bearing against the same errors-log incident every prior select in this app already avoids.** `$productCategoryId` is `''` (the placeholder match); `$status` is a **plain string** defaulting to `ProductStatus::Draft->value` (not a typed enum — Livewire's `EnumSynth` hydrates a forged backing value through `$type::from($value)` **before** validation runs, the identical reason `Users\Index::$status` was retyped away from an enum at task 0015 finding F8); `$type` is a **plain string** defaulting to `''` with **no** legitimate default at all — 0024 states categorically that no fallback type may ever be applied on a product's behalf, so the type select's placeholder `<option>` carries both `disabled` and `selected`, the one new markup rule this screen adds to the set below.
- **Imagery and region assignment are wired through two independent `Gallery` embeds, one `WysiwygEditor`, and one `SearchableMultiSelect`, all inside `@can('viewAny', \App\Models\Media::class)` where they touch media.** The featured-image picker (`select-event="featured-image-selected"`) and the gallery-strip picker (`select-event="product-images-added"`, multi-select) are direct embeds with distinct literal event names — the same two literals [`Gallery`'s own subsection](#applivewiremediagallery--a-gated-surface-with-no-route-and-how-a-consumer-embeds-it) already names as this screen's published contract; the WYSIWYG's own internal gallery derives its event name per instance (0021 D5). **Corrected 2026-09-06 (story 0031) — this bullet used to end "so three `Gallery` instances on one page never cross-wire"; it is now four.** `App\Livewire\Products\VariantBuilder` (see below) embeds one more `Gallery` instance of its own, `select-event="variant-image-selected"` — a fourth distinct literal, so **four** `Gallery` instances render on `products.edit` at once (two of `Editor`'s own, one of `WysiwygEditor`'s, one of `VariantBuilder`'s) and none cross-wire. The region picker is `<livewire:components.searchable-multi-select :option-resolver="\App\Actions\Products\SearchSalesRegions::class" wire:model="regionIds" .../>`, the exact class-string 0022's own consumer example names.
- **`products.edit` also embeds `App\Livewire\Products\VariantBuilder` (story 0031) — a nested child of `Editor`, not a new route of its own.** `resources/views/livewire/products/editor.blade.php` mounts it below a `flux:separator`, only once a product exists: `<livewire:products.variant-builder :product-id="$productId" wire:key="variant-builder-{{ $productId }}" />` when `$productId !== null`, and a `flux:callout` naming `products.variants.builder.requires_saved_product` in its place on `products.create` — the builder is unreachable on the create route by construction (0031 D-1), not merely hidden by a permission check. It re-authorizes `update` on the parent `Product` as the first statement of nine of its ten public methods (`openCreateForm`, `openEditForm`, `saveVariant`, `addCombinationRow`, `removeCombinationRow`, `confirmDelete`, `deleteVariant`, `revertToInheritedImage`, the Gallery listener `setVariantImage`) — the tenth, `mount()`, asks the coarser `viewAny` instead — through a **bare** `Gate::authorize()`, not `App\Actions\Auth\LogRefusedPrivilegedAttempt`, the one place a `products.*` screen on this page diverges from `Products\Index`'s/`Editor`'s own logged-refusal shape, matching the story's own D-10 pseudocode exactly. `ProductPolicy` now has real call sites on a **third** screen — see [architecture/authorization.md](../architecture/authorization.md#product-variant-actions-gate-against-the-parent-product-not-a-new-policy) for the corrected section recording it. **Corrected 2026-09-07 (story 0031a) — the gated-method count above is superseded, not merely extended.** This bullet's "nine of its ten public methods" was 0031's own count. Story 0031a composes its cartesian-combination-generator UI onto this **same** component and view — no second Livewire component, no new route, no new `docs/api/routes.md` row — and adds **two** more gated methods, `openGenerateModal()` and `generateCombinations()`, each `Gate::authorize('update', $this->product())` as its own first statement, the identical bare (not `LogRefusedPrivilegedAttempt`-logged) shape the nine before them already use. The count is now **eleven of its twelve public methods** authorizing `update` on the parent product — the twelfth, `mount()`, still asks the coarser `viewAny`. The generator's own axis-picker modal opens **no** `media.gallery` instance at all: it is a plain `flux:checkbox.group` over the already-loaded `attributeTypes()` catalog (`GenerateProductVariantCombinations`, story 0029b, acquiring its first and only UI call site), so the "four `Gallery` instances on `products.edit`" count two bullets above is unaffected by this story.
- **The gallery strip's order is an in-memory array until save; reorder ships as buttons, not drag.** `moveGalleryImageEarlier()`/`moveGalleryImageLater()` swap two elements in `$galleryMediaIds`/`$galleryPreviews` and touch nothing else — no query, no pivot write. `save()` resubmits the complete array to `CreateProduct`/`UpdateProduct` on every save, which reach `SyncProductGallery` internally and rewrite every row's `position` from the array's 0-based index. `SyncProductGallery` is **never called directly from `Editor`** — the ordered array goes *into* the two core actions, discharging 0024's own hand-off.
- **The region-id array and the gallery-id array are each validated in two sequential `Validator::make(...)->validate()` calls, never one combined rule array.** This discharges 0026's own Definition-of-Done hand-off for `regionIds` (`salesRegionIdsRules()` alone, then `regionIds.*` against `salesRegionIdRules($preserved)`, `$preserved` read server-side from `$product->salesRegions` and never the request) and extends the identical shape to `galleryMediaIds` on this story's own finding — Laravel expands a `.*` wildcard against every submitted element regardless of whether the parent array's own `max:` rule already failed, so a single combined call pays one `Rule::exists()` query per submitted id before the size cap is ever consulted. Full mechanism, the measured numbers and a second, sharper finding (a cap on the *array* is not a cap on the *loop* — `addGalleryImages()`'s own mutation-point query count) are on [security/array-validation-bounds.md](../security/array-validation-bounds.md#story-0027-the-two-pass-shape-is-only-half-the-bound--the-mutation-point-needs-one-too).
- **The whole save is one `DB::transaction()`, opened after every validation step and after the mandatory `resolveSelected()` re-check, and closed here because this is the only place all three writers compose.** `CreateProduct`/`UpdateProduct` (which reach `SyncProductGallery`) and `SyncProductSalesRegions` all run inside it; a `ValidationException` never travels through an open transaction, since every check that can fail on ordinary input runs before the transaction opens. This discharges 0026's own Definition-of-Done hand-off item 4.
- **Every Flux/Blaze markup trap this doc set has already recorded recurs here, and one narrows in the finding.** The tooltip-presence trap and the `cursor-not-allowed!`-on-the-wrapper rule are reused verbatim on both screens' disabled row/reorder actions; every id in a `wire:*` argument goes through `@js()` unconditionally. The gallery strip's two reorder buttons use `:disabled="$index === 0"` / `:disabled="$index === count($galleryPreviews) - 1"` directly on a `<flux:button>` tag — a **colon-bound** attribute expression, not the bare `@disabled(...)` **directive call** the errors-log's 2026-08-31 entry documents as breaking the whole compiled view; the two forms are not equivalent to `livewire/blaze`'s tag compiler, and this story's own Phase 5 review is what narrowed that entry. See [errors-log.md](../errors-log.md#a-bare-disableddisabled-inside-a-fluxbutton-tags-attribute-list-corrupts-the-whole-compiled-view--2026-08-31).
- **`/products` is linked from the sidebar only to a user holding `products.view`.** [`config/modules.php`](../../config/modules.php) gained an `items.products` entry (icon `cube`, `route` `products.index`, `current_when` `products.*` — so the item stays highlighted on `products.create`/`products.edit` too — `permissions` **exactly** `['products.view']`), with matching leaves in `lang/{en,es}/navigation.php`. `resources/views/layouts/app/sidebar.blade.php` was **not** touched by story 0027 — the fifth confirmation in a row that a module registry entry costs data, not template edits. **It shipped as a flat item in the `groups.platform` group; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `product_categories` and `product_attribute_types` — its own name coincides with the cluster's, but per the story's own Q-1 it is just another equal cluster child, never the cluster's "home" link (the cluster carries no `route`/`current_when` of its own). See [`architecture/authorization.md`](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema.

**This story also retires the one route this page used to deliberately keep out of the table.** `dev.media-gallery-harness` — story 0020's temporary, environment-gated scaffolding, extended by story 0021 to also host a `WysiwygEditor` instance — existed only because neither `Gallery` nor `WysiwygEditor` had a real page to be browser-tested against. `App\Livewire\Products\Editor` is that real page: both of the harness's browser test files (`tests/Browser/Media/GalleryTest.php`, `tests/Browser/Components/WysiwygEditorTest.php`) were re-pointed at `route('products.create')`/`route('products.edit', $product)` and made green against it, with the re-entrancy assertions strengthened rather than merely migrated (the WYSIWYG's own per-instance event name now competes against **two** real literals on the same page, not a second copy of itself). ### `product-attribute-types.index` — the fifth permission-gated route

Story 0028 (backend) and story 0030 (the real screen, replacing the backend-only placeholder — the same 0017→0018 split, closed the identical way). `App\Livewire\Products\AttributeTypes\Index` holds authorization, validation and action wiring in full (0028); [`resources/views/livewire/products/attribute-types.blade.php`](../../resources/views/livewire/products/attribute-types.blade.php) (0030) is the real markup, not the one-line placeholder this subsection used to describe. Declared in its own [`routes/product-attribute-types.php`](../../routes/product-attribute-types.php), the same shape every prior area file uses:

```php
// routes/product-attribute-types.php
use App\Livewire\Products\AttributeTypes\Index as ProductAttributeTypesIndex;   // aliased: `Index` is
// ambiguous across areas, exactly like every other area file's own import
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as every other
    // gated route in this app: Livewire 4's PersistentMiddleware allowlist carries
    // Laravel's `Authorize` (`can:`) but not Spatie's `PermissionMiddleware`, so a
    // `permission:`-gated route would protect the initial GET only, leaving every
    // save()/deleteType() /livewire/update round-trip unauthorized. See
    // docs/architecture/authorization.md.
    Route::livewire('products/attribute-types', ProductAttributeTypesIndex::class)
        ->middleware(['can:products.view'])
        ->name('product-attribute-types.index');
});
```

Thirteen consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route (same reason as `users.index`'s in [Users & Roles routes](users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** [`App\Livewire\Products\AttributeTypes\Index`](../../app/Livewire/Products/AttributeTypes/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`, `openCreateModal()`/`save()` (create branch) ask `create`, `openEditModal()`/`save()` (edit branch) ask `update` against a freshly resolved target, and `confirmDelete()`/`deleteType()` ask `delete` against a freshly resolved target. **All six methods gate**, matching [security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — including `openEditModal()`, which discloses the type's whole value list before any write.
- **The write path is protected twice over, designed that way from Phase 1 rather than retrofitted.** All three domain actions — [`CreateProductAttributeType`](../../app/Actions/Products/CreateProductAttributeType.php), [`UpdateProductAttributeType`](../../app/Actions/Products/UpdateProductAttributeType.php), [`DeleteProductAttributeType`](../../app/Actions/Products/DeleteProductAttributeType.php) — authorize their own operation as their first statement, each constructor-injecting `App\Actions\Auth\LogRefusedPrivilegedAttempt` and passing `targetType: 'product_attribute_type'` explicitly (`resolveTarget()` auto-resolves only `User` and `Role`). A fourth action in the same folder, `App\Actions\Products\SyncProductAttributeValues`, deliberately authorizes **nothing** — the codebase's fifth shipped instance of "a collaborator invoked only by an already-authorized action needs no gate of its own"; see [architecture/authorization.md](../architecture/authorization.md#productattributetypepolicy--the-seventh-policy-and-the-first-whose-no-policy-recommendation-was-reversed-at-phase-2).
- **`Index` resolves to this screen's own subfolder-shaped flat view, per the established exception.** `App\Livewire\Products\AttributeTypes\Index` drops the `.index` segment and resolves to [`resources/views/livewire/products/attribute-types.blade.php`](../../resources/views/livewire/products/attribute-types.blade.php) — one level *shallower* than the class, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name). **Since story 0030 this is the real screen**, mirroring `product-categories.blade.php`'s shape: a header with `typesSummary()`'s live `:total types · :values values` count and a primary "New attribute type" button; a `flux:table` of types (name, a value-count badge, a truncated value preview — the first five values joined with a `+N more` suffix built from `valueCount`, an em dash for a zero-value type — and icon-only edit/delete row actions, `data-test="edit-type-{id}"` / `"delete-type-{id}"`, rendered enabled or disabled from that row's `canEdit`/`canDelete`); a create/edit modal holding the name field plus a hand-rolled values repeater (no Flux repeater primitive exists) — each row a stable-`wire:key`, `chevron-up`/`chevron-down`/`trash` icon-only trio, `data-test` hooks keyed by the value's own database id when it has one (`$row['id'] ?? $row['key']`, since a test that seeded the fixture knows the id ahead of time but never the row's UI-only `key`, a fresh UUID minted on every `openEditModal()`/`addValue()` call); and a delete-confirmation modal reading `$deletingTypeName`.
- **The `@continue` guard skipping a malformed `$values` row must check every key the loop dereferences, not only the row's outer type** — a Phase 4 security-audit finding (F-1) fixed within this story rather than deferred: `$values` (and `$showModal`) are both client-writable, so a `products.view`-only actor can force this branch open with a forged row shape before `save()`'s own validation ever runs, and a row that *is* an array but is missing `key`, or whose `value` is non-scalar, crashed the render until the guard was widened to `@continue(! is_array($row) || ! isset($row['key']) || ! is_string($row['key']) || ! isset($row['value']) || ! is_string($row['value']))`.
- **The component's public surface**: `$types` (`#[Locked]` — entirely server-derived, the *stronger* side of the `#[Locked]` convention rather than `ProductCategories\Index::$productCategories`'s documented unlocked exception, since nothing here needs to be client-writable and locking costs nothing), the `#[Locked]` `$editingTypeId` (assigned only from `$target->id`, never the raw method argument — what makes the id fed to `attributeTypeNameRules()`'s `->ignore()` server-authoritative), `$showModal`, the plain `string $name` field, the deliberately **not** `#[Locked]` `array $values` (the form's own client-writable input, re-scoped against a fresh database read on every save — see [database/schema.md](../database/schema-products.md#product_attribute_values)), the delete-modal trio `$showDeleteModal`/`#[Locked] $deletingTypeId`/`#[Locked] $deletingTypeName`/`#[Locked] $deletingTypeUsageCount` (real since story 0029a, not story 0030's own doing — `confirmDelete()` populates it from `App\Models\ProductAttributeType::variantUsageCount()`, the same query `App\Actions\Products\DeleteProductAttributeType`'s own in-use block consumes; see [database/schema.md](../database/schema-products.md#product_attribute_types)), and — since story 0030a — the `#[Locked] array $valueUsageCounts` (`array<string, int>`, keyed by value id), populated once per `openEditModal()` call and reset alongside `$values` in both `closeModal()`/`openCreateModal()`. This view renders `$deletingTypeUsageCount` only inside the reactive blocked-delete message below, never as a proactive line in the confirmation dialog, matching `product-categories.blade.php`'s identical choice for its own in-use block.
- **Since story 0030a, `openEditModal()` also computes a per-row usage notice with one bulk query, never one query per row.** [`App\Models\ProductAttributeValue::variantUsageCounts()`](../../app/Models/ProductAttributeValue.php) is called once with the type's own value ids and assigned to `$valueUsageCounts` — see [database/schema.md](../database/schema-products.md#product_attribute_values) for how this bulk, display-oriented query differs from the type-level and per-value in-use queries story 0029a already shipped over the same pivot. The values repeater renders a muted, **non-blocking** `trans_choice('products.variants.rename_notice', ...)` notice beside any row whose count is positive, `data-test="value-in-use-notice-{id}"` — keyed by the row's own persisted id (the same `$rowHook` convention every other hook in this repeater already uses, never the row's UI-only, freshly-minted `key`). A row with no persisted id yet (an `addValue()`-created row) never renders the notice; the count read is guarded the same way `$rowHook` itself is, to avoid a PHP deprecation notice on undefined-key array access rather than crash.
- **A fourth `@error(...)` outlet, keyed `sku`, renders whichever refusal 0029's already-shipped SKU re-derivation cascade throws when a rename changes a derived SKU** — `derived_sku_taken`, `derived_sku_empty_segment`, `derived_sku_too_long`, or the translated unique-violation race message, all already produced by `SyncProductAttributeValues::reDeriveVariantSkusForRenamedValues()`/`DeriveVariantSku::checked()` (story 0029, unchanged here) and reused as-is with **no new translation key**. One generic `<flux:callout>`, styled like the two existing `@error('values')`/`@error('productAttributeTypeId')` precedents immediately beside it, renders whichever message fires with no per-message branching — the modal stays open and nothing is written, since 0029's transaction rolls back the whole rename on any of the four. Its `:heading="$message"` binding is deliberately **colon-bound**, unlike its two older siblings' `heading="{{ $message }}"` form: the double-brace form double-HTML-encodes a literal quote character inside `$message` under this Flux-folded tag (verified by `Blade::render()` execution), which is exactly what `derived_sku_empty_segment`'s own copy — the one message of the four containing a literal quote — exposes. This is a latent, pre-existing, non-security quirk on the two older callouts, left unchanged since neither's current copy contains a quote.
- **Both modal openers now call `resetValidation()` as their own last statement**, closing a Phase 4 audit finding: dismissing the modal via its `wire:model`-bound `$showModal` directly — the X control or a click outside, bypassing `closeModal()` entirely — left a stale `sku`/`values` error from a previously refused save rendering against a different, unrelated type on reopen, since Livewire persists the error bag across that round trip.
- **Two in-use guards story 0029a added to the backend now have their rendering, discharging that story's own explicit hand-off** ("the markup rendering the blocked-delete message is 0030's"). Deleting a type still backing any product variant throws a `ValidationException` keyed `productAttributeTypeId` — rendered as a `flux:callout` inside the still-open delete modal, the identical `@error('productAttributeTypeId')` pattern `product-categories.blade.php` already established for its own in-use block, naming the exact variant count via `trans_choice('products.variants.type_in_use', ...)`. Removing a value still backing any variant throws on the whole-array key `values` (not a per-row key, since the guard runs after the diff has already decided which ids are being deleted) — rendered as a `flux:callout` inside the still-open create/edit modal via `@error('values')`, naming the count via `products.variants.value_in_use`. Both refusals leave every other field's edits in place, since the whole save is one transaction that never partially applies (D-A5).
- **`removeValue()` and `moveValue()` take a stable, server-generated `key`, never an array index** — the single most important detail the UI sibling story inherits. Each value row is assigned `(string) Str::uuid()` once, when the row is created (`addValue()`, or read from the database in `openEditModal()`), and that key is what `wire:key` and every row-targeting method argument must use. Removing row 1 by *index* would shift row 2 into index 1, reuse the DOM node keyed `1`, and leave the browser's own input showing the old value while the server holds the new one — the standard Livewire foot-gun this design avoids entirely rather than works around.
- **`canEdit`/`canDelete` per row are UI hints, never a layer, and cannot drift from what a click would do.** `loadTypes()` writes `Gate::allows('update'|'delete', $type)` onto each row — the *same* policy methods `save()`/`deleteType()` authorize against. Like `SalesRegionPolicy`/`ProductCategoryPolicy`, `ProductAttributeTypePolicy::update()`/`delete()` ignore their target entirely, so this hint has **no accepted drift** — a property of the policy having no target-dependent branch, not a guarantee.
- **Two of this screen's `ValidationException`s are not row-shaped errors a naive read would expect.** A duplicate value within the same type surfaces as a validation error on `values.*.value` (`distinct:ignore_case`, run only after the array's size and each row's shape have already passed — see [database/schema.md](../database/schema-products.md#product_attribute_values)'s Phase 4 findings subsection), never as an unhandled `QueryException` reaching the caller; and a race that slips past `distinct:ignore_case` is caught at the composite `UNIQUE(product_attribute_type_id, value)` index by `SyncProductAttributeValues`, which converts SQLSTATE `23000` into the identical `ValidationException` shape rather than letting a raw database error surface.
- **Since story 0030 this route has a `config/modules.php` entry** (`items.product_attribute_types`, gated on exactly `['products.view']`) and matching `lang/{en,es}/navigation.php` leaves — closing the linkless half-state the App-owned-routes preamble above records, the same split `sales-regions.index` sat in between tasks 0017 and 0018. **It shipped as a flat `group: platform` item; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `products` and `product_categories`.

### `App\Livewire\Media\Gallery` — a gated surface with no route, and how a consumer embeds it

Story 0019 (the backend) and story 0020 (the modal itself). **There is no row for this in [routes.md](routes.md#app-owned-routes)'s app-owned route table and there never will be one**: [PRD §2.3](../PRD/PRD.md) makes the Shared Media Gallery a component Products and Blog *embed*, not a page. It is documented here anyway because it is the app's first contract surface that is real, permission-gated and **invisible to `php artisan route:list`** — a reader auditing "what is reachable and what protects it" from the table alone would miss it entirely.

**The consumer contract (story 0020's D2) is the deliverable, because stories 0021 and 0027 bind to it without re-deciding any of it.** Four attributes and one listener is the *entire* integration surface:

```blade
{{-- D12: the consumer decides whether the child renders at all. --}}
@can('viewAny', \App\Models\Media::class)
    <livewire:media.gallery
        wire:model="showFeaturedGallery"
        wire:key="featured-image-gallery"
        :multi="false"
        select-event="featured-image-selected"
        :confirm-label="__('products.featured_image.confirm_label')"
    />
@endcan
```

```php
#[On('featured-image-selected')]
public function setFeaturedImage(array $media): void { /* $media[0] */ }
```

Nine consequences for anyone binding to this, or adding a method to it:

- **`@can` at the consumer site is a *layer*, not the gate.** A bare `Gate::authorize('viewAny', …)` in `mount()` with no wrapper would **403 the entire host page** for anyone who can reach the product editor but lacks `media.view` — an unrelated-permission failure dressed up as a security control. The wrapper is what makes the child's absence graceful; the component's own gates are what make it safe. Hiding a control is never the control ([security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)).
- **Every method that discloses or mutates re-authorizes on *every* round trip, and this is stricter than a routed screen needs to be.** `mount()`, `toggleSelect()`, `confirmSelection()` ask `viewAny`; `startEditing()` and `updateMediaDetails()` ask `update`; `upload()` asks `create`. All six log their refusal through `App\Actions\Auth\LogRefusedPrivilegedAttempt`. This is [story 0020's Phase 4 finding **F-1** (Medium)](../architecture/authorization.md#a-routeless-livewire-component-has-no-per-request-authorization-backstop): the first implementation gated `mount()` only — sufficient for `users.index`/`roles.index`/`sales-regions.index`, whose routes' `can:` **is** replayed on `/livewire/update`, and **not** sufficient here, where nothing is.
- **`tiles()` fails *closed* instead of throwing, and that asymmetry is deliberate.** It is reached from `render()`, where an `AuthorizationException` would take down the **host** page — exactly what the `@can` layer exists to prevent — so a revoked actor gets an empty array. The two explicit user actions next to it (`toggleSelect()`, `confirmSelection()`) throw and log like every other screen in this app.
- **The event name is consumer-supplied, and that is forced rather than stylistic.** `$this->dispatch($name)` fires a bubbling DOM event routed by Livewire's own `#[On($name)]`; `->to(Gallery::class)` was **verified impossible** for this purpose — `dispatchTo()` resolves by *component name*, so it broadcasts to **every** mounted `Gallery`, and story 0027's product editor embeds two. Two instances on one page must not receive each other's selection.
- **The payload is one shape in both modes — always a list**, `array<int, array{id, title, description, url, webpUrl, avifUrl, width, height}>`. Single-select dispatches a list of exactly one (`$media[0]`); a bare object for single mode was rejected so a listener's signature never depends on a prop set elsewhere. It is **re-fetched from the database at confirm time**, never assembled from what the grid rendered, so a tampered or since-deleted id is silently dropped rather than erroring.
- **`$search` is the only client-writable property besides `$pendingUploads`** and the inline-edit fields; `$multi`, `$selectEvent`, `$confirmLabel`, `$selectedIds` and `$editingMediaId` are all `#[Locked]`. `$open` is the `#[Modelable]` boolean the host toggles, and `cancel()`/`confirmSelection()` close the modal from this side by writing it.
- **Two caps, neither of which may ever drop a staged selection.** The grid renders at most **60** tiles, `latest()` first, with a `data-test="media-results-truncated"` notice when it truncates; one upload batch carries at most **3** files (`MAX_FILES`, lowered from 5 by a Phase 4 re-audit that *measured* five 4000×4000 encodes at **34.8 s** against PHP's 30 s `max_execution_time` default — three measured ~21 s). `$selectedIds` is component state, never a projection of the rendered grid, so neither cap nor a search filter can touch it; the footer count is the only on-screen evidence a filtered-out tile is still staged.
- **Its `data-test` hooks, all icon-only or dynamic and therefore not selectable by visible text**: `media-search`, `media-upload-button`, `media-dropzone`, `media-upload-progress-transport` / `media-upload-progress-processing` (D8's two distinct in-flight phases — only the first has a percentage), `media-tile-{id}` (carrying `aria-pressed`, the assertable selection state — never a CSS class), `media-selection-count`, `media-results-truncated`, `media-empty-state`, `media-cancel`, `media-confirm`, and the inline editor's `edit-media-{id}` / `edit-media-form-{id}` / `save-media-{id}` / `cancel-edit-media-{id}`. Every id interpolated into a `wire:*` argument goes through `@js()` ([security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md)), and a disabled control's tooltip is a written-out `<flux:tooltip>` wrapper on its own branch — both traps [errors-log.md](../errors-log.md) records, reused verbatim.
- ⚠️ **A role without `media.view` loses the gallery silently.** Under the `@can` wrapper there is no "Add image" affordance, no error and no explanation — the host screen simply has one fewer control. Latent today (every seeded `Administrator` holds all four `media.*` permissions), and real the moment custom roles become common. Recorded here rather than discovered in support.

### `App\Livewire\Components\WysiwygEditor` — the gallery's first real consumer, and the second routeless gated component

Story 0021. **This is also not in [routes.md](routes.md#app-owned-routes)'s app-owned route table and never will be**: same reasoning as `Gallery` immediately above it — no route, reached only over `/livewire/update`, embedded by a host screen. It is worth its own subsection rather than a bullet under `Gallery`'s because it sits **one layer further out**: `WysiwygEditor` *is* a `Gallery` consumer (it embeds `<livewire:media.gallery>` itself, single-select, D4 in the story's own task file), and it is in turn embedded by the product/blog editors that are `WysiwygEditor`'s own consumers — [0027](../../ai-spec/tasks/done/0027-products-list-and-editor-ui.md), [0061](../../ai-spec/tasks/0061-blog-posts-core-crud-backend.md), [0077](../../ai-spec/tasks/0077-product-editor-language-tabs-ui.md) and [0079](../../ai-spec/tasks/0079-blog-post-editor-language-tabs-ui.md). A reusable rich-text toolbar (Bold, Italic, Underline, H2, bullet list, numbered list, link, "Insert image") whose output is HTML a future column stores; the eight-action set and the exact tag set it may emit are fixed by [PRD §2.3](../PRD/PRD.md#23-shared-media-gallery)'s design reference and by the story's own D2, not repeated here.

```blade
<livewire:components.wysiwyg-editor
    wire:model="description"
    wire:key="product-description-editor"
    :label="__('products.description_label')"
/>
```

Seven consequences for anyone binding to this, or adding a method to it:

- **`$value` (the `#[Modelable]` HTML) is deliberately not `#[Locked]`, for the same reason `Gallery`'s `$search` is not** — it is the model binding a consumer's own `wire:model` writes through, and it is untrusted HTML by construction. **This is a hard, load-bearing dependency rather than a detail to skim**: nothing in this component sanitizes `$value` — it cannot, without duplicating [0024a](../../ai-spec/tasks/done/0024a-product-description-html-sanitization.md)'s `symfony/html-sanitizer` allow-list — so **no consumer may bind `wire:model` to a persisted column until that column's own write path runs a server-side sanitizer first.** **Corrected 2026-09-02 (story 0024a)** — this bullet previously credited "0027 and 0077" with already discharging the dependency "via `SanitizeProductDescription` in their `Create`/`UpdateProduct` actions", written speculatively before that class existed and naming the wrong stories as its origin: `CreateProduct`/`UpdateProduct` are [0024](../../ai-spec/tasks/done/0024-products-core-crud-backend.md)'s own actions, and 0027 has none of its own. `App\Actions\Products\SanitizeProductDescription` is **0024a's** class, and its first two real call sites are 0024's `CreateProduct` and `UpdateProduct` — sanitizing `description` before validation on every write — which is what actually discharges this dependency for `products.description` today. See [security/html-sanitization.md](../security/html-sanitization.md) for the mechanism. **Confirmed 2026-09-03 (story 0027):** the product editor binds `<livewire:components.wysiwyg-editor wire:model="description" .../>` and its `save()` calls `CreateProduct`/`UpdateProduct` for every write — no second write path was opened, so it inherited the guarantee for free exactly as predicted rather than needing a sanitizer call of its own; **0061, 0076, 0077 and 0079 remain not yet built**, each recording its own planned use of the class in its own task file (0061 reusing this exact config for the blog `body` column, 0076 adding a second call site behind a model-event layer, 0077/0079 each constructor-injecting the class directly into a Livewire component) rather than being a verified consumer today.
- **The component embeds its own `Gallery` child, `@can`-wrapped exactly as 0020's D12 requires of any embedder**, single-select (`:multi="false"`) — "insert one image at the cursor" has no multi-select reading. The "Insert image" toolbar button itself is **not** hidden for a user lacking `media.view`; it renders `disabled` inside an explicit `<flux:tooltip>` (the tooltip-presence Flux/Blaze trap applies here too — see [errors-log.md](../errors-log.md)), matching every other disabled-row-action convention in this app. The other seven toolbar actions are pure client-side formatting and are unaffected by media permissions.
- **The embedded gallery's `select-event` is derived per mount, never a literal — and this corrects the rationale story 0020's own D2 states for why two galleries on one page never cross-wire.** 0020 D2 credits "DOM bubbling plus `#[On(...)]`" with the disambiguation; that is not the real mechanism. Livewire registers **every** `#[On]`/`$listeners` entry as a page-global `window.addEventListener(name, handler)`, for every mounted component instance — the event **name string** is the only thing separating two listeners, verified directly against `vendor/livewire/livewire/dist/livewire.js`. A component that nests a re-entrant `Gallery` child with a **fixed** literal `select-event` would have every mounted instance receive every other instance's confirmed image the moment a second one is mounted on the same page (a product's short and long description, say). `WysiwygEditor::mount()` derives `'wysiwyg-image-selected-'.$this->getId()` instead, and the matching `#[On('{galleryEvent}')]` on `insertImage()` resolves the whole placeholder from the component's own persisted state on every request — not merely its first one, which matters because `insertImage()` is reached from a **separate** `/livewire/update` round trip than `mount()`, after the modal has already opened. **Any future component nesting a re-entrant `Gallery` (or any other child whose confirm event must not cross-wire) must derive a per-instance-unique event name the same way — a fixed literal is a name collision waiting for a second mounted instance, and it will not show up in a single-instance test.**
- **`openGallery()` and `insertImage()` gate themselves as their own first statement** — `Gate::authorize('viewAny', Media::class)` via `App\Actions\Auth\LogRefusedPrivilegedAttempt`, matching `Gallery`'s own routeless-component pattern ([security/livewire-authorization.md](../security/livewire-authorization.md#the-routeless-case-a-component-with-no-route-has-no-per-request-backstop-at-all)) rather than trusting the host page's `@can` wrapper to be the only perimeter (a Phase 4 security-audit fix, finding F-2 — the first implementation gated neither method). `insertImage()` additionally **re-fetches** the selected item from `Media::query()->find(...)` rather than trusting the client-supplied `url`/`title` fields — the same "derive, never accept" rule `Gallery::confirmSelection()` already follows for its own dispatch payload — so a tampered, malformed or since-deleted id collapses to a silent no-op.
- **The editable region is `wire:ignore`d — the app's first use of that directive.** Livewire must never diff or re-render a `contenteditable` region a user is actively typing into, or it fights the browser's own editing. The convention this establishes (a client-owned region, seeded from the server once and synced back at defined points only, never continuously) is documented in [conventions/base-standards.md](../conventions/base-standards.md#a-wireignored-client-owned-region--the-apps-first-instance). One consequence a consumer must know: because the region is `wire:ignore`d, **a server-side write to `$value` does not appear in the editor** — a consumer resetting its form by nulling the bound property sees the editor keep its old content. There is no programmatic content-replacement hook.
- **Its `data-test` hooks are static strings, and the component's own root carries a per-instance scoping hook**: `data-test="wysiwyg-editor-{{ $this->getId() }}"` on the outermost `<div>`, with every toolbar/region hook (`wysiwyg-bold`, `wysiwyg-italic`, `wysiwyg-underline`, `wysiwyg-h2`, `wysiwyg-bullet-list`, `wysiwyg-numbered-list`, `wysiwyg-link`, `wysiwyg-link-url`, `wysiwyg-link-apply`, `wysiwyg-insert-image`, `wysiwyg-editor-region`) present on every mounted instance — exactly the same duplication trap [playwright-setup.md](../testing/frontend/playwright-setup.md#a-page-embedding-the-same-component-twice-duplicates-every-data-test-hook) already documents for `Gallery`. A browser test against a page mounting two editors must scope its selector to the containing instance's root, never query a hook page-wide.
- ⚠️ **Every button on the toolbar is written as a full `@if ($disabled) … @else … @endif` pair of separately-compiled `<flux:button>` tags, never one tag carrying a conditional `@disabled(...)` directive.** A bare `@disabled(...)` directive call inside a Flux component tag's attribute list does not compile there the way it would on a plain HTML tag — it corrupts the whole tag's attribute string into invalid PHP, a syntax error breaking the entire compiled view. **Narrowed 2026-09-04 (story 0027):** a colon-bound `:disabled="..."` attribute expression is *not* the same shape and is safe on a `<flux:*>` tag at any value — `resources/views/livewire/products/editor.blade.php`'s gallery-reorder buttons use exactly that form and render correctly, verified by execution. Only a `@directive(...)` call written where an attribute is expected breaks. See [errors-log.md](../errors-log.md#a-bare-disableddisabled-inside-a-fluxbutton-tags-attribute-list-corrupts-the-whole-compiled-view--2026-08-31).
