# Products & Media Routes — product-categories.index

> Part of [Products & Media Routes](../products.md). **Read this part when:** the task touches the product categories screen. The other parts are listed in the [hub](../products.md#table-of-contents).

### `product-categories.index` — the fourth permission-gated route

Story 0025, this screen's own doc-sync pass. The first UI story to call [`ProductCategoryPolicy`](../../architecture/authorization/policies-sales-media-categories.md#productcategorypolicy--the-fifth-policy-and-the-first-to-gain-its-call-site-in-a-later-story-than-the-one-that-created-it) and the three `app/Actions/ProductCategories/*` actions story 0023 shipped with no consumer. Declared in its own [`routes/product-categories.php`](../../../routes/product-categories.php), the same shape `users.index`/`roles.index`/`sales-regions.index` use:

```php
// routes/product-categories.php
use App\Livewire\ProductCategories\Index as ProductCategoriesIndex;   // aliased: `Index` is ambiguous across areas,
// exactly like routes/roles.php's and routes/sales-regions.php's own imports
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as
    // users.index / roles.index / sales-regions.index: Livewire 4's
    // PersistentMiddleware allowlist carries Laravel's `Authorize` (`can:`)
    // but not Spatie's `PermissionMiddleware`, so a `permission:`-gated
    // route would protect the initial GET only, leaving every
    // save()/deleteProductCategory() /livewire/update round-trip
    // unauthorized. See docs/architecture/authorization.md.
    Route::livewire('product-categories', ProductCategoriesIndex::class)
        ->middleware(['can:products.view'])
        ->name('product-categories.index');
});
```

Eleven consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route (same reason as `users.index`'s in [Users & Roles routes](../users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** [`App\Livewire\ProductCategories\Index`](../../../app/Livewire/ProductCategories/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`, `openCreateModal()`/`save()` ask `create` (or `update` on `save()`'s edit branch), `openEditModal()` asks `update` against a freshly resolved target, and `confirmDelete()`/`deleteProductCategory()` ask `delete` against a freshly resolved target. **All five methods gate**, matching [security/livewire-authorization.md](../../security/livewire-authorization/entry-point-and-method-gates.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — the story's own OQ-4 had asked whether the two disclosure-only openers needed to gate at all, recommending "follow the shipped Users precedent" of gating only `save()`/`deleteUser()`, but that recommendation cited a snapshot of `Users\Index` from the story's 2026-08-18 Three Amigos debate, before task 0015 (closed 2026-08-24) added authorization to `Users\Index`'s own three modal openers. The shipped screen here gates every opener, which is consistent with the *current* Users precedent rather than the stale one OQ-4 described.
- **The write path is protected twice over, and — like `sales-regions.index` — it was designed that way rather than retrofitted.** All three domain actions — [`CreateProductCategory`](../../../app/Actions/ProductCategories/CreateProductCategory.php), [`RenameProductCategory`](../../../app/Actions/ProductCategories/RenameProductCategory.php), [`DeleteProductCategory`](../../../app/Actions/ProductCategories/DeleteProductCategory.php) — now authorize their own operation as their first statement, discharging the hand-off story 0023 recorded (see [database/schema.md](../../database/schema-products/categories-and-products.md#product_categories)). Each constructor-injects `App\Actions\Auth\LogRefusedPrivilegedAttempt` and passes `targetType: 'product_category'` explicitly, since `resolveTarget()` auto-resolves only `User` and `Role` instances. A future Artisan command, queued job or REST controller inherits the identical refusal the dashboard gets.
- **In `DeleteProductCategory`, the new authorization call runs *before* the in-use product count, and the order is load-bearing.** The in-use block ([database/schema.md § `product_categories`](../../database/schema-products/categories-and-products.md#product_categories)) is a domain invariant, not an authorization rule, and stays a `ValidationException` rather than a `Gate` denial — but the count it discloses is data, and computing it before the `delete` gate has run would leak the number to an actor who does not even hold `products.delete`. Reversing the order would turn a clean 403 into a business message ("this category is used by 12 products") available to anyone reaching the method.
- **The component's public surface**: `$productCategories` (deliberately **unlocked** — display-only, documented in its own docblock, the identical rationale [security/blade-livewire-output-encoding.md](../../security/blade-livewire-output-encoding.md) already records for `Users\Index::$users`: every mutating method re-reads its target with `findOrFail()` and re-authorizes, so nothing here is ever read for a decision), the `#[Locked]` `$editingCategoryId` (assigned only from `$target->id`, never the raw method argument — what makes the id fed to `ProductCategoryValidationRules::uniqueNormalisedName()`'s `->ignore()` server-authoritative), `$showModal`, the plain `string $name` form field (never `?string`), and the delete-modal trio `$showDeleteModal`/`#[Locked] $deletingCategoryId`/`#[Locked] $deletingCategoryName`.
- **The view behind it renders the whole screen.** [`resources/views/livewire/product-categories.blade.php`](../../../resources/views/livewire/product-categories.blade.php) — the **flat** path Livewire resolves for `App\Livewire\ProductCategories\Index`, per the [`Index`-in-a-subfolder exception](../../conventions/naming/livewire-components-and-views.md#exception-a-component-named-index-resolves-to-its-parent-folders-name) — renders: a header with a primary "New category" button (no live count/summary line — OQ-2 resolved "no header summary", since nothing in the PRD or the brief asked for one and, unlike Users, there is no second dimension to summarise); a `flux:table` of categories (name, product count, and icon-only edit/delete row actions rendered enabled or disabled from that row's `canEdit`/`canDelete`); a create/edit modal whose only field is `name`; a delete-confirmation modal naming the target; and an explicit empty state (`data-test="product-categories-empty-state"`) when the catalog is empty. Both modals' inner content is wrapped in `@if ($showModal)` / `@if ($showDeleteModal)` so only one "Cancel" control is ever in the DOM, matching `users.blade.php`/`roles.blade.php`.
- **The product count is shown but is never used to disable the delete action.** `loadProductCategories()`'s `productCount` (from `withCount('products')`) is purely informational — pre-disabling delete on `productCount > 0` would visually conflate the in-use refusal (a domain invariant) with the `canEdit`/`canDelete` authorization UI hint, which exists precisely to mirror what a `Gate::authorize()` call would do. Letting the actor attempt the delete and read the exact count in the modal is what satisfies the PRD's own wording, which requires the *message* to state the count.
- **The blocked-delete refusal renders inline in the still-open delete modal.** `deleteProductCategory()` carries no `try`/`catch` around the action call — `DeleteProductCategory`'s `ValidationException`, keyed on `productCategoryId`, is the one exception Livewire already routes into the component's error bag with no plumbing at the call site, and the throw aborts the method before `closeDeleteModal()` ever runs, which is what keeps the modal open by construction rather than by an explicit flag. The view binds `@error('productCategoryId')` to a `<flux:callout variant="danger" data-test="product-category-delete-blocked">`, the same non-field-error-key pattern `settings/security.blade.php`'s `@error('setupData')` block already establishes. `closeDeleteModal()` also calls `resetErrorBag('productCategoryId')`, or a stale block message would leak into the next delete attempt on a different, unblocked category.
- **No confirm-and-proceed or force-delete control exists anywhere on the screen, and none can be added client-side.** `DeleteProductCategory::__invoke()` takes no `bool $force` parameter — the refusal is architecturally impossible to bypass from the UI, not merely absent from this screen's markup (story 0024b's D-14).
- **Its row actions are icon-only, so they are not selectable by visible text.** Each carries an `aria-label` plus a `data-test="edit-product-category-{id}"` / `data-test="delete-product-category-{id}"` hook, present on **both** the enabled and the disabled branch, so a test selects the same control regardless of state. Both `wire:click` arguments are passed through `@js(...)` — mandatory, not stylistic, since a value interpolated into a `wire:*` attribute lands in a JavaScript evaluator that undoes Blade's HTML escaping (see [security/blade-livewire-output-encoding.md](../../security/blade-livewire-output-encoding.md)). The two Flux/Blaze markup rules `users.blade.php`/`roles.blade.php`/`sales-regions.blade.php` already established are reused verbatim: an explicit `<flux:tooltip>` wrapper on the disabled branch rather than a conditionally-bound `:tooltip` prop, and `cursor-not-allowed!` on that wrapper rather than on the `pointer-events-none` disabled button — both documented in [errors-log.md](../../errors-log.md).
- **`canEdit`/`canDelete` per row are UI hints, never a layer, and they cannot drift from what a click would do.** `loadProductCategories()` writes `Gate::allows('update'|'delete', $category)` onto each row — the *same* policy methods `save()`/`deleteProductCategory()` authorize against — following [Gate::allows() in a list query is a UI hint, not a layer](../../architecture/authorization/grant-meta-rules-and-ui-hints.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer). Like `SalesRegionPolicy`, `ProductCategoryPolicy::update()`/`delete()` ignore their target entirely, so this hint has **no accepted drift** — a property of the policy having no target-dependent branch, not a guarantee.
- **`/product-categories` is linked from the sidebar only to a user holding `products.view`.** [`config/modules.php`](../../../config/modules.php) gained an `items.product_categories` entry (icon `tag`, `route` `product-categories.index`, `current_when` `product-categories.*`, `permissions` **exactly** `['products.view']` — the single ability the route's own `can:` enforces), with matching leaves in `lang/{en,es}/navigation.php`. [`resources/views/layouts/app/sidebar.blade.php`](../../../resources/views/layouts/app/sidebar.blade.php) was **not** touched by story 0025 — this is the registry's "append data, never behavior" claim holding for a fourth entry in a row, following the mechanism task 0013 built. Nothing about the route's contract changed — hiding the link is presentation only. **It shipped as a flat item in the `groups.platform` group; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `products` and `product_attribute_types` — see [`architecture/authorization.md`](../../architecture/authorization/how-to-gate.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema.
