# Products & Media Routes — products.index / .create / .edit

> Part of [Products & Media Routes](../products.md). **Read this part when:** the task touches the products list or the product create/edit editor. The other parts are listed in the [hub](../products.md#table-of-contents).

### `products.index`, `products.create` and `products.edit` — the fifth permission-gated route family

Story 0027, this screen's own doc-sync pass. The first UI story to call [`ProductPolicy`](../../architecture/authorization/policies-products.md#productpolicy--the-sixth-policy-and-the-second-built-entirely-for-a-screen-that-does-not-exist-yet)'s `viewAny` ability, and the first to give every one of the four Products-domain shared components (`Media\Gallery`, `Components\WysiwygEditor`, `Components\SearchableMultiSelect`, `ProductPolicy` itself) a real caller at once. Declared in a new [`routes/products.php`](../../../routes/products.php), the same shape the other five area files use — the first to put **two routes on one component**:

```php
// routes/products.php
use App\Livewire\Products\Editor as ProductEditor;
use App\Livewire\Products\Index as ProductsIndex;
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as every other gated
    // area file: Livewire 4's PersistentMiddleware allowlist carries `can:` but not
    // `permission:`, so every /livewire/update round-trip would run unauthorized under the
    // latter. The finer create/update/delete abilities are authorized inside the components.
    Route::livewire('products', ProductsIndex::class)
        ->middleware(['can:products.view'])
        ->name('products.index');

    Route::livewire('products/create', ProductEditor::class)
        ->middleware(['can:products.view'])
        ->name('products.create');

    Route::livewire('products/{product}/edit', ProductEditor::class)
        ->middleware(['can:products.view'])
        ->name('products.edit');
});
```

**`products.create` and `products.edit` resolve the same `App\Livewire\Products\Editor` class**, which branches on whether `mount()` received a route-model-bound `Product` — the first repeat of a component across two route names in this app (`routes/roles.php`, `sales-regions.php` and `product-categories.php` all alias their one `Index` import for a different reason, ambiguity across areas; here the ambiguity is the *second* route needing the identical component). `Route::livewire()` is a plain `Route::get()` macro, so route-model binding behaves normally and `HasUuids` makes a malformed non-UUID `{product}` a 404 before any query runs.

Thirteen consequences for anyone reading this table as a contract:

- **The middleware column understates what protects these routes (same reason as `users.index`'s in [Users & Roles routes](../users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** Both components re-authorize on every method that mutates or discloses. `Products\Index::mount()` asks `viewAny`; `confirmDelete()`/`deleteProduct()` ask `delete` against a freshly `findOrFail()`d target. `Products\Editor::mount()`, `save()` and the two gallery-selection listeners (`setFeaturedImage()`, `addGalleryImages()`) each authorize their own first statement — `create`/`update` on `Product` for `mount()`/`save()`, `viewAny` on `Media::class` for the two listeners (see the `WysiwygEditor` subsection below for why a page-globally-registered `#[On]` listener needs its own gate rather than trusting the host page's `@can` wrapper).
- **`Editor::mount()`'s gate is reachable over HTTP, unlike `Index::mount()`'s.** `Index::mount()` asks `viewAny`, the *same* ability the route's own `can:products.view` already enforces, so a real HTTP actor who would fail it never reaches `mount()` at all — the check is only reachable through a direct `Livewire::test()` call. `Editor::mount()` asks the *finer* `create`/`update` ability: an actor holding only `products.view` passes the route's coarser middleware and reaches `mount()`, where they are refused — a refusal that **is** reachable over HTTP and is logged through `LogRefusedPrivilegedAttempt` for exactly that reason.
- **`ProductPolicy` now has real call sites for all four abilities.** `viewAny` (this story's `mount()`s), `create`/`update` (`Editor::mount()`/`save()`, layered over `CreateProduct`/`UpdateProduct`'s own self-authorization) and `delete` (`Index::confirmDelete()`/`deleteProduct()`, layered over `DeleteProduct`'s). See [architecture/authorization.md](../../architecture/authorization/policies-products.md#productpolicy--the-sixth-policy-and-the-second-built-entirely-for-a-screen-that-does-not-exist-yet) for what "layered over" means here — every gate in this story is a **second** layer, not the only one, since 0024's actions self-authorize.
- **The list query is explicit-column and eager-loaded, never `SELECT *`.** `Products\Index::products()` selects nine named columns (never `description` — a `MEDIUMTEXT` inline in the clustered index the list never renders), eager-loads `category:id,name` and `featuredImage:id,title,path,webp_path,avif_path`, orders by `name` then `id` (the tiebreak, since only `sku` is unique), and paginates at 25 — the first Products-domain screen with real pagination, unlike `Users\Index`/`ProductCategories\Index`'s unpaginated bounded lists.
- **The thumbnail is built from 0019's real column names, at the query site, mirroring `Gallery::toPayloadItem()`.** There is no `url()`-style accessor on `App\Models\Media` — every URL is `Storage::disk('public')->url($media->path)` (and the `webp`/`avif` siblings), built once inside `products()`'s `->through()` closure and again inside `Editor::toPreview()`, never left to the Blade view to reach into the model.
- **Three `wire:model`-bound selects, three different "never-`null`" answers, all load-bearing against the same errors-log incident every prior select in this app already avoids.** `$productCategoryId` is `''` (the placeholder match); `$status` is a **plain string** defaulting to `ProductStatus::Draft->value` (not a typed enum — Livewire's `EnumSynth` hydrates a forged backing value through `$type::from($value)` **before** validation runs, the identical reason `Users\Index::$status` was retyped away from an enum at task 0015 finding F8); `$type` is a **plain string** defaulting to `''` with **no** legitimate default at all — 0024 states categorically that no fallback type may ever be applied on a product's behalf, so the type select's placeholder `<option>` carries both `disabled` and `selected`, the one new markup rule this screen adds to the set below.
- **Imagery and region assignment are wired through two independent `Gallery` embeds, one `WysiwygEditor`, and one `SearchableMultiSelect`, all inside `@can('viewAny', \App\Models\Media::class)` where they touch media.** The featured-image picker (`select-event="featured-image-selected"`) and the gallery-strip picker (`select-event="product-images-added"`, multi-select) are direct embeds with distinct literal event names — the same two literals [`Gallery`'s own subsection](routeless-components.md#applivewiremediagallery--a-gated-surface-with-no-route-and-how-a-consumer-embeds-it) already names as this screen's published contract; the WYSIWYG's own internal gallery derives its event name per instance (0021 D5). **Corrected 2026-09-06 (story 0031) — this bullet used to end "so three `Gallery` instances on one page never cross-wire"; it is now four.** `App\Livewire\Products\VariantBuilder` (see below) embeds one more `Gallery` instance of its own, `select-event="variant-image-selected"` — a fourth distinct literal, so **four** `Gallery` instances render on `products.edit` at once (two of `Editor`'s own, one of `WysiwygEditor`'s, one of `VariantBuilder`'s) and none cross-wire. The region picker is `<livewire:components.searchable-multi-select :option-resolver="\App\Actions\Products\SearchSalesRegions::class" wire:model="regionIds" .../>`, the exact class-string 0022's own consumer example names.
- **`products.edit` also embeds `App\Livewire\Products\VariantBuilder` (story 0031) — a nested child of `Editor`, not a new route of its own.** `resources/views/livewire/products/editor.blade.php` mounts it below a `flux:separator`, only once a product exists: `<livewire:products.variant-builder :product-id="$productId" wire:key="variant-builder-{{ $productId }}" />` when `$productId !== null`, and a `flux:callout` naming `products.variants.builder.requires_saved_product` in its place on `products.create` — the builder is unreachable on the create route by construction (0031 D-1), not merely hidden by a permission check. It re-authorizes `update` on the parent `Product` as the first statement of nine of its ten public methods (`openCreateForm`, `openEditForm`, `saveVariant`, `addCombinationRow`, `removeCombinationRow`, `confirmDelete`, `deleteVariant`, `revertToInheritedImage`, the Gallery listener `setVariantImage`) — the tenth, `mount()`, asks the coarser `viewAny` instead — through a **bare** `Gate::authorize()`, not `App\Actions\Auth\LogRefusedPrivilegedAttempt`, the one place a `products.*` screen on this page diverges from `Products\Index`'s/`Editor`'s own logged-refusal shape, matching the story's own D-10 pseudocode exactly. `ProductPolicy` now has real call sites on a **third** screen — see [architecture/authorization.md](../../architecture/authorization/policies-variants-and-routeless.md#product-variant-actions-gate-against-the-parent-product-not-a-new-policy) for the corrected section recording it. **Corrected 2026-09-07 (story 0031a) — the gated-method count above is superseded, not merely extended.** This bullet's "nine of its ten public methods" was 0031's own count. Story 0031a composes its cartesian-combination-generator UI onto this **same** component and view — no second Livewire component, no new route, no new `docs/api/routes.md` row — and adds **two** more gated methods, `openGenerateModal()` and `generateCombinations()`, each `Gate::authorize('update', $this->product())` as its own first statement, the identical bare (not `LogRefusedPrivilegedAttempt`-logged) shape the nine before them already use. The count is now **eleven of its twelve public methods** authorizing `update` on the parent product — the twelfth, `mount()`, still asks the coarser `viewAny`. The generator's own axis-picker modal opens **no** `media.gallery` instance at all: it is a plain `flux:checkbox.group` over the already-loaded `attributeTypes()` catalog (`GenerateProductVariantCombinations`, story 0029b, acquiring its first and only UI call site), so the "four `Gallery` instances on `products.edit`" count two bullets above is unaffected by this story.
- **The gallery strip's order is an in-memory array until save; reorder ships as buttons, not drag.** `moveGalleryImageEarlier()`/`moveGalleryImageLater()` swap two elements in `$galleryMediaIds`/`$galleryPreviews` and touch nothing else — no query, no pivot write. `save()` resubmits the complete array to `CreateProduct`/`UpdateProduct` on every save, which reach `SyncProductGallery` internally and rewrite every row's `position` from the array's 0-based index. `SyncProductGallery` is **never called directly from `Editor`** — the ordered array goes *into* the two core actions, discharging 0024's own hand-off.
- **The region-id array and the gallery-id array are each validated in two sequential `Validator::make(...)->validate()` calls, never one combined rule array.** This discharges 0026's own Definition-of-Done hand-off for `regionIds` (`salesRegionIdsRules()` alone, then `regionIds.*` against `salesRegionIdRules($preserved)`, `$preserved` read server-side from `$product->salesRegions` and never the request) and extends the identical shape to `galleryMediaIds` on this story's own finding — Laravel expands a `.*` wildcard against every submitted element regardless of whether the parent array's own `max:` rule already failed, so a single combined call pays one `Rule::exists()` query per submitted id before the size cap is ever consulted. Full mechanism, the measured numbers and a second, sharper finding (a cap on the *array* is not a cap on the *loop* — `addGalleryImages()`'s own mutation-point query count) are on [security/array-validation-bounds.md](../../security/array-validation-bounds/story-history.md#story-0027-the-two-pass-shape-is-only-half-the-bound--the-mutation-point-needs-one-too).
- **The whole save is one `DB::transaction()`, opened after every validation step and after the mandatory `resolveSelected()` re-check, and closed here because this is the only place all three writers compose.** `CreateProduct`/`UpdateProduct` (which reach `SyncProductGallery`) and `SyncProductSalesRegions` all run inside it; a `ValidationException` never travels through an open transaction, since every check that can fail on ordinary input runs before the transaction opens. This discharges 0026's own Definition-of-Done hand-off item 4.
- **Every Flux/Blaze markup trap this doc set has already recorded recurs here, and one narrows in the finding.** The tooltip-presence trap and the `cursor-not-allowed!`-on-the-wrapper rule are reused verbatim on both screens' disabled row/reorder actions; every id in a `wire:*` argument goes through `@js()` unconditionally. The gallery strip's two reorder buttons use `:disabled="$index === 0"` / `:disabled="$index === count($galleryPreviews) - 1"` directly on a `<flux:button>` tag — a **colon-bound** attribute expression, not the bare `@disabled(...)` **directive call** the errors-log's 2026-08-31 entry documents as breaking the whole compiled view; the two forms are not equivalent to `livewire/blaze`'s tag compiler, and this story's own Phase 5 review is what narrowed that entry. See [errors-log.md](../../errors-log/2026-08-28-to-2026-08-31.md#a-bare-disableddisabled-inside-a-fluxbutton-tags-attribute-list-corrupts-the-whole-compiled-view--2026-08-31).
- **`/products` is linked from the sidebar only to a user holding `products.view`.** [`config/modules.php`](../../../config/modules.php) gained an `items.products` entry (icon `cube`, `route` `products.index`, `current_when` `products.*` — so the item stays highlighted on `products.create`/`products.edit` too — `permissions` **exactly** `['products.view']`), with matching leaves in `lang/{en,es}/navigation.php`. `resources/views/layouts/app/sidebar.blade.php` was **not** touched by story 0027 — the fifth confirmation in a row that a module registry entry costs data, not template edits. **It shipped as a flat item in the `groups.platform` group; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `product_categories` and `product_attribute_types` — its own name coincides with the cluster's, but per the story's own Q-1 it is just another equal cluster child, never the cluster's "home" link (the cluster carries no `route`/`current_when` of its own). See [`architecture/authorization.md`](../../architecture/authorization/how-to-gate.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema.

**This story also retires the one route this page used to deliberately keep out of the table.** `dev.media-gallery-harness` — story 0020's temporary, environment-gated scaffolding, extended by story 0021 to also host a `WysiwygEditor` instance — existed only because neither `Gallery` nor `WysiwygEditor` had a real page to be browser-tested against. `App\Livewire\Products\Editor` is that real page: both of the harness's browser test files (`tests/Browser/Media/GalleryTest.php`, `tests/Browser/Components/WysiwygEditorTest.php`) were re-pointed at `route('products.create')`/`route('products.edit', $product)` and made green against it, with the re-entrancy assertions strengthened rather than merely migrated (the WYSIWYG's own per-instance event name now competes against **two** real literals on the same page, not a second copy of itself). Once those files were green, `App\Livewire\Dev\MediaGalleryHarness`, its view, its `routes/web.php` registration block, and `tests/Feature/Dev/MediaGalleryHarnessRouteTest.php` were all deleted — verified with `Route::has('dev.media-gallery-harness')` returning `false` and a repository-wide grep for `media-gallery-harness` returning nothing. There is no longer a subsection for it on this page, by design: its own text said "if 0027 has shipped and this section still exists, the scaffolding was not removed," and this story is the proof it was.
