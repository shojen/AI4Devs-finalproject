# Products & Media Routes — product-attribute-types.index

> Part of [Products & Media Routes](../products.md). **Read this part when:** the task touches the product attribute types screen. The other parts are listed in the [hub](../products.md#table-of-contents).

### `product-attribute-types.index` — the fifth permission-gated route

Story 0028 (backend) and story 0030 (the real screen, replacing the backend-only placeholder — the same 0017→0018 split, closed the identical way). `App\Livewire\Products\AttributeTypes\Index` holds authorization, validation and action wiring in full (0028); [`resources/views/livewire/products/attribute-types.blade.php`](../../../resources/views/livewire/products/attribute-types.blade.php) (0030) is the real markup, not the one-line placeholder this subsection used to describe. Declared in its own [`routes/product-attribute-types.php`](../../../routes/product-attribute-types.php), the same shape every prior area file uses:

```php
// routes/product-attribute-types.php
use App\Livewire\Products\AttributeTypes\Index as ProductAttributeTypesIndex;   // aliased: `Index` is
// ambiguous across areas, exactly like every other area file's own import
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as every other
    // gated route in this app: Livewire 4's PersistentMiddleware allowlist carries
    // Laravel's `Authorize` (`can:`) but not Spatie's `PermissionMiddleware`, so a
    // `permission:`-gated route would protect the initial GET only, leaving every
    // save()/deleteType() /livewire/update round-trip unauthorized. See
    // docs/architecture/authorization.md.
    Route::livewire('products/attribute-types', ProductAttributeTypesIndex::class)
        ->middleware(['can:products.view'])
        ->name('product-attribute-types.index');
});
```

Thirteen consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route (same reason as `users.index`'s in [Users & Roles routes](../users-and-roles.md#usersindex--the-first-permission-gated-route): `verified` isn't Livewire-persistent either).** [`App\Livewire\Products\AttributeTypes\Index`](../../../app/Livewire/Products/AttributeTypes/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`, `openCreateModal()`/`save()` (create branch) ask `create`, `openEditModal()`/`save()` (edit branch) ask `update` against a freshly resolved target, and `confirmDelete()`/`deleteType()` ask `delete` against a freshly resolved target. **All six methods gate**, matching [security/livewire-authorization.md](../../security/livewire-authorization/entry-point-and-method-gates.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — including `openEditModal()`, which discloses the type's whole value list before any write.
- **The write path is protected twice over, designed that way from Phase 1 rather than retrofitted.** All three domain actions — [`CreateProductAttributeType`](../../../app/Actions/Products/CreateProductAttributeType.php), [`UpdateProductAttributeType`](../../../app/Actions/Products/UpdateProductAttributeType.php), [`DeleteProductAttributeType`](../../../app/Actions/Products/DeleteProductAttributeType.php) — authorize their own operation as their first statement, each constructor-injecting `App\Actions\Auth\LogRefusedPrivilegedAttempt` and passing `targetType: 'product_attribute_type'` explicitly (`resolveTarget()` auto-resolves only `User` and `Role`). A fourth action in the same folder, `App\Actions\Products\SyncProductAttributeValues`, deliberately authorizes **nothing** — the codebase's fifth shipped instance of "a collaborator invoked only by an already-authorized action needs no gate of its own"; see [architecture/authorization.md](../../architecture/authorization/policies-products.md#productattributetypepolicy--the-seventh-policy-and-the-first-whose-no-policy-recommendation-was-reversed-at-phase-2).
- **`Index` resolves to this screen's own subfolder-shaped flat view, per the established exception.** `App\Livewire\Products\AttributeTypes\Index` drops the `.index` segment and resolves to [`resources/views/livewire/products/attribute-types.blade.php`](../../../resources/views/livewire/products/attribute-types.blade.php) — one level *shallower* than the class, per the [`Index`-in-a-subfolder exception](../../conventions/naming/livewire-components-and-views.md#exception-a-component-named-index-resolves-to-its-parent-folders-name). **Since story 0030 this is the real screen**, mirroring `product-categories.blade.php`'s shape: a header with `typesSummary()`'s live `:total types · :values values` count and a primary "New attribute type" button; a `flux:table` of types (name, a value-count badge, a truncated value preview — the first five values joined with a `+N more` suffix built from `valueCount`, an em dash for a zero-value type — and icon-only edit/delete row actions, `data-test="edit-type-{id}"` / `"delete-type-{id}"`, rendered enabled or disabled from that row's `canEdit`/`canDelete`); a create/edit modal holding the name field plus a hand-rolled values repeater (no Flux repeater primitive exists) — each row a stable-`wire:key`, `chevron-up`/`chevron-down`/`trash` icon-only trio, `data-test` hooks keyed by the value's own database id when it has one (`$row['id'] ?? $row['key']`, since a test that seeded the fixture knows the id ahead of time but never the row's UI-only `key`, a fresh UUID minted on every `openEditModal()`/`addValue()` call); and a delete-confirmation modal reading `$deletingTypeName`.
- **The `@continue` guard skipping a malformed `$values` row must check every key the loop dereferences, not only the row's outer type** — a Phase 4 security-audit finding (F-1) fixed within this story rather than deferred: `$values` (and `$showModal`) are both client-writable, so a `products.view`-only actor can force this branch open with a forged row shape before `save()`'s own validation ever runs, and a row that *is* an array but is missing `key`, or whose `value` is non-scalar, crashed the render until the guard was widened to `@continue(! is_array($row) || ! isset($row['key']) || ! is_string($row['key']) || ! isset($row['value']) || ! is_string($row['value']))`.
- **The component's public surface**: `$types` (`#[Locked]` — entirely server-derived, the *stronger* side of the `#[Locked]` convention rather than `ProductCategories\Index::$productCategories`'s documented unlocked exception, since nothing here needs to be client-writable and locking costs nothing), the `#[Locked]` `$editingTypeId` (assigned only from `$target->id`, never the raw method argument — what makes the id fed to `attributeTypeNameRules()`'s `->ignore()` server-authoritative), `$showModal`, the plain `string $name` field, the deliberately **not** `#[Locked]` `array $values` (the form's own client-writable input, re-scoped against a fresh database read on every save — see [database/schema.md](../../database/schema-products/attribute-types-and-values.md#product_attribute_values)), the delete-modal trio `$showDeleteModal`/`#[Locked] $deletingTypeId`/`#[Locked] $deletingTypeName`/`#[Locked] $deletingTypeUsageCount` (real since story 0029a, not story 0030's own doing — `confirmDelete()` populates it from `App\Models\ProductAttributeType::variantUsageCount()`, the same query `App\Actions\Products\DeleteProductAttributeType`'s own in-use block consumes; see [database/schema.md](../../database/schema-products/attribute-types-and-values.md#product_attribute_types)), and — since story 0030a — the `#[Locked] array $valueUsageCounts` (`array<string, int>`, keyed by value id), populated once per `openEditModal()` call and reset alongside `$values` in both `closeModal()`/`openCreateModal()`. This view renders `$deletingTypeUsageCount` only inside the reactive blocked-delete message below, never as a proactive line in the confirmation dialog, matching `product-categories.blade.php`'s identical choice for its own in-use block.
- **Since story 0030a, `openEditModal()` also computes a per-row usage notice with one bulk query, never one query per row.** [`App\Models\ProductAttributeValue::variantUsageCounts()`](../../../app/Models/ProductAttributeValue.php) is called once with the type's own value ids and assigned to `$valueUsageCounts` — see [database/schema.md](../../database/schema-products/attribute-types-and-values.md#product_attribute_values) for how this bulk, display-oriented query differs from the type-level and per-value in-use queries story 0029a already shipped over the same pivot. The values repeater renders a muted, **non-blocking** `trans_choice('products.variants.rename_notice', ...)` notice beside any row whose count is positive, `data-test="value-in-use-notice-{id}"` — keyed by the row's own persisted id (the same `$rowHook` convention every other hook in this repeater already uses, never the row's UI-only, freshly-minted `key`). A row with no persisted id yet (an `addValue()`-created row) never renders the notice; the count read is guarded the same way `$rowHook` itself is, to avoid a PHP deprecation notice on undefined-key array access rather than crash.
- **A fourth `@error(...)` outlet, keyed `sku`, renders whichever refusal 0029's already-shipped SKU re-derivation cascade throws when a rename changes a derived SKU** — `derived_sku_taken`, `derived_sku_empty_segment`, `derived_sku_too_long`, or the translated unique-violation race message, all already produced by `SyncProductAttributeValues::reDeriveVariantSkusForRenamedValues()`/`DeriveVariantSku::checked()` (story 0029, unchanged here) and reused as-is with **no new translation key**. One generic `<flux:callout>`, styled like the two existing `@error('values')`/`@error('productAttributeTypeId')` precedents immediately beside it, renders whichever message fires with no per-message branching — the modal stays open and nothing is written, since 0029's transaction rolls back the whole rename on any of the four. Its `:heading="$message"` binding is deliberately **colon-bound**, unlike its two older siblings' `heading="{{ $message }}"` form: the double-brace form double-HTML-encodes a literal quote character inside `$message` under this Flux-folded tag (verified by `Blade::render()` execution), which is exactly what `derived_sku_empty_segment`'s own copy — the one message of the four containing a literal quote — exposes. This is a latent, pre-existing, non-security quirk on the two older callouts, left unchanged since neither's current copy contains a quote.
- **Both modal openers now call `resetValidation()` as their own last statement**, closing a Phase 4 audit finding: dismissing the modal via its `wire:model`-bound `$showModal` directly — the X control or a click outside, bypassing `closeModal()` entirely — left a stale `sku`/`values` error from a previously refused save rendering against a different, unrelated type on reopen, since Livewire persists the error bag across that round trip.
- **Two in-use guards story 0029a added to the backend now have their rendering, discharging that story's own explicit hand-off** ("the markup rendering the blocked-delete message is 0030's"). Deleting a type still backing any product variant throws a `ValidationException` keyed `productAttributeTypeId` — rendered as a `flux:callout` inside the still-open delete modal, the identical `@error('productAttributeTypeId')` pattern `product-categories.blade.php` already established for its own in-use block, naming the exact variant count via `trans_choice('products.variants.type_in_use', ...)`. Removing a value still backing any variant throws on the whole-array key `values` (not a per-row key, since the guard runs after the diff has already decided which ids are being deleted) — rendered as a `flux:callout` inside the still-open create/edit modal via `@error('values')`, naming the count via `products.variants.value_in_use`. Both refusals leave every other field's edits in place, since the whole save is one transaction that never partially applies (D-A5).
- **`removeValue()` and `moveValue()` take a stable, server-generated `key`, never an array index** — the single most important detail the UI sibling story inherits. Each value row is assigned `(string) Str::uuid()` once, when the row is created (`addValue()`, or read from the database in `openEditModal()`), and that key is what `wire:key` and every row-targeting method argument must use. Removing row 1 by *index* would shift row 2 into index 1, reuse the DOM node keyed `1`, and leave the browser's own input showing the old value while the server holds the new one — the standard Livewire foot-gun this design avoids entirely rather than works around.
- **`canEdit`/`canDelete` per row are UI hints, never a layer, and cannot drift from what a click would do.** `loadTypes()` writes `Gate::allows('update'|'delete', $type)` onto each row — the *same* policy methods `save()`/`deleteType()` authorize against. Like `SalesRegionPolicy`/`ProductCategoryPolicy`, `ProductAttributeTypePolicy::update()`/`delete()` ignore their target entirely, so this hint has **no accepted drift** — a property of the policy having no target-dependent branch, not a guarantee.
- **Two of this screen's `ValidationException`s are not row-shaped errors a naive read would expect.** A duplicate value within the same type surfaces as a validation error on `values.*.value` (`distinct:ignore_case`, run only after the array's size and each row's shape have already passed — see [database/schema.md](../../database/schema-products/attribute-types-and-values.md#product_attribute_values)'s Phase 4 findings subsection), never as an unhandled `QueryException` reaching the caller; and a race that slips past `distinct:ignore_case` is caught at the composite `UNIQUE(product_attribute_type_id, value)` index by `SyncProductAttributeValues`, which converts SQLSTATE `23000` into the identical `ValidationException` shape rather than letting a raw database error surface.
- **Since story 0030 this route has a `config/modules.php` entry** (`items.product_attribute_types`, gated on exactly `['products.view']`) and matching `lang/{en,es}/navigation.php` leaves — closing the linkless half-state the App-owned-routes preamble above records, the same split `sales-regions.index` sat in between tasks 0017 and 0018. **It shipped as a flat `group: platform` item; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `products` and `product_categories`.
